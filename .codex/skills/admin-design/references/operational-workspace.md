# 状态与行动工作台

适用于围绕一个租户、项目或流程展示当前状态和下一步有效操作的 Admin 页面，例如抖音小程序工作台。用户进入页面的主要任务是判断能否继续、处理阻断、执行当前动作；记录浏览、筛选和指标比较不是主任务。列表页、图表仪表盘和独立的大型编辑表单继续使用各自的布局规范。

## 信息顺序

1. 页面标题和一句业务说明。
2. 首屏状态与当前动作：用文字明确授权、版本或流程状态；最重要的可执行按钮与状态处于同一视觉层。权限不足、处理中或业务阻断时，保留动作的可见性并在附近说明原因。
3. 阻断与异常：紧接动作区逐项展示原因及到达修复位置的链接；正常就绪状态只需一行确认，避免重复成功提示。异步失败、审核驳回等真实异常保持清晰的错误文案。
4. 支撑信息：公开资料、少量内容计数、局部设置、最近版本等，用标题、字段和水平分隔线排列。详情与历史记录放在当前任务之后。
5. 验证材料：二维码、附件或预览优先放在对应动作附近，即使其他支撑信息都在下方；显示过期或不可用状态，不为材料增加一层 Card。

当阻断会使按钮不可执行时，在动作旁解释禁用原因，阻断明细可位于下一分区。当前动作允许多个并列选项，但只将推进流程的主要动作设为主按钮；同步、查看或维护入口用次要按钮或文字链接。

## 容器与层级

- 在中性页面背景上使用一张带 `bg-card` 样式的普通 `div` 作为页面底板；它是背景 surface，不是 `Card` 组件，也不需要边框、阴影或 `CardHeader`。内容按 `section` 排列，通常用 `border-b`、`py-5` 和留白分组。独立的错误提示可以使用 `Alert`。
- 不使用“总览 Card → 状态/动作 Card → 设置 Card”的层级。简单计数以 `dl`、标签和值展示，不做 KPI Card 网格；仅当指标比较本身是页面任务时，转用仪表盘规范。
- 开关与保存动作直接置于所属分区。若一组控件有自己的完整编辑流程、单独提交和独立错误处理，应拆为独立页面或 `Dialog`；不要在工作台底板中新增表单 Card 或工具 Card。
- 已经在首屏出现的状态不要在最近版本区重复做第二组 Badge。正常状态、最新模板及就绪结果不占用显眼 Alert；新版、过期、阻断和失败才提高视觉权重。
- 使用现有语义 token：`bg-card`、`text-foreground`、`text-muted-foreground`、`border-border` 和状态 Badge。主操作使用 `primary`，次要维护入口使用 `ghost` 或文字链接；不新增页面级颜色、渐变和装饰图标。

## 适配与验证

- 页面标题和底板在当前 Admin 内容区内对齐；可参考 `max-w-5xl`、底板 `px-5 sm:px-7`，但须服从周边页面与全局宽度偏好。
- 小屏按状态、动作、阻断、支撑信息纵向阅读。Badge 和按钮允许换行；长中文名称和错误原因可断行，AppID 等技术值可 `break-all`。二维码保持可扫码尺寸和清楚的替代文字。
- 保留键盘焦点、显式表单标签、非纯颜色状态表达，以及只读、加载、空态和错误态。客户端权限、请求、状态策略和服务端阻断规则不能因视觉简化而被隐藏或绕过。
- 审查时先看首屏能否找到状态与下一步；再检查是否有卡片嵌套、重复状态、无判断价值的 KPI Card 和正常状态 Alert。验证手机与桌面宽度下的文字、按钮、二维码，以及权限不足、阻断、过期和失败场景。

**仓库实例：** `apps/admin/components/douyin-miniapp/workspace.tsx`、`release-readiness-panel.tsx`、`workspace-lead-capture-config.tsx` 和 `workspace-qr-card.tsx`。这些文件是布局实例；业务权限与动作策略仍由各自现有代码负责。
