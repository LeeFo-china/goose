状态：追加隔离 SQL 验收已通过根代理运行及独立规格与质量审查。不是开发库或真实 API 放行记录。

## 覆盖范围

- `receipt-weighted-race.sql` 复用 `receipt-weighted-cost.sql` 的真实商品、价格命令和采购种子；新建同租户第二个仓库，不修改原仓库余额。
- 通过批次保存、内部拆单/审批会计入口与正式确认命令生成两张单：同 SKU，分别冻结为 3 件 × 20 元、7 件 × 30 元。改价调用真实 SKU 命令，不直接改采购单或库存事实。
- 两个独立 PostgreSQL 连接执行正式收货命令。连接 A 保持事务未提交，连接 B 异步执行另一张订单的收货；观察 B 实际进入锁等待后才提交 A。第一轮覆盖新余额创建，第二轮覆盖已有余额累加。
- 第一轮分别收 1 件、2 件，检查数量 3、金额 80、平均成本 26.6667；第二轮收余下 2 件、5 件，检查数量 10、金额 270、平均成本 27。
- 每轮核对库存流水和应付的条数及总金额；最终两单各两次收货，应付分别为 60 与 210。原仓库余额完整 JSON 不变，没有项目成本或预算占用。
- 全部收货后，用首轮原 receipt ID、key、version 和数量重放，必须返回原冻结响应，不新增库存/应付或改变余额版本、金额。

## 安全与执行证据

- 使用既有一次性离线 PostgreSQL runner，不发布端口、不挂载卷；两连接仅通过本容器 `/tmp` Unix socket 访问。锁等待观察 4 秒、各会话语句超时 8 秒。
- 种子与并发事务只提交到本次随机容器；正常路径断开 dblink，失败或结束时 runner 停止并自动删除该容器。未修改已有本地数据库、开发库或生产库。
- 根代理运行以下两份夹具 exit 0。首次尝试因测试中的 `ordinal` 列与局部变量同名而报歧义，限定表别名后通过；这不是业务缺陷 RED。没有为通过测试修改生产 SQL、约束或触发器。
- 组合性能测试时，须按 `receipt-weighted-cost.sql` → `inventory-read-performance.sql` → 本夹具的顺序执行。性能探针固定验证原租户 3 条收货流水加 10 万合成流水；本夹具另增加 4 条真实收货，放在性能探针之前会破坏其固定规模前提。首次 18 份组合运行因此在性能探针总数检查失败；没有放宽既有性能断言或删除已发生测试事实。
