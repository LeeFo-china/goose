# 工序完工与验收推进分离

## 问题与根因

项目 `397803a3-eed8-4c19-a23a-22d3956e2df4` 在水电配置 `trigger_acceptance=true` 时，2026-10-08 21:02:29（北京时间）执行 `complete_procedure` 已推进至中期款，21:04:03 推进至木工；水电验收 21:05:34 才创建，状态仍为 draft。

后端动作元数据允许完工，runtime guard 仅检查日志/图片，数据库 `complete_workflow_instance_node` 直接结束节点并推进。时间线将未确认验收显示为待验收，但运行态指针已改变。因此根因在后端推进规则，而非小程序自行跳转。

## 修复合同

- 仅针对 construction 工作流的 procedure 节点，且发布快照 `config.trigger_acceptance=true`。
- 工序完工在同一数据库事务保存节点 output 的 `procedure_completed`、完工时间/操作人，并完成对应派工及写入派工日志；实例、节点和任务仍停留在当前待验收阶段。
- 重复完工不改写首次事实、不重复派工日志、不推进流程。免派工节点同样受验收限制。
- 通用 complete 不能越过验收。客户确认必须匹配当前项目客户、当前阶段的最新非取消验收、真实 customer_confirmed 状态及确认时间；请求参数无法代替真实数据库记录。
- 客户确认写入前先检查当前必需工序的完工事实，未完工返回 409 且不保存确认状态；验证当前项目客户归属。
- 客户确认后，原有实例锁保证推进原子性。重复确认或历史补验收不再推进后续节点。
- 免验收节点保留原有完工推进行为。最终验收沿用原有专门链路。
- API 继续返回原有结果，增加可选 `awaitingAcceptance`。待验收时间线显示对应验收状态及发起/处理/查看动作，不再显示派工或重复完工动作。

## 验证及发布

- 隔离 PostgreSQL 测试 `supabase/tests/workflow_procedure_acceptance_gate.sql` 在旧函数下先复现失败，在新迁移下通过。
- 实际 SQL 覆盖完工保持当前节点、派工原子完成、任务 pending、重复完工、拒绝通用完成/伪造确认、拒绝未完工/未确认/主管通过/驳回/取消/错客户/错阶段/错验收、确认只推进一次、免验收、免派工和 RPC ACL。
- 测试 fixture 在事务结束回滚；生产只读核查，不代做真实验收。
- 迁移 `20261008140000_gate_procedure_completion_on_acceptance.sql` 只替换函数，不回填或重写历史业务行。
- 发布顺序：先部署兼容新旧 RPC 结果的 API，再应用迁移。旧 API 会在 SQL 原子完成派工后再次尝试完成派工，因此不可先迁移后部署旧 API。
- 回退：有待验收节点时只能通过后续 migration 前向修正；不得恢复会直接越过验收的旧函数，也不得删除完工事实。API 回退必须使用理解 awaitingAcceptance 的兼容版本。

聚焦 API 回归共 156 项通过（按隔离进程/兼容测试分组执行），包含既有收款、流程投影、免验收、历史补验收、竣工验收以及提前确认阻断。独立审查提出的提前确认状态写入问题已添加红绿回归。测试使用显式 dummy 环境，无生产写入。
