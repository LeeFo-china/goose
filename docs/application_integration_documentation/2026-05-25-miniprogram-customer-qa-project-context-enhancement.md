# 客户端 AI 项目问答上下文增强对接说明

## 背景

客户侧项目详情进入“AI 项目问答”后，前端已经按约定传：

```json
{
  "context": {
    "role": "customer",
    "project_id": "当前项目ID"
  }
}
```

但原后端注入的项目上下文只包含项目基础信息、房产信息、设计师/施工管理和最近 5 条施工日志。AI 可以从最近日志判断“当前大概在哪个工序”，但不知道施工阶段状态机里的下一步工序、阻塞原因、验收状态和未完成必需工序。

## 后端需对接的增强

建议后端增强 `POST /ai/decoration-qa/stream` 的项目上下文聚合逻辑：在 `context.role=customer` 且传入 `context.project_id` 时，除现有项目基础信息、房产信息、团队信息、最近施工日志外，再注入“施工阶段状态机”信息。

建议新增注入维度：

- 当前施工工序
  - `stage_code`
  - `stage_label`
  - `status`
  - `blocked_reason`
- 下一步施工工序
  - `stage_code`
  - `stage_label`
  - `status`
  - `blocked_reason`
- 必需工序是否全部完成
- 尚未完成的必需工序
- 全量施工阶段列表
  - 阶段名称
  - 阶段状态
  - 是否必需工序
  - 验收状态
  - 该阶段最近日志
  - 阻塞原因

## 后端对接状态

已对接。

后端在 `POST /ai/decoration-qa/stream` 解析到：

```json
{
  "context": {
    "role": "customer",
    "project_id": "project-id"
  }
}
```

时，会在系统上下文中注入施工阶段状态机信息。小程序端不需要新增字段，也不需要自行拼接项目详情、施工日志或阶段状态到用户问题文本。

如果阶段状态机查询失败，后端会在上下文中标记“施工阶段状态机：未同步”，并保留现有最近施工日志作为兜底上下文。

## 小程序端影响

小程序端无需新增请求字段，继续传原有结构即可。当前小程序侧已按该结构传递项目上下文：

```json
{
  "question": "我家现在施工到哪一步了？",
  "conversation_id": null,
  "context": {
    "role": "customer",
    "project_id": "project-id"
  }
}
```

需要确认的前端行为：

- 从客户项目详情进入 AI 问答时必须带 `projectId`。
- AI 问答页发请求时必须保持 `context.role=customer`。
- 不要由小程序端自行拼接项目详情、施工日志或阶段数据到问题文本里。

## 预期回答能力

后端完成增强后，AI 对以下问题应能基于后端已同步资料回答：

- “我家现在施工到哪一步了？”
- “下一步是什么工序？”
- “为什么还不能进入下一阶段？”
- “还有哪些工序没完成？”
- “当前阶段我需要注意什么？”

如果施工阶段状态机没有同步到足够信息，AI 仍应按提示词要求说明“根据当前已同步的项目资料，暂时无法确认更多细节”，不能编造进度。

## 建议后端实现口径

- 复用现有 `GET /customer/projects/:id/construction-stages` 或同源服务层的阶段计算逻辑。
- AI 项目上下文中，回答进度、下一步工序、能否进入下一阶段时，应优先使用施工阶段状态机，而不是只根据最近施工日志推断。
- 如果施工阶段状态机查询失败，可以保留现有最近日志兜底，但需要在上下文中明确“施工阶段状态机未同步”。
- 不建议由小程序端把项目详情、施工日志或阶段数据拼到用户问题文本里，避免上下文不一致和权限边界分散。

## 验收建议

使用一个已进入施工阶段的客户项目验证：

1. 客户项目详情点击“AI 项目问答”。
2. 提问“我家现在施工到哪一步了？”
3. 提问“下一步是什么？”
4. 提问“为什么还不能进入下一阶段？”
5. 核对回答是否和 `GET /customer/projects/:id/construction-stages` 的 `current_stage`、`next_stage`、`missing_required_stages` 一致。
