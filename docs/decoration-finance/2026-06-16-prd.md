# 装修公司财务系统 PRD

日期：2026-06-16

## 1. 背景

Gooes 当前已经具备装修业务的核心基础：

- 客户、项目、员工、部门、岗位、角色和权限。
- 多租户隔离。
- 项目状态和施工 workflow。
- 任务中心。
- 项目收款 `payments`。
- 费用申请 `expense_requests`。
- 费用审批和打款已经可以通过 workflow task bridge 承接。
- Admin 已支持流程编排，项目 workflow 已支持财务收款节点方向。

但目前财务能力仍然是分散的：

1. `payments` 更像项目收款记录，还没有完整应收计划、欠款、回款进度和利润口径。
2. `expense_requests` 已经具备报销审批雏形，但还没有和项目成本、利润报表形成统一闭环。
3. workflow 能控制流程推进，但不应该成为财务统计事实来源。
4. 老板、财务、项目经理缺少统一视角来判断项目是否赚钱、款项是否逾期、成本是否超预算。

因此，本 PRD 建议建设“装修公司经营财务系统”，优先解决装修公司日常经营里的项目收款、项目成本、费用审批、财务台账和项目利润问题，而不是一开始建设完整会计总账系统。

## 2. 产品定位

本系统定位为：

> 面向装修公司的项目经营财务系统。

第一阶段重点服务：

- 财务人员：登记收款、审核费用、登记付款、查看台账。
- 项目经理：查看项目收款进度、提交项目费用、跟踪项目成本。
- 管理者：查看项目利润、回款、成本、逾期应收和经营概览。

第一阶段不定位为完整会计软件，不覆盖法定财务报表、复杂会计科目、凭证借贷、税务申报和银行自动对账。

## 3. 目标

### 3.1 业务目标

1. 每个项目能清楚看到合同金额、应收金额、已收金额、未收金额。
2. 每个项目能归集费用、报销、材料、人工、分包等成本。
3. 每个项目能实时计算毛利和毛利率。
4. 财务动作能进入 workflow 和任务中心，避免线下沟通遗漏。
5. 财务数据能沉淀成统一台账，支持后续报表。
6. 财务审批和收款确认过程可追溯。

### 3.2 系统目标

1. 复用现有 `payments`、`expense_requests`、workflow、task-center 和权限体系。
2. 新增财务台账层，避免报表直接依赖 workflow 历史。
3. 所有列表接口必须分页。
4. 所有数据库结构变化必须通过 Supabase migration。
5. 所有财务动作必须具备租户隔离、权限校验和审计信息。

## 4. 非目标

第一阶段不做：

1. 完整会计总账、科目表、借贷凭证。
2. 税务申报、发票验真、银行流水自动对账。
3. 客户小程序在线支付。
4. 供应商门户或班组门户。
5. 自动催款短信和自动催款计划。
6. 复杂预算体系和成本预测模型。
7. 跨租户财务合并报表。

这些能力可以在项目经营财务闭环稳定后分阶段扩展。

## 5. 角色和权限

### 5.1 财务人员

财务人员需要：

- 查看待确认收款任务。
- 新增、确认、驳回项目收款。
- 查看费用申请。
- 财务审核费用。
- 登记费用打款。
- 查看财务台账。
- 查看项目收支和利润。

### 5.2 项目经理

项目经理需要：

- 查看自己负责项目的收款计划和收款进度。
- 提交项目费用或报销。
- 查看项目成本汇总。
- 处理需要项目经理审批的费用任务。
- 在项目详情中看到财务节点状态。

### 5.3 管理者

管理者需要：

- 查看全公司项目收入、成本、毛利。
- 查看逾期应收。
- 查看待审批的大额费用或超预算费用。
- 查看项目利润排行和异常项目。

### 5.4 普通员工

普通员工需要：

- 提交费用申请。
- 查看自己的费用申请状态。
- 根据 workflow 处理分配给自己的审批任务。

## 6. 核心原则

### 6.1 workflow 驱动动作，不承载财务事实

workflow 负责：

- 谁处理。
- 什么时候处理。
- 节点是否可以推进。
- 审批路径和任务分派。

财务模块负责：

- 应收。
- 实收。
- 应付。
- 实付。
- 成本。
- 退款。
- 利润。
- 凭证。
- 台账。

报表不得直接扫描 workflow 历史来计算收入、成本或利润。

### 6.2 财务事实必须落业务表和台账

项目收款、费用打款、退款、成本确认等动作必须落到业务表，并同步形成财务台账记录。

推荐数据流：

```text
workflow task/action
        |
        v
finance service command
        |
        v
business table: payments / expense_requests / future supplier_payments
        |
        v
finance_ledger_entries
        |
        v
dashboard / reports / project profit
```

### 6.3 平台计费和装修公司财务隔离

现有 `billing` 模块用于平台对租户的积分、AI、短信等用量计费，不应混入装修公司内部财务。

装修公司经营财务应独立建模，避免把平台 SaaS 计费和租户内部收支混在一起。

### 6.4 支付能力采用平台统一网关、租户独立商户配置

后续接入微信支付时，不采用“所有装修项目款进入平台统一商户号”的模式。项目款
属于租户装修公司的经营收入，应优先采用：

```text
平台统一支付能力 + 租户独立商户/子商户配置
```

平台统一负责：

- 微信支付 API 封装。
- 证书和密钥托管能力。
- 回调验签、幂等、状态查询、退款封装。
- 支付结果写入 `payments` 和 `finance_ledger_entries`。
- 根据 payment 关联的 workflow task 推进 `payment_collection` 节点。

租户独立负责：

- 商户号或子商户号。
- 结算账户和资金归属。
- 支付开通状态。
- 可用支付渠道。
- 退款、付款、转账等高风险能力开关。

如果未来采用微信支付服务商模式，平台可以作为服务商统一接入，租户作为特约商户
或子商户承接资金结算；如果租户使用自己的直连商户号，也应作为租户级支付配置
接入同一套 payment service。无论采用哪种商户接入模式，业务系统中最终都统一
归一为 `payments.status = confirmed`，再写台账并推进 workflow。

## 7. 功能范围

## 7.1 项目收款

### 目标

让财务和项目成员清楚知道项目应该收多少钱、已经收了多少钱、还有多少钱未收。

### 第一阶段能力

1. 项目下展示收款记录。
2. 支持收款类型：
   - 意向定金 `deposit`
   - 开工首付款 `stage_1`
   - 中期进度款 `stage_2`
   - 工程尾款 `stage_3`
   - 后期增项款 `add_on`
   - 退款 `refund`
3. 支持收款状态：
   - 待确认
   - 已确认
   - 已驳回
   - 已退款
4. 财务确认收款时记录：
   - 金额
   - 收款类型
   - 收款时间
   - 确认人
   - 凭证图片
   - 备注
   - 来源 workflow task
5. 项目详情展示：
   - 合同金额
   - 已收金额
   - 未收金额
   - 收款进度
   - 最近收款记录

### workflow 集成

项目 workflow 中的 `payment_collection` 节点进入后，应生成或暴露财务待办任务。

第一阶段采用“先创建已确认收款，再完成 workflow task”的规则。也就是说，
收款节点不是单纯点一下放行，而是财务必须先提交本次入账金额和收款凭证，
后端创建 `status = confirmed` 的收款记录后，才能推进 workflow。

财务完成任务时：

1. 后端校验当前员工是否为任务 assignee 或具备对应权限。
2. 财务提交入账金额、收款时间、凭证图片和备注。
3. 后端创建或确认 `payments.status = confirmed` 的收款记录。
4. 后端写入财务台账。
5. 后端完成 workflow task，workflow 节点推进。

该流程应由后端财务命令统一编排，避免前端先调 `/payments`、再调
`/workflow-tasks/:id/complete` 造成部分成功。若同一个 workflow task 重复提交，
后端必须通过 `workflow_task_id`、`source_type/source_id` 或幂等键避免重复入账。

如果创建 confirmed payment 失败，workflow task 必须保持 pending；如果 payment
已经创建但 workflow complete 失败，后端必须能安全重试，不得重复生成收款和台账。

## 7.2 收款计划

### 目标

从“收款记录”升级为“应收计划 + 实收记录”，支持欠款和逾期管理。

### 第二阶段能力

1. 项目签约后生成收款计划。
2. 收款计划可按固定金额或合同金额比例配置。
3. 收款计划字段：
   - 项目 ID
   - 收款阶段
   - 应收金额
   - 应收日期
   - 已收金额
   - 状态
   - 逾期天数
4. 收款记录可以核销到收款计划。
5. 管理者可查看逾期应收列表。

### workflow 集成

收款计划可以由流程节点配置触发：

- 签约节点完成后生成首款计划。
- 施工节点完成后生成阶段款计划。
- 增项确认后生成增项款计划。

收款节点推进时，应优先校验对应收款计划是否已完成或达到最低收款金额。

## 7.3 费用申请和报销

### 目标

让员工和项目经理能提交费用申请，费用通过审批后由财务打款，并归集到项目成本。

### 当前基础

现有 `expense_requests` schema 已经支持：

- 多费用明细。
- 项目关联。
- 费用模式。
- 审批链。
- 经理审核。
- 财务审核。
- 财务打款。
- 凭证图片。

### 第一阶段能力

1. 员工创建费用申请。
2. 支持草稿、提交、审批、驳回、撤回、打款完成。
3. 支持多费用明细。
4. 费用可关联项目。
5. 财务打款后写入项目成本台账。
6. 项目详情展示费用成本汇总。

### workflow 集成

费用申请提交后创建 workflow subject。

推荐固定流程：

```text
submit -> manager_review -> finance_review -> payment -> paid
```

workflow task 完成时，由 bridge 调用费用服务：

- `manager_review` 通过：费用进入下一节点。
- `finance_review` 通过：费用进入待打款。
- `payment` 完成：登记打款，费用变为已支付，写入台账。

## 7.4 项目成本

### 目标

按项目归集真实成本，为利润计算服务。

### 第一阶段成本来源

1. 已支付费用申请。
2. 手工录入的项目成本。
3. 后续供应商付款。
4. 后续班组结算。

第一阶段建议先以已支付费用申请和手工项目成本为主。

### 成本分类

建议第一阶段支持基础分类：

- 材料费
- 人工费
- 分包费
- 设计费
- 运输费
- 管理费
- 其他费用

分类可以先使用稳定字典，不必一开始做复杂科目体系。

## 7.5 财务台账

### 目标

为报表和审计提供统一事实表。

### 台账范围

所有会影响项目经营财务的动作都应写入台账：

- 项目收款确认。
- 项目退款确认。
- 费用打款完成。
- 手工成本确认。
- 后续供应商付款。
- 后续班组结算。

### 推荐字段

```text
id
tenant_id
project_id
direction: income / expense
entry_type
source_type
source_id
amount
occurred_at
confirmed_by
description
metadata
created_at
updated_at
```

### 约束

1. 台账记录必须可追溯到来源业务单据。
2. 同一来源业务单据不能重复入账。
3. 台账只记录已确认的财务事实，不记录草稿或待审批状态。
4. 台账列表必须分页。
5. 高频统计查询必须按租户、项目、时间范围建立必要索引。

## 7.6 项目利润

### 目标

让管理者和项目经理实时看到项目经营结果。

### 第一阶段指标

项目维度：

- 合同金额。
- 已收金额。
- 未收金额。
- 已确认成本。
- 毛利。
- 毛利率。
- 回款进度。

计算口径：

```text
毛利 = 已收金额 - 已确认成本
毛利率 = 毛利 / 已收金额
```

如果项目已签约但尚未完全收款，可以额外展示预测口径：

```text
预计毛利 = 合同金额 - 已确认成本
预计毛利率 = 预计毛利 / 合同金额
```

第一阶段应明确区分“现金口径”和“合同口径”，避免误导管理者。

## 7.7 财务看板

### 目标

给财务和管理者一个经营概览。

### 第一阶段看板

1. 本月已收金额。
2. 本月已付成本。
3. 本月净现金流。
4. 逾期应收金额。
5. 待确认收款数量。
6. 待财务审核费用数量。
7. 待打款费用数量。
8. 毛利异常项目列表。

所有列表必须分页或限制条数。概览统计必须限定租户和时间范围。

## 8. 页面需求

## 8.1 Admin 财务总览

入口建议：`财务管理 / 财务总览`

展示：

- 关键指标卡片。
- 待处理任务入口。
- 逾期应收列表。
- 项目利润排行。
- 最近财务流水。

Admin 菜单第一阶段建议新增独立“财务”分组，避免继续把装修公司内部财务和
平台/租户计费账户混在一起。现有 `费用审批` 可以迁入该分组；现有 `计费账户`
仍表示平台 SaaS 用量计费，不应改造成装修公司财务入口。

## 8.2 项目财务详情

入口建议：项目详情页新增“财务”页签。

展示：

- 收款进度。
- 收款记录。
- 费用成本。
- 财务台账。
- 项目利润。
- 当前 workflow 财务节点。

当前项目详情已有 workflow 收款闸门能力，第一阶段应复用现有收款节点状态、
收款记录查询和 workflow action，不要在财务页签里另做一套独立推进逻辑。

## 8.3 收款管理

入口建议：`财务管理 / 收款管理`

能力：

- 分页查看收款记录。
- 按项目、客户、状态、类型、时间筛选。
- 新增收款。
- 确认收款。
- 驳回收款。
- 上传凭证。

当收款来自 workflow task 时，Admin 和小程序应使用同一套后端命令：提交金额、
凭证、收款时间和备注，由后端创建 confirmed payment、写台账、完成 workflow。
Admin 不应长期保留“先单独创建 payment，再手动推进 workflow”的双提交路径。

## 8.4 费用管理

入口建议：`财务管理 / 费用管理`

能力：

- 分页查看费用申请。
- 按状态、项目、申请人、时间筛选。
- 查看费用详情和审批记录。
- 财务审核。
- 财务打款。

## 8.5 财务台账

入口建议：`财务管理 / 财务台账`

能力：

- 分页查看台账。
- 按项目、方向、类型、来源、时间筛选。
- 查看来源单据。
- 导出能力后续再做。

## 8.6 小程序员工端对接

小程序第一阶段不建设完整财务后台，但必须支持财务人员处理 workflow 收款待办。

### 项目收款节点

当项目当前 workflow 节点为 `payment_collection`，且当前员工是该 task 的
处理人时，小程序应从后端返回的 `workflow_state.actions` 或
`GET /workflow-tasks` 中展示“确认收款”操作。

小程序识别收款动作只依赖后端 action metadata：

```text
business_domain = payment_collection
business_action = confirm_payment
output_fields[].type = payment_collection
```

小程序不得根据本地角色、岗位、部门或项目状态自行补出收款按钮。

财务人员点击确认收款时，小程序必须收集：

- 入账金额。
- 收款凭证图片，至少 1 张。
- 收款时间，默认当前时间。
- 备注，可选。

提交仍以 workflow task 为入口，但 output 必须携带收款信息：

```json
{
  "action": "complete",
  "reason": null,
  "output": {
    "payment_status": "success",
    "amount": 10000,
    "paid_at": "2026-06-16T10:00:00.000Z",
    "evidence_images": ["https://..."],
    "remark": "中期进度款入账"
  }
}
```

后端收到后必须先创建 `payments.status = confirmed` 的收款记录，再写入财务台账，
最后完成 workflow task。小程序不直接调用 `/payments` 创建收款，避免客户端
两步提交导致 payment 已创建但 workflow 未推进。

### 费用申请

小程序继续复用现有费用申请页面和 workflow action：

- 费用草稿、新建、提交继续走 `/expense-requests` 和 `/expense-requests/:id/submit`。
- 审批、驳回、打款继续使用 `workflow_state.actions` 中的 task，通过
  `POST /workflow-tasks/:taskId/complete` 完成。
- 财务打款时继续上传打款凭证，后端在打款成功后写入财务台账。

### 任务中心

小程序任务中心继续以 `/workflow-tasks?page=1&pageSize=20` 为唯一待办来源。

- `payment_collection` 显示为“项目收款”。
- `expense_request` 显示为“费用申请”。
- task 可见性完全由后端 assignee 和权限过滤决定。
- 收款节点 complete 成功后，刷新项目详情和任务中心，不在本地手动推进 timeline。

## 9. 典型流程

## 9.1 项目阶段款确认

```text
项目进入中期款收款节点
        |
财务收到任务中心待办
        |
财务输入金额、上传凭证并确认收款
        |
系统创建 confirmed payment
        |
系统写入 finance_ledger_entries
        |
workflow 推进到下一施工节点
        |
项目利润和收款进度更新
```

## 9.2 员工报销

```text
员工提交费用申请
        |
系统创建费用 workflow subject
        |
项目经理审批
        |
财务审核
        |
财务登记打款
        |
系统写入费用结算记录
        |
系统写入 finance_ledger_entries
        |
项目成本和利润更新
```

## 9.3 超预算费用审批

```text
费用提交后系统计算项目成本
        |
超过预算阈值
        |
workflow 增加管理者审批节点
        |
管理者通过
        |
财务继续审核和打款
```

超预算能力不作为第一阶段必做，但数据模型和 workflow 设计应预留。

## 10. 数据和技术方向

## 10.1 建议新增核心表

第一阶段建议至少新增：

1. `finance_ledger_entries`
2. `project_manual_costs` 或等价项目成本表

同时需要小步增强现有 `payments`，确保能承载 workflow 收款确认：

- `paid_at` 或等价收款时间字段。
- `handled_by` 或等价确认人字段。
- `evidence_images` 凭证图片数组。
- `remark` 备注。
- `workflow_task_id` 或 `source_type/source_id`，用于追溯和幂等。

如果这些字段已在数据库存在但未进入 API schema，需要补齐 schema、service 和
Admin/小程序请求契约；如果数据库缺失，必须通过 Supabase migration 增加。

第二阶段再新增：

1. `project_receivable_plans`
2. `project_receivable_plan_allocations`

接入微信支付前需要新增租户级支付配置表，建议命名为
`tenant_payment_configs` 或等价名称，用于存储：

- `tenant_id`
- `provider = wechat_pay`
- `merchant_mode = service_provider_sub_merchant / direct_merchant`
- `merchant_id` 或 `sub_merchant_id`
- `app_id` / `sub_app_id`
- `status`
- `enabled_channels`
- `settlement_account_summary`
- 加密后的证书、密钥引用或密钥管理引用
- 高风险能力开关，例如退款、付款、转账
- 创建人、更新人、启停时间

敏感配置必须加密或引用密钥管理系统，不允许明文存储在普通 JSON 字段中。

如现有 `payments` 字段不足，应通过 migration 小步增强，而不是重建整套收款模型。

## 10.2 服务边界

建议新增或收敛以下服务：

- `finance-ledger`：台账写入和查询。
- `project-finance`：项目财务汇总、利润计算。
- `payment`：项目收款业务。
- `expense-requests`：费用申请、审批、打款。
- `workflow-task-* bridge`：只做 workflow task 到业务 command 的转换。
- `workflow-task-payment-bridge`：处理 `payment_collection` task，负责先创建
  confirmed payment、再写台账、最后推进 workflow。

controller 只处理 HTTP、参数校验和响应包装；service 做业务编排；repository 负责 Supabase 查询。

## 10.3 权限边界

第一阶段确定新增 `finance.*` 权限码，作为装修公司经营财务的权限命名空间：

- `finance.view`
- `finance.payment.create`
- `finance.payment.confirm`
- `finance.expense.review`
- `finance.expense.pay`
- `finance.ledger.view`
- `finance.dashboard.view`

现有权限的迁移关系：

- 项目收款第一阶段从 `project.update` 迁移到 `finance.payment.create` /
  `finance.payment.confirm`。
- 费用财务审核从 `expense_request.approve_finance` 逐步迁移到
  `finance.expense.review`。
- 费用打款从 `expense_request.pay` 逐步迁移到 `finance.expense.pay`。
- 迁移期可以同时兼容旧权限和新权限，但新页面、新 workflow task assignee
  和新接口应优先使用 `finance.*`。

workflow task 指派规则：

- 指定财务员工处理时，使用 `assignee_employee_id`。
- 任意财务人员可处理时，使用 `assignee_permission_code = finance.payment.confirm`。
- 不允许 `payment_collection` task 在无 assignee 的情况下对所有员工可见。

项目经理查看自己项目财务时，应基于项目成员关系或项目负责人关系控制范围。

## 10.4 性能要求

1. 所有财务列表必须分页，默认 `page=1&pageSize=20`，最大 `pageSize=100`。
2. 财务台账查询必须支持租户、项目、时间范围过滤。
3. 收款、费用、台账的高频筛选字段必须有索引。
4. 项目利润列表不能对每个项目做 N+1 汇总查询。
5. 大范围报表应通过聚合查询或预聚合策略实现，但第一阶段不引入缓存或队列。

## 11. 分期计划

## 11.1 第一阶段：项目财务闭环

目标：项目收入、成本、利润能闭环。

范围：

1. 项目财务详情页。
2. 收款节点确认时创建 confirmed payment 并写入台账。
3. 费用打款后写入台账。
4. 项目利润计算。
5. 财务台账列表。
6. workflow 收款节点和费用打款节点沉淀财务事实。
7. 小程序财务人员可以在收款 task 中输入金额和凭证。

验收：

- 一个项目完成收款确认后，生成 confirmed payment，项目已收金额更新。
- 一个项目完成费用打款后，项目成本更新。
- 项目利润能正确计算。
- 财务台账能追溯到来源单据。
- workflow 节点推进不会丢失财务事实。
- 同一个 workflow task 重复提交不会重复生成收款和台账。

## 11.2 第二阶段：应收计划和逾期管理

目标：从记录已发生收款，升级到管理应该收款。

范围：

1. 项目收款计划。
2. 合同金额比例配置。
3. 应收计划核销。
4. 逾期应收列表。
5. workflow 节点生成或校验应收计划。

## 11.3 第三阶段：成本预算和超预算审批

目标：控制项目成本风险。

范围：

1. 项目预算。
2. 成本分类。
3. 预算 vs 实际。
4. 超预算 workflow 审批。
5. 管理者异常项目看板。

## 11.4 第四阶段：供应商、班组和发票

目标：覆盖更完整装修财务场景。

范围：

1. 供应商管理。
2. 供应商付款。
3. 班组结算。
4. 发票记录。
5. 经营报表导出。

## 12. 验收标准

第一阶段完成时，至少满足：

1. 财务可以在 Admin 或小程序确认一笔项目收款。
2. 收款确认时必须填写金额并上传至少一张凭证。
3. 收款确认后，后端生成 `status = confirmed` 的 payment。
4. 收款确认后，项目财务详情展示已收金额变化。
5. 收款确认后，财务台账新增收入记录。
6. 员工可以提交项目费用申请。
7. 费用通过 workflow 审批并完成打款后，财务台账新增支出记录。
8. 项目成本随费用打款更新。
9. 项目利润和毛利率可查看。
10. 财务列表接口全部分页。
11. 财务数据按租户隔离。
12. 财务动作有操作人、时间、来源单据和凭证。

## 13. 风险和注意事项

1. 不要把 workflow 历史作为利润计算来源，否则报表会难以维护。
2. 不要把平台 `billing` 和装修公司内部财务混用。
3. 不要一次性引入完整会计系统，第一阶段先把项目经营财务闭环跑通。
4. 金额字段口径必须统一，避免同一系统里同时出现元、分、小数积分等混乱单位。
5. 台账写入需要幂等，避免重复确认导致重复入账。
6. 所有数据库变更必须走 migration。
7. 涉及项目列表、台账列表、报表统计时必须考虑分页和查询性能。
8. 收款 task 必须避免 payment 创建成功但 workflow 未推进后的重复入账风险。

## 14. 已确认决策

1. 第一阶段以“项目财务详情 + 财务台账 + 项目利润”为主线。
2. 收款 workflow 采用“先创建 confirmed payment，再 complete workflow task”。
3. 小程序财务人员确认收款时必须输入金额并上传凭证。
4. 第一阶段新增 `finance.*` 权限命名空间。
5. 微信支付等线上收付款能力采用“平台统一支付网关 + 租户独立商户/子商户配置”，
   不让租户项目款进入平台统一商户号。
