# 平台共享与租户私有供应商体系设计

**日期：** 2026-08-13
**状态：** 已确认，待实施规划
**影响范围：** 供应商、合作关系、商品、SKU、分类、品牌、规格、单位、价格和采购单

## 1. 决策摘要

供应商体系采用“统一主表、永久所有权、单向共享”模型：

- 平台供应商和平台商品由平台维护，所有租户可以复用。
- 租户自行创建的供应商、商品、分类和品牌永久属于该租户。
- 租户私有数据不能升级、转换或合并成平台共享数据。
- 租户不能修改平台共享供应商或平台共享商品。
- 租户可以在平台共享供应商下创建本租户私有商品，不影响其他租户。
- 供应商采购价始终属于租户，不因供应商或商品是平台共享数据而共享。
- 平台分类、品牌和单位构成装修行业标准字典；租户可以补充永久私有的分类和品牌，并建立只读映射。
- 项目采购统一引用合作供应商、商品和 SKU，提交时保存完整业务快照。

供应商、商品、分类和品牌使用统一主表，通过不可变所有权字段区分平台共享数据与租户私有数据。合作关系、合同、价格和采购单始终属于具体租户。

## 2. 背景与现状

当前系统已经具备：

- 平台统一供应商主档和准入流程。
- 租户从平台目录建立供应商合作关系。
- 租户采购员为合作供应商代录供应商级商品、SKU 和基础供货价。
- 采购申请、采购单、履约、应付和付款闭环。
- 平台标准分类、品牌和单位字典。

现有模型不能完整支持租户自建采购体系：

1. 租户不能创建永久私有的供应商主档，只能选择平台已准入供应商。
2. 当前商品归属于供应商主体，租户代录后可能被其他合作该供应商的租户看到或修改。
3. 分类和品牌只有平台标准层，租户无法补充本企业需要的私有资料。
4. 供应商编码是平台全局编码，没有独立的租户内部编码分配规则。
5. 当前 `tenant_proxy` 语义把租户商品维护视为替供应商代操作，不适合租户合法维护自己的私有采购资料。

本设计替代“所有供应商和商品最终进入平台共享库”的方向，建立明确、不可逆的所有权边界。

## 3. 目标与非目标

### 3.1 目标

- 租户能够创建和维护永久私有供应商。
- 租户能够为平台供应商或私有供应商创建永久私有商品和 SKU。
- 平台能够维护全租户共享的供应商、商品、分类、品牌、规格和单位。
- 租户能够补充永久私有的分类、品牌和规格模板。
- 平台共享数据与租户私有数据使用统一引用契约，避免采购单维护两套外键。
- 从认证上下文确定租户范围，客户端不能改变数据所有权。
- 采购申请和采购单可以使用当前租户可见且合作有效的共享或私有商品。
- 历史采购单通过快照保持稳定，不受主数据后续修改影响。
- 所有列表分页，查询限定必要字段并具备明确索引边界。
- 现有供应商、商品、价格和采购数据能够安全迁移。

### 3.2 非目标

本阶段不实现：

- 把租户私有供应商申请升级为平台供应商。
- 把租户私有商品、分类或品牌转成平台共享资料。
- 不同租户之间共享、转让或合并私有供应商资料。
- 自动根据名称、信用代码或相似度合并供应商。
- 供应商门户认证和供应商自助维护。
- 租户自由创建计量单位。
- 自动把历史自由文本 `vendor_name` 或 `payee_name` 转成供应商。
- 跨租户集中采购或跨公司采购合单。

## 4. 核心原则与不可变约束

### 4.1 永久所有权

共享与私有是创建时确定且不可修改的事实：

```text
ownership_scope = platform  -> owner_tenant_id IS NULL
ownership_scope = tenant    -> owner_tenant_id IS NOT NULL
```

数据库约束、受控命令和触发器必须禁止更新 `ownership_scope` 和 `owner_tenant_id`。

### 4.2 单向共享

- 平台共享数据可以被所有满足业务门禁的租户复用。
- 租户私有数据只能由所属租户访问。
- 私有数据不能变成平台数据，平台数据也不能降级为租户数据。
- 相似或重复数据只提示，不自动合并、不改变所有权。

### 4.3 主档与合作关系分离

`suppliers` 表示供应商主体，`tenant_suppliers` 表示租户与供应商的合作关系。

- 平台供应商需要租户主动建立合作关系后才能进入采购流程。
- 租户私有供应商创建时原子创建所属租户的合作关系。
- 合同、账期、授信、负责人、租户黑名单和采购价属于合作租户，不写回供应商主档。

### 4.4 历史事实不可回写

采购申请和采购单在提交时各自冻结供应商、商品、规格、单位、税率和价格快照，不能因主数据更新而改变。收货、退货、履约、应付和付款不重复复制整套主数据快照，只保存采购单 ID、采购单行 ID、自身业务事实和必要的展示冗余；其供应商和商品历史口径始终追溯到已提交采购单快照。

## 5. 领域模型

### 5.1 所有权类型

共享领域新增稳定值：

```ts
type OwnershipScope = "platform" | "tenant";
```

所有支持双层数据的表统一使用：

- `ownership_scope`
- `owner_tenant_id`
- `created_by_employee_id`
- `updated_by_employee_id`
- `version`
- `created_at`
- `updated_at`

平台与租户写入口不能接受客户端直接传入所有权字段；所有权由 controller 和 service 所在上下文确定。

### 5.2 供应商主档

`suppliers` 增加：

- `ownership_scope`
- `owner_tenant_id`

平台供应商：

- `ownership_scope = platform`
- `owner_tenant_id = null`
- 由平台准入、审核、暂停和拉黑。
- 所有租户可在共享目录中发现。

租户私有供应商：

- `ownership_scope = tenant`
- `owner_tenant_id = 当前租户`
- 不需要平台审核。
- 不进入平台共享供应商目录。
- 其他租户和普通平台运营人员不可见。

供应商编码唯一规则：

- 平台供应商编码在平台作用域内唯一。
- 租户私有供应商编码在所属租户内唯一。
- 不同租户可以拥有相同内部编码。
- 编码创建成功后不可修改。

`suppliers.code` 是供应商所有者维护的主档编码：平台供应商保存平台编码，租户私有供应商保存所属租户的内部编码。`tenant_suppliers.internal_supplier_code` 是采购方在合作关系中使用的内部编码：

- 对平台供应商，两者可以不同，采购界面同时展示平台编码和租户内部编码。
- 对租户私有供应商，创建者同时是所有者和采购方，两者必须相同，由原子创建命令一次写入。
- 采购单同时保存供应商主档编码和合作关系内部编码快照，不根据供应商类型省略字段。

统一社会信用代码唯一规则：

- 平台供应商在平台作用域内唯一。
- 租户私有供应商在所属租户内唯一。
- 租户创建时若命中平台相似供应商，界面提示优先复用平台供应商，但允许继续创建永久私有供应商。

### 5.3 租户合作关系

`tenant_suppliers` 继续保存：

- `tenant_id`
- `supplier_id`
- 合作状态
- 结算账期和授信额度
- 发票要求
- 默认币种和含税规则
- 租户负责人
- 合作日期和备注

新增或明确：

- `internal_supplier_code`：当前租户对该合作供应商使用的内部编码，新建合作关系时必填。
- `(tenant_id, internal_supplier_code)` 唯一。

对租户私有供应商，`tenant_suppliers.tenant_id` 必须等于 `suppliers.owner_tenant_id`。数据库命令必须禁止其他租户为该私有供应商建立合作关系。

对平台供应商，各租户独立建立合作关系，并可拥有不同的内部供应商编码、合同、价格和状态。

### 5.4 供应商内部编码

新增供应商表单支持手工输入和一键生成。

推荐格式：

```text
SUP-000001
SUP-000002
SUP-000003
```

规则：

- 编码在当前租户内唯一。
- 编码保存前执行 `trim + upper` 规范化；允许 `A-Z`、`0-9`、`-` 和 `_`，长度为 2 至 64 个字符。
- 点击“自动生成”后调用服务端分配命令并回填输入框。
- 服务端使用租户级计数器和行锁原子分配编号。
- 分配接口要求 `Idempotency-Key`，相同请求重试返回同一编号。
- 保存前允许用户把生成值改成手工编码；创建时重新校验唯一性。
- 已分配但未使用的编号不回收，允许断号。
- 创建成功后编码不可修改，也不复用已停用或已删除记录的编码。

建议增加：

```text
tenant_supplier_code_counters
- tenant_id primary key
- next_value bigint
- version integer
- updated_at timestamptz

tenant_supplier_code_registry
- id uuid primary key
- tenant_id
- normalized_code
- display_code
- source: generated | manual | migration
- status: reserved | used | abandoned
- idempotency_key
- tenant_supplier_id nullable
- created_at
- consumed_at nullable
- unique (tenant_id, normalized_code)
- unique (tenant_id, idempotency_key)
```

受控 RPC `allocate_tenant_supplier_code` 在事务内锁定当前租户计数器，检查编码登记表并跳过已被手工录入或预占的编号，然后写入 `reserved` 登记并返回 `allocation_id + code`。相同分配幂等键从登记表返回原结果。

编码分配和供应商创建是两个独立命令，必须使用两个不同的 `Idempotency-Key`。使用自动编码创建时，请求必须提交 `allocation_id`，创建命令在同一事务内校验预占记录属于当前租户、状态为 `reserved` 且编码一致，再改为 `used` 并绑定 `tenant_supplier_id`。手工编码不提交 `allocation_id`，由创建命令直接登记为 `used`。用户生成后又改成手工编码时，原预占记录不被消费，继续保留并最终标记为 `abandoned`。取消创建时预占记录同样可由定时任务改成 `abandoned`；`reserved` 和 `abandoned` 都不允许复用。

计数器首次创建时，从当前租户已登记的 `SUP-` 六位数字编码最大后缀加一开始；若未找到则从 `1` 开始。生成范围固定为 `SUP-000001` 至 `SUP-999999`，余量进入监控，耗尽前通过前向 migration 扩展位数。前导零只属于自动生成格式，手工编码按规范化后的完整字符串判重。

平台供应商保留平台主档编码；租户合作关系同时保存租户内部编码。采购申请和采购单使用固定的非空快照字段：

- `supplier_master_code_snapshot`：平台供应商的平台编码，或租户私有供应商的主档编码。
- `tenant_internal_supplier_code_snapshot`：当前合作关系内部编码。
- `supplier_ownership_scope_snapshot`：`platform | tenant`。

租户私有供应商的两个编码快照值相同，但字段仍同时写入，避免下游按供应商类型维护两套结构。

### 5.5 商品和 SKU

`supplier_products` 和 `supplier_skus` 增加不可变所有权字段。

有效组合：

| 供应商所有权 | 商品所有权 | 是否允许 |
|---|---|---|
| platform | platform | 允许，平台共享商品 |
| platform | tenant | 允许，租户补充商品 |
| tenant | 同一 tenant | 允许，租户私有供应商商品 |
| tenant | platform | 禁止 |
| tenant A | tenant B | 禁止 |

平台商品：

- 只能属于平台供应商。
- 租户只读。
- 由平台权限入口维护，未来供应商门户可以在独立认证上下文中维护。

租户商品：

- 可以属于平台供应商或本租户私有供应商。
- 只对创建租户可见。
- 由租户维护，不再标记为替共享供应商代录。
- 保留创建人、更新人和审计事件，但不强制填写 `proxy_reason`。

编码唯一规则：

- 平台商品：`supplier_id + product_code` 唯一。
- 租户商品：`supplier_id + owner_tenant_id + product_code` 唯一。
- 平台 SKU：`supplier_id + sku_code` 唯一。
- 租户 SKU：`supplier_id + owner_tenant_id + sku_code` 唯一；SKU 编码在同一供应商和租户作用域内唯一，不只在单个 SPU 内唯一。

SKU 继续表达可采购规格、型号、采购单位、批次、颜色和序列号管理方式。

### 5.6 分类

`catalog_categories` 使用统一主表和永久所有权字段。

平台分类：

- 构成装修行业标准分类树。
- 全租户共享。
- 由平台维护编码、名称、完整路径、层级、排序和是否允许挂商品。
- 商品只能绑定允许挂商品的末级分类。

租户分类：

- 永久属于当前租户。
- 只能挂在本租户分类树下。
- 可设置 `mapped_platform_category_id` 指向一个平台标准分类。
- 映射只用于统计、搜索和标准化，不改变名称、路径或所有权。
- 租户可以按乐观版本更新或移除映射；“只读映射”表示租户不能修改被映射的平台分类，不表示映射关系永久不可修改。
- 平台分类不能挂在租户分类下，租户分类也不能直接进入平台分类树。

完整分类名由系统根据树路径生成并保存或稳定计算，例如：

```text
主材 / 瓷砖 / 地砖
水电 / 电线电缆 / 家装电线
```

### 5.7 品牌

品牌采用与分类一致的双层所有权：

- 平台品牌全租户共享。
- 租户可以创建永久私有品牌。
- 租户品牌可通过 `mapped_platform_brand_id` 映射平台品牌。
- 映射不改变租户品牌所有权。
- 租户可以按乐观版本更新或移除映射，但不能通过映射入口修改平台品牌。
- 无品牌商品统一使用平台“无品牌”记录，不使用空字符串或任意文本。

平台商品只能引用平台品牌；租户商品可以引用平台品牌或本租户私有品牌。

### 5.8 分类规格模板

末级分类通过规格模板定义结构化字段。建议新增：

```text
catalog_spec_definitions
- id
- category_id
- code
- name
- value_type
- required
- enum_options
- unit_dimension
- participates_in_sku_name
- filterable
- sort_order
- ownership_scope
- owner_tenant_id
- status
- version
```

支持的数据类型至少包括：

- 文本
- 数值
- 布尔
- 单选枚举
- 多选枚举
- 日期

平台分类使用平台规格模板。租户创建私有分类时可以复制平台模板，再增加本租户私有规格；不能直接修改平台规格定义。

SKU 使用结构化 `spec_values` 保存具体值，service 必须按分类当前有效模板校验必填项、类型、枚举值和计量维度。规格值独立于展示名称，禁止只依赖 SKU 名称反向解析。

系统可以按参与命名的规格生成建议名称，例如：

```text
东鹏 地砖 800×800×10mm 柔光 灰色
```

用户可以修改展示名称，但结构化规格值仍是筛选、采购和快照的事实来源。

### 5.9 单位与换算

单位保持平台统一字典，不开放租户自由创建。平台按计量维度维护：

- 数量：个、只、套、片、块、箱、卷。
- 长度：毫米、厘米、米。
- 面积：平方米。
- 体积：立方米、升。
- 重量：克、千克、吨。

缺失单位通过平台建议流程补充。商品 SKU 可以保存商品特定换算：

```text
采购单位：箱
库存基础单位：片
1 箱 = 8 片
1 片 = 0.18 平方米
```

换算必须形成可解释的计量链路，禁止跨无关维度换算。提交冻结后的采购单保存单位和换算快照。

### 5.10 采购价

`supplier_price_lists`、价格版本和价格条目始终属于具体租户，并显式保存 `tenant_id`。本阶段不存在跨租户共享采购价：

- 平台共享商品只共享商品资料，不共享租户成交价、折扣、税率或合同价。
- 各租户为自己的合作关系维护独立采购价格。
- 租户私有商品和平台共享商品使用同一租户价格契约。
- 价格写入必须同时校验 `tenant_id`、`tenant_supplier_id`、`supplier_id` 和商品/SKU 对当前租户可见。
- 价格发布版本不可变；新价格通过新版本生效，历史采购继续引用原版本和快照。

## 6. 权限与可见范围

### 6.1 平台权限

- `platform.supplier.view`：查看平台共享供应商。
- `platform.supplier.manage`：创建和维护平台共享供应商。
- `platform.catalog.manage`：维护平台分类、品牌、规格和单位。
- `platform.supplier-product.manage`：维护平台共享商品与 SKU。

普通平台运营人员默认不能查看租户私有供应商、商品、分类、品牌、合同、价格和采购单。

平台超级管理员仅可通过专门的租户数据审计入口临时只读访问私有数据，并必须记录租户、原因、操作者、时间和查询范围。不能借此入口直接修改租户私有资料。

### 6.2 租户权限

- `supplier.view`：查看本租户合作供应商。
- `supplier.manage`：建立、激活、暂停合作关系，维护合作条件和合同。
- `supplier.master.manage`：创建和维护租户私有供应商主档。
- `supplier.product.view`：查看本租户可用商品和 SKU。
- `supplier.product.manage`：维护本租户私有商品和 SKU。
- `supplier.catalog.manage`：维护本租户私有分类、品牌和规格模板。
- `supplier.cost-price.view` / `supplier.cost-price.manage`：查看或维护本租户采购价。
- `supplier.purchase-order.view` / `supplier.purchase-order.manage`：查看或生成采购单。

租户 `system_admin` 默认获得上述权限，其他角色通过现有角色权限体系显式配置。`supplier.manage` 不隐式获得商品、分类、价格或采购单管理权限。

### 6.3 可见范围矩阵

| 数据 | 平台运营 | 所属租户 | 其他租户 |
|---|---|---|---|
| 平台共享供应商 | 可见 | 可见 | 可见 |
| 租户私有供应商 | 默认不可见 | 可见 | 不可见 |
| 平台共享商品 | 可见 | 建立合作后可用 | 建立合作后可用 |
| 租户补充商品 | 默认不可见 | 可见 | 不可见 |
| 平台分类、品牌、单位 | 可见 | 可见 | 可见 |
| 租户分类和品牌 | 默认不可见 | 可见 | 不可见 |
| 合同、价格和采购单 | 默认不可见 | 可见 | 不可见 |

共享供应商目录可以在建立合作前浏览；商品和价格进入采购选择前必须存在当前租户合作关系。

### 6.4 分层强制

- controller 只读取认证上下文、校验参数、调用 service 并包装响应。
- service 校验模块开关、权限、所有权、合作关系和生命周期。
- repository 只能使用 service 解析出的租户和供应商范围。
- 客户端不能提交 `owner_tenant_id` 或任意租户 ID 改变查询范围。
- 租户查询固定为 `ownership_scope = platform OR owner_tenant_id = 当前租户`。
- 租户写入固定为 `ownership_scope = tenant AND owner_tenant_id = 当前租户`。
- 平台共享数据必须通过平台 controller 写入，租户 controller 永远不能写共享数据。
- 跨租户访问返回无权限或资源不存在，不泄露目标是否存在。
- 错误统一经过 `error-factory.ts` 包装。
- 商品、SKU、分类和品牌的跨表所有权组合由受控 RPC 和数据库校验触发器强制，不能只依赖普通 `CHECK`。相关表只向 `service_role` 开放必要权限，`anon` 和 `authenticated` 无表直写权限。

平台共享商品不能脱离供应商关系直接进入租户商品列表。读取商品要求供应商模块已启用且当前租户与目标供应商存在合作关系；`evaluating`、`suspended`、`terminated` 或 `blacklisted` 关系仍可只读追溯历史商品，只有 `active` 关系允许新增、修改、定价和创建新采购。

## 7. 业务流程

### 7.1 创建租户私有供应商

租户填写供应商身份、联系人、地址、合作负责人、账期、授信、合同和附件。内部编码可以手工输入或点击自动生成。

后端通过一个幂等原子命令创建：

```text
租户私有供应商主档
        -> 当前租户合作关系
        -> 联系人和地址
        -> 初始合作资料
        -> 审计事件
```

合作关系默认进入 `evaluating`。租户确认资料后显式激活；只有 `active` 关系可以维护商品和价格、提交采购申请或创建采购单。

私有供应商不经过平台审核，也不进入平台目录。

### 7.2 添加平台共享供应商

租户从平台共享目录选择供应商，只创建本租户合作关系，不复制平台主档。

租户可以维护自己的内部编码、负责人、合同、账期、授信、采购价、合作状态和备注。平台企业身份、公共联系人和平台商品保持只读。

### 7.3 维护商品

选择有效合作供应商后：

- 平台共享商品只读，可配置本租户采购价。
- 租户可以在平台供应商下创建本租户私有补充商品。
- 租户私有供应商的商品全部由所属租户维护。
- 新增商品必须选择可用分类和品牌。
- 新增 SKU 必须通过规格模板校验，并选择采购单位及换算关系。

平台共享商品与租户私有商品在界面中显示明确来源标签，不能通过同一编辑入口混淆。

### 7.4 项目采购

采购链路固定为：

```text
当前租户项目
  -> active 合作供应商
  -> 当前租户可见商品与 SKU
  -> 当前租户有效采购价
  -> 数量、交付地址和税务信息
  -> 采购申请
  -> 采购单
```

所有列表分页，默认 `page=1&pageSize=20`，`pageSize` 最大为 `100`。

采购申请草稿和采购单草稿可以随主数据重新选择或刷新；采购申请提交时冻结申请行快照，采购单提交时冻结订单行及供应商快照。冻结后的快照只能由显式变更单形成新版本，不能原地修改。

采购单提交时至少保存：

- 供应商 ID、`supplier_ownership_scope_snapshot`、`supplier_master_code_snapshot` 和 `tenant_internal_supplier_code_snapshot`。
- 供应商名称、法定名称和身份信息快照。
- 商品和 SKU ID、编码、名称、分类完整名称和品牌快照。
- 结构化规格及可读规格文本快照。
- 采购单位、基础单位和换算关系快照。
- 单价、税率、币种、含税规则和价格来源快照。
- 联系人和交付地址快照。
- 合同 ID、合同版本、合同编号、有效期、账期和发票门禁快照。

主数据后续修改不回写历史采购单。

### 7.5 停用与删除

- 已被采购申请、采购单、价格、履约、应付或付款引用的数据不能物理删除，只能停用。
- 未发生业务引用的租户私有草稿可以删除，但内部编码不回收。
- 停用平台供应商阻止所有租户创建新采购，不阻断历史收货、退货、应付和付款收尾。
- 租户停用合作关系只影响当前租户。
- 停用租户私有供应商不会影响任何其他租户。
- 停用分类、品牌或单位前必须检查启用商品和历史引用。

## 8. API 与命令边界

具体路径在实施计划中按现有 controller 命名复核，逻辑契约固定如下：

### 8.1 租户供应商

- 分页查询共享目录。
- 分页查询本租户合作供应商。
- 创建租户私有供应商并原子建立合作关系。
- 为平台共享供应商建立合作关系。
- 分配租户内部供应商编码。
- 更新租户私有供应商主档。
- 更新合作条件、合同和合作状态。

创建、编码分配和生命周期命令必须携带 `Idempotency-Key`。编码分配键与创建键互相独立；自动编码创建通过 `allocation_id` 消费预占记录，不复用分配幂等键。

新建合作关系必须提供已登记的自动编码或手工编码；服务端不能因为字段为空而静默生成，自动生成必须由用户点击触发。现有合作关系在功能切换 migration 中统一补齐，不允许上线后长期为空。

### 8.2 商品与目录

- 商品查询合并平台共享商品和当前租户私有商品。
- 租户商品写接口只接受租户私有目标。
- 平台商品使用独立平台 controller。
- 分类和品牌查询合并平台共享数据和当前租户私有数据。
- 私有分类和品牌写接口只允许当前租户。
- 规格保存时由 service 加载分类模板并校验结构化值。
- 商品只读接口同样要求当前租户与供应商存在合作关系；暂停或终止关系保留历史只读能力，写接口拒绝。

### 8.3 稳定错误码

至少定义：

- `SUPPLIER_OWNERSHIP_CONFLICT`
- `SUPPLIER_CODE_CONFLICT`
- `SUPPLIER_CODE_ALLOCATION_CONFLICT`
- `TENANT_SUPPLIER_NOT_FOUND`
- `TENANT_SUPPLIER_STATE_CONFLICT`
- `SHARED_RESOURCE_READ_ONLY`
- `PRIVATE_RESOURCE_FORBIDDEN`
- `PRODUCT_OWNERSHIP_CONFLICT`
- `CATEGORY_OWNERSHIP_CONFLICT`
- `BRAND_OWNERSHIP_CONFLICT`
- `SPEC_TEMPLATE_VALIDATION_ERROR`
- `UNIT_CONVERSION_INVALID`
- `SUPPLIER_MODULE_DISABLED`
- `SUPPLIER_ORDER_NOT_ELIGIBLE`

repository 将数据库错误转换为稳定错误码，service 通过 error factory 转成中文业务响应。

## 9. 查询与性能边界

- 供应商、商品、SKU、分类、品牌、价格和采购列表全部分页。
- repository 只选择页面需要的字段，详情按需加载联系人、地址、合同和规格。
- 禁止供应商列表逐行查询合同、价格或商品数量。
- 共享与私有合并查询必须由数据库一次完成，不能在应用层分别拉取全量后合并。
- 关键词搜索限定编码、名称、法定名称和必要的规格检索字段。
- 大表过滤和排序索引至少覆盖所有权、租户、供应商、状态、更新时间和 ID。
- 商品编码、SKU 编码、分类编码、品牌编码和租户内部供应商编码使用作用域局部唯一索引。
- 迁移实施时对核心分页和采购商品选择执行 `EXPLAIN ANALYZE`。

## 10. 数据迁移

### 10.1 供应商

现有 `suppliers` 均来自平台流程，回填为：

```text
ownership_scope = platform
owner_tenant_id = null
```

现有 `tenant_suppliers` 业务关系保持不变，但必须在功能切换 migration 中补齐内部编码，不能长期为空。按每个租户的关系 `created_at, id` 稳定排序，从 `SUP-000001` 开始批量分配，写入编码登记表并初始化计数器。平台供应商原编码继续保存在 `suppliers.code`，不会被内部编码覆盖。批量结果、冲突和计数器起点全部由 migration 生成并纳入审计，禁止手工远程更新。

### 10.2 商品与 SKU

现有商品由租户代录，不自动转成平台共享商品。

先为每个商品计算两类证据：

- 创建证据：最早的 `create_supplier_product` 命令事件及其 `tenant_id`。
- 使用证据：价格簿、采购申请和采购单父记录中的所有 `tenant_id` 集合。

归属和复制规则：

1. 创建事件唯一确定租户 A 时，原商品和 SKU 归租户 A；无论使用证据是否包含 A，都为每个使用租户中不等于 A 的租户创建私有副本。因此“创建 A、唯一使用 B”按原件归 A、克隆给 B 处理，不视为所有权转移。
2. 创建事件缺失但使用证据只有一个租户时，可以归该唯一使用租户。
3. `created_by_employee_id` 的员工租户只能作为佐证；只有它与创建或唯一使用证据一致时才采用，不能单独决定所有权，避免员工历史调动造成误判。
4. 创建事件缺失且存在多个使用租户时，禁止自动选择原件所有者。该商品进入异常表，由人工基于原始单据和操作记录确认一个原始租户；确认后原件归该租户，并为其他使用租户克隆。
5. 创建事件存在多个不同租户、事件租户不存在，或证据无法验证时，同样进入异常表，禁止自动迁移。
6. migration 按父记录 `tenant_id` 把各租户的价格条目、采购申请行和采购单行引用改指向对应租户副本；业务快照字段保持原值不变。
7. 原始 ID、目标租户和克隆 ID 写入永久迁移映射表，历史命令事件保持 append-only，不改写事件资源 ID；审计查询通过映射表解释旧 ID 与新 ID 的关系。
8. SKU、价格簿和价格条目必须与对应商品及租户链路一致。
9. 父子链路不一致或引用无法唯一映射时，写入迁移异常表并阻止正式切换。

不能使用当前 `acting_tenant_id` 直接认定原始所有者，因为更新操作可能覆盖最后操作租户。

建议保留两张审计表：

```text
supplier_product_ownership_migration_map
- old_product_id
- old_sku_id nullable
- tenant_id
- new_product_id
- new_sku_id nullable
- evidence
- created_at

supplier_ownership_migration_issues
- id
- resource_type
- resource_id
- issue_type
- evidence
- status: open | resolved
- resolution
- resolved_by_employee_id nullable
- resolved_at nullable
- created_at
```

正式切换门禁是 `open` 异常数为零，且每个被价格、采购申请或采购单引用的商品/SKU都能按父记录租户唯一解析。处理人必须在异常表记录证据和结论，再通过补充 migration 应用修正。

### 10.3 历史采购数据

- 已提交采购申请和采购单保留原快照，不从迁移后的主数据重新生成业务事实。
- 对其他租户的商品克隆只调整外键引用，快照内容和金额不变，并在迁移映射表保留追踪关系。
- 草稿采购申请和采购单在引用重写后重新执行当前所有权、合作关系和价格有效性校验；不满足条件的草稿进入异常表，不能提交。
- 收货、退货、履约、应付和付款继续从已提交采购单及其快照读取，不因供应商或商品当前不可见而中断收尾。
- 历史关键快照完整清单包括：供应商主档编码和内部编码、供应商名称和法定名称、商品/SKU 编码和名称、分类完整名称、品牌、结构化及可读规格、采购单位、基础单位、换算关系、数量、单价、金额、税率、币种、含税规则、合同 ID/版本/编号/有效期/账期/发票门禁、联系人和交付地址。
- 上述关键字段缺失时，不允许从当前主档补写并冒充历史事实；能够从同时期不可变单据或事件证明的，通过 migration 写入并记录证据，否则进入异常表。
- 商品说明、图片、营销文案和界面辅助标签属于非关键展示信息，不补写历史快照；历史页面统一显示“历史数据未记录”。

### 10.4 分类、品牌和单位

现有标准分类、品牌和单位回填为平台共享数据。现有商品引用保持不变。租户私有分类和品牌从新入口上线后产生。

### 10.5 分阶段 migration

1. 添加所有权字段、计数器和必要枚举，先允许兼容状态。
2. 执行确定性回填、按使用租户克隆商品并生成迁移映射和异常报告。
3. 异常数归零后增加非空约束、所有权检查和局部唯一索引。
4. 增加受控 RPC、RLS、授权和不可变所有权触发器。
5. 切换后端读取与写入路径。
6. 灰度启用 Admin 和采购入口。

所有数据库变更必须位于 `supabase/migrations/`。应用前确认待执行 migration，应用后使用 `supabase migration list` 验证 Local/Remote 对齐。

## 11. 灰度与回滚

### 11.1 灰度

按租户功能开关分四阶段上线：

1. 数据库基础和只读兼容。
2. 后端所有权、权限和查询边界。
3. Admin 私有供应商、编码、分类、品牌和商品入口。
4. 采购申请与采购单统一选择和快照。

每个阶段先在测试租户执行两租户隔离 smoke，再扩大范围。

### 11.2 回滚

- 新写入启用前可以关闭功能开关并回退到原读取路径。
- 新写入开始后，可以关闭私有供应商功能并停止新增，但不删除所有权字段和业务数据。
- 所有权和采购快照一旦被业务引用，只允许通过前向 migration 修复。
- 破坏性回滚前必须停止新写入、导出新增数据并核对采购、履约、应付和付款引用。

## 12. 测试与验收

### 12.1 领域和 schema

- 所有权稳定值和权限码契约。
- 平台/租户所有权字段组合校验。
- 编码格式、唯一性和不可修改规则。
- 分类树、映射和规格模板校验。
- 单位计量维度和换算链路校验。
- 分页默认值和 `pageSize <= 100`。

### 12.2 service 和 repository

- 租户 ID 仅来自认证上下文。
- 平台共享读取和租户私有读取正确合并。
- 租户写入永远不能命中平台数据或其他租户数据。
- 私有供应商只能由所属租户建立合作关系。
- 平台商品只读，租户补充商品只对所属租户可见。
- 商品、SKU、价格和采购链路所有权一致。
- 所有列表使用 `.range()`、`.limit()` 或数据库分页 RPC。
- 无 N+1 查询。

### 12.3 数据库

- 所有权检查约束和不可变触发器。
- 平台及租户局部唯一索引。
- 编码并发分配和幂等重放。
- 手工编码占用自动生成候选值时，生成命令跳号且不会覆盖登记。
- 新关系内部编码非空，租户私有供应商主档编码与合作内部编码一致。
- 跨租户直接访问和受控 RPC 拒绝。
- 商品迁移归属推导、多租户使用克隆、引用重写、映射留痕和异常阻断。
- 已提交采购快照在迁移前后保持一致，草稿重新通过当前门禁。
- 核心列表与采购商品选择执行计划。

### 12.4 Admin 和 E2E

- 租户 A、B 都能看到平台共享供应商。
- A 创建的私有供应商，B 和普通平台运营人员不可见。
- A、B 可以拥有相同内部供应商编码。
- 并发点击自动生成不会得到重复编码；重试同一幂等键返回同一编码。
- 用户手工占用未来自动编号时，自动生成安全跳过该编号。
- A 可以给平台供应商创建私有商品，B 看不到。
- A 不能修改平台共享商品。
- A 不能给 B 的私有供应商创建商品。
- 租户私有分类、品牌和规格不会出现在其他租户。
- 平台分类映射不改变私有分类名称和所有权。
- 采购单只能引用当前租户可见且合作有效的数据。
- 主数据修改后历史采购单快照不变。
- 暂停或终止合作后历史商品仍可查看，但不能编辑、定价或创建新采购。
- 已被业务引用的数据不能物理删除。
- 停用平台供应商阻止新采购，不阻断历史收货和付款。

## 13. 审计与可观测性

所有创建、更新、停用、编码分配和合作状态命令记录：

- 资源类型和 ID
- 所有权作用域和所属租户
- 操作者用户和员工
- 命令、原因和幂等键
- 前后版本
- 操作时间和来源

平台超级管理员的租户私有数据审计访问另记只读访问日志。日志不得记录合同正文、联系方式全文、价格明细或其他不必要敏感数据。

应监控：

- 跨租户拒绝次数
- 所有权冲突次数
- 编码分配冲突和计数器余量
- 商品迁移异常数量
- 私有供应商创建量
- 采购商品选择接口延迟和分页扫描量

## 14. 已确认决策

1. 平台供应商全租户共享，租户供应商永久私有。
2. 租户私有供应商不能升级、转换或合并为平台供应商。
3. 平台商品共享只读，租户补充商品永久私有。
4. 租户可以在平台供应商或本租户私有供应商下创建私有商品。
5. 平台分类共享，租户分类永久私有，只允许映射。
6. 品牌采用与分类一致的共享/私有双层模型。
7. 单位由平台统一维护，SKU 保存商品特定换算。
8. 采用统一主表和不可变所有权字段，不拆成两套采购外键。
9. 租户内部供应商编码支持手工输入和一键原子生成。
10. 采购单保存供应商、商品、规格、单位、价格和税务快照。
11. 已被业务引用的数据只能停用，不能物理删除。
12. 现有租户代录商品迁移为创建租户私有商品，不自动变成平台共享商品。

## 15. 对既有设计的影响

本设计保留既有供应商平台的以下能力：

- 平台供应商统一准入和风险治理。
- 租户独立合作关系、合同、价格和采购闭环。
- 标准分类、品牌和单位。
- 商品、价格和采购命令的幂等、版本和审计机制。

本设计明确替换以下旧语义：

- 租户不再只能从平台目录选择供应商。
- 租户维护的商品不再天然成为供应商级跨租户共享商品。
- 租户合法维护私有商品不再强制使用 `tenant_proxy` 和代录原因。
- 分类和品牌不再只有平台单层数据。

后续实施计划必须按“migration -> domain/schema -> repository/service -> controller -> Admin -> 采购闭环 -> 两租户 E2E”的顺序拆分，小步验证，不在同一变更中顺手重构无关供应商模块。
