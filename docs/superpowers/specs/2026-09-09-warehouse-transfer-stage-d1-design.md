# 阶段 D1：仓库调拨设计

日期：2026-09-09

依据：已确认的 [仓库采购与库存闭环设计](2026-09-05-warehouse-procurement-inventory-mvp-design.md)。用户授权阶段 C 测试通过后直接进入 D，并委托处理本任务内的确认；不扩大到生产发布、真实付款、修改 Orange 或授予无关权限。

## 1. 阶段拆分与当前交付边界

- D1：同租户仓库调拨。
- D2：盘点及手工调整，分别保留来源单据、差异原因和确认权限，不直接覆盖余额。
- D3：库位、批号、安全库存、自动补货和 BOM 库存联动，按独立子项目交付。

D1 分为请求契约、数据库原子命令、API、Admin、开发验收五个可验证批次。本次首先实现请求契约，不注册路由、不创建表、不开放开关，也不把领域类型完成等同于调拨功能上线。

2026-09-09 进度更新：契约、数据库原子命令、核心 API、库存调拨来源和原子开关配置已完成并发布 DEV（604 migrations，run `34294327062`）。这更新了上述首批边界，不代表 D1 全量完成。下一批为 Admin 调拨管理、来源跳转和开关 UI，之后在固始晴天装饰工程有限公司用有权限员工验收；此前保持调拨开关 false。详见 [来源/配置发布证据](../../operations/evidence/2026-09-09-warehouse-transfer-integration-dev-release.md)。

## 2. 方案选择

采用“确认时双仓同时过账”：源仓扣减与目标仓增加在同一数据库事务内完成，适合当前公司仓库管理范围，与既有领退料命令模式一致。

备选“发出／在途／签收”可以覆盖跨地区运输，但需要独立在途库存、部分签收和损耗处理，留作后续独立需求；不在 D1 混入部分签收。备选统一通用库存单据引擎会引入新架构，本次沿用仓库领域现有模式，不实施通用引擎。

## 3. 业务规则

1. 一张调拨单绑定同租户的一个源仓、一个目标仓，两仓必须不同；均须启用。
2. 一张单 1–100 个不同 SKU，数量必须为正十进制字符串，最多 14 位整数、4 位小数。UUID 大小写不同仍视为同一仓库或 SKU。
3. 原因必须填写，去除首尾空白后 1–500 字符。数量、仓库、SKU 和原因由用户填写；单号、租户、操作人、状态、库存成本及金额由服务端产生。
4. 状态为 `draft → submitted → completed`；草稿及待调拨可以取消。草稿可保存、提交、取消；待调拨只可完成、取消；已完成和已取消不能再修改。
5. 提交不预占库存，完成时重新校验库存和当前移动平均成本。前端不能提交 `unit_cost`、`amount`、成本分类或项目 ID。
6. 确认后错误通过新的反向调拨纠正，不删除原调拨、原流水或审计回执。

## 4. 会计与并发不变量

- 源仓以完成时移动平均成本计算出库金额；清空该 SKU 时取剩余库存价值，避免残留分币。
- 目标仓收到完全相同的数量和金额，随后重新计算自身移动平均成本；不采用目标仓原成本作为入库金额。
- 每项形成一条 `transfer_out` 与一条 `transfer_in`，以相同调拨明细关联；两条数量之和、价值之和均为 0。沿用现有 `(tenant_id, source_type, source_id)` 唯一键：分别使用 `warehouse_transfer_out_item`、`warehouse_transfer_in_item` 来源类型，`source_id` 均为该调拨明细 ID，不放宽采购／领退料的既有来源去重约束。
- 不写 `project_cost_events`、`supplier_payable_events`、付款或现金事实。
- 余额、两条流水、完成状态和成功回执必须原子提交。任何异常整体回滚。
- 延续 C 的锁顺序：租户设置、按 UUID 排序的仓库、单据、按仓库与 SKU 排序的余额。不存在的目标余额也必须在仓库锁内建立，避免反向调拨死锁及重复投影。
- 版本冲突、库存不足、跨租户、已完成修改、重复 key 不同内容均由数据库最终拒绝；API 预检不能替代最终门禁。
- 幂等 key 继续使用既有请求头约定；同一身份、相同 key 和相同请求重放返回原回执，不重复过账。开关关闭不影响已成功命令重放和有权限的历史读取。

## 5. 分层与后续数据库范围

Domain 维护状态、标签、动作和草稿／命令 DTO。API Zod schema 采用严格对象，复用 `PaginationQuerySchema`；controller 处理 HTTP，service 派生身份和权限上下文，repository 调用数据库命令，错误经过 `error-factory.ts`。

数据库批次使用 `supabase migration new` 建立独立 migration：

- `warehouse_transfer_orders`：租户、源仓、目标仓、单号、状态、版本、原因、创建／更新／提交／完成／取消审计字段。
- `warehouse_transfer_order_items`：租户、单据、行号、SKU、数量、完成时冻结的源仓单位成本和金额；同单 SKU 唯一。
- `warehouse_transfer_command_events`：单据、命令、身份、幂等 key、请求指纹和不可变回执。
- 扩展库存流水类型与调拨明细外键，确保每个明细每个方向唯一，保持既有来源兼容。
- 新增租户级 `warehouse_transfers_enabled`，默认关闭；独立于领退料开关，不自动打开任何租户。
- 新增 `inventory.transfer.manage` 与 `inventory.transfer.approve` 权限定义；不自动给员工或角色授权。历史及成本读取仍要求 `inventory.stock.view`，仓库调拨不要求项目权限。
- 所有新增表强制 RLS、同租户复合外键及受控 RPC 权限；普通客户端不能直接写库存事实。

数据库批次的具体 SQL、索引和验证计划须在修改前继续细化；本请求契约批次不预先应用部分数据库结构。

## 6. API 请求契约

预定路由（本批次不注册）：

```text
GET  /warehouse-transfers
GET  /warehouse-transfers/:id
GET  /warehouse-transfers/:id/items
POST /warehouse-transfers/:id/save-draft
POST /warehouse-transfers/:id/submit
POST /warehouse-transfers/:id/complete
POST /warehouse-transfers/:id/cancel
```

保存草稿 body：

```json
{
  "expected_version": 0,
  "source_warehouse_id": "10000000-0000-4000-8000-000000000001",
  "destination_warehouse_id": "10000000-0000-4000-8000-000000000002",
  "reason": "公司仓库向分仓调拨",
  "items": [
    { "supplier_sku_id": "10000000-0000-4000-8000-000000000003", "quantity": "0.3333" }
  ]
}
```

新建草稿版本 0，更新草稿版本为正整数；统一最大 `2147483647`。提交、完成、取消只接收 `{ "expected_version": 1 }` 形状，必须是正整数且不能夹带成本或身份字段。

列表过滤：`sourceWarehouseId`、`destinationWarehouseId`、`status`、`keyword`。关键词去首尾空白且最多 100 字符。列表与明细默认 `page=1&pageSize=20`，`pageSize≤100`。拒绝未知参数，不接受客户端指定租户、操作人或项目。

状态常量、标签和动作只用于契约与展示，不构成授权判断；实际接口必须校验身份、权限、租户开关和数据库状态。

## 7. 验收门禁

请求契约批次：

- 状态、中文标签、合法动作和终态不可编辑。
- 同仓及大小写变体同仓拒绝；大小写变体重复 SKU 拒绝。
- 1 与 100 行通过；0 与 101 行拒绝。
- 数量最小／最大合法值原样保留；0、负数、数字 JSON、小数超精度、指数和超范围值拒绝。
- 必填原因、版本边界、分页边界和未知字段拒绝。
- 共享 Domain 构建、API 类型检查、现有领退料契约回归通过。

后续完整 D1 验收：空目标余额、多 SKU、不同仓均价、源仓清空尾差、重复命令、双向并发调拨、与领退料／收货并发、注入失败回滚、跨租户／无权限、关闭开关、历史来源链接、分页查询计划及桌面／移动页面。实际开发租户仍为固始晴天装饰工程有限公司，只使用有权限员工和明确标记的测试库存。

应用 migration 前确认完整差集和目标，应用后 `supabase migration list` 验证对齐。异常以前向修复或反向业务事实处理；不删除历史，不发布生产。
