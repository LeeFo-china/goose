# 平台技术服务套装限时活动设计

## 1. 目标

为平台技术服务正式套餐增加一场由超管管理的限时折扣活动，同时覆盖：

- `platform_service_1y`：1 年套餐；
- `platform_service_2y`：2 年套餐；
- `platform_service_3y`：3 年套餐。

活动默认按套餐已发布标价的 2 折计算，超管可以修改运营文案、折扣率、开始时间和结束时间。活动必须保存为草稿并由超管明确发布后才会影响新订单；migration 和代码发布均不得自动启用折扣。

开发专用的 `platform_service_smoke_1fen` 商品不参加活动。

## 2. 范围

本阶段包含：

- 限时活动的数据表、不可变发布版本和数据库约束；
- 超管 Admin 的活动列表、编辑、价格预览、发布和提前停止操作；
- 租户侧商品列表的活动内容与实时有效价格；
- 创建订单时由服务端确定活动资格、金额并固化活动快照；
- API、Admin、数据库测试和小程序交接文档。

本阶段不包含：

- 优惠券、兑换码、用户分群、租户白名单或使用次数限制；
- 多个活动叠加、满减、阶梯价或单独配置某一档套餐；
- 活动图片、主题色、富文本装修器或广告位系统；
- 修改历史订单、延长待支付订单或活动结束后补差价；
- 自动创建并发布生产活动。

## 3. 核心业务规则

### 3.1 活动范围

每个活动发布版本固定覆盖三个正式套餐，不提供单套餐勾选。后端按三个稳定商品编码解析适用商品，并在发布时确认三个商品均存在、已发布且未归档。

这种约束避免开发 smoke 商品和未来其他技术服务商品被误纳入活动，也使运营页面能够一次预览三档价格。

### 3.2 折扣与金额

折扣使用基点表示，`10000` 为原价，默认 `2000` 为 2 折。第一期允许配置 `1` 至 `9999`，但活动发布前必须确认三档活动价均低于各自日常实付价。

```text
活动价（分） = max(1, round(已发布标价（分） × 折扣基点 / 10000))
```

金额计算只在服务端和数据库中进行。客户端不得提交活动价、标价、折扣率或活动 ID 作为订单定价依据。

以当前初始化标价和默认 2 折计算：

| 套餐 | 标价 | 活动价 |
| --- | ---: | ---: |
| 1 年 | ¥9,800 | ¥1,960 |
| 2 年 | ¥19,600 | ¥3,920 |
| 3 年 | ¥29,400 | ¥5,880 |

价格预览使用当前已发布商品版本。若商品价格在活动发布前发生变化，活动发布确认必须展示新价格；若商品价格在活动已发布后发生变化，新订单使用新商品标价和活动版本折扣重新计算，订单仍同时记录商品版本与活动版本。发布商品新版本时也必须针对待开始或进行中的活动重新校验三档活动价，任何活动价不再低于日常价时拒绝发布商品。

### 3.3 时间语义

- 数据库存储 `timestamptz`，Admin 按 Asia/Shanghai 展示和输入；
- 活动有效区间为 `[starts_at, ends_at)`，开始时间包含，结束时间不包含；
- 商品列表与创建订单均以数据库时间判断，不信任客户端时间；
- 不使用定时任务切换状态，页面状态由发布时间和数据库时间计算；
- 同一时间最多存在一个覆盖正式套餐的已发布活动；数据库发布 RPC 阻止时间重叠。

活动展示阶段为：草稿、待开始、进行中、已结束、已停止、已归档。待开始、进行中和已结束均来自已发布版本与数据库时间推导。

### 3.4 待支付订单

订单创建成功后，活动金额锁定至该订单现有的 `payment_expires_at`：

- 活动到期或被提前停止，不修改已创建订单；
- 订单在自身支付有效期内可以继续支付锁定金额；
- 订单过期后重新下单，服务端重新判断当时有效价格；
- 相同幂等键重试返回原订单及原价格，不重复选择活动；
- 历史订单、退款和服务履约继续读取订单快照。

## 4. 活动内容

活动草稿包含以下字段：

| 字段 | 用途 | 约束 |
| --- | --- | --- |
| `name` | Admin 内部识别名称 | 必填，最多 80 字 |
| `badge_text` | 小程序价格旁角标 | 默认“限时 2 折”，最多 20 字 |
| `title` | 活动主标题 | 默认“平台技术服务限时优惠”，最多 60 字 |
| `summary` | 一句话活动说明 | 默认说明三档套餐同步优惠，最多 200 字 |
| `rules_text` | 面向购买方的活动规则 | 纯文本，最多 2000 字 |
| `discount_rate_basis_points` | 折扣率 | 默认 2000，发布时必须形成降价 |
| `starts_at` | 开始时间 | 草稿可为空，发布必填 |
| `ends_at` | 结束时间 | 草稿可为空，发布必填且晚于开始时间 |

按钮文字和跳转目标由小程序固定为现有购买流程，不开放任意链接、HTML、颜色或脚本配置。

## 5. 数据设计

数据库变更全部通过 `supabase/migrations/` 完成。

新增活动主表和活动版本表：

- 主表保存稳定活动 ID、编码、当前草稿指针、当前发布版本指针、乐观锁版本、停止/归档状态和操作人；
- 版本表保存文案、折扣率、活动时间、发布状态、创建人和发布时间；
- 已发布版本的业务字段不可修改；编辑已发布活动时创建新草稿版本，重新发布后旧版本转为 `superseded` 并保留；
- 提前停止只把当前发布版本转为 `stopped` 并记录停止时间、操作人和原因，不修改活动文案、价格和时间字段，不删除发布版本；
- 发布和停止通过 `SECURITY DEFINER` RPC 原子执行并仅授权 `service_role`；
- 对 `published` 状态的活动版本时间范围建立约束和索引，阻止重叠活动；`stopped` 与 `superseded` 版本不占用后续活动时间；
- Admin 列表按创建时间倒序分页，默认 20、最大 100。

不复用官网 `site_content` 表。该模型只支持文章、案例和城市内容，且不负责交易价格、活动时间约束或订单快照。

### 5.1 订单快照

现有 `tenant_service_orders.product_snapshot` 增加可选的 `promotion` 对象：

```json
{
  "promotion": {
    "id": "活动 ID",
    "version_id": "活动版本 ID",
    "version": 1,
    "name": "平台技术服务限时优惠",
    "badge_text": "限时 2 折",
    "discount_rate_basis_points": 2000,
    "starts_at": "ISO 8601",
    "ends_at": "ISO 8601",
    "base_amount_fen": 980000,
    "effective_amount_fen": 196000
  }
}
```

无活动时不写 `promotion`。现有 `tenant_service_orders.amount_fen` 始终保存最终应付金额，兼容支付、退款和财务链路。

## 6. 服务端设计

### 6.1 分层

- controller：读取请求、Zod 校验、取得平台权限或租户会话、调用 service、使用 `ResponseHandler.success`；
- service：编排活动草稿、发布、停止、商品展示和订单定价；
- repository/RPC：访问 Supabase、解析数据库时间、执行发布与订单原子操作；
- 所有错误使用 `error-factory.ts`，不直接抛出普通 `Error`。

### 6.2 超管接口

新增：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/platform/billing/service-promotions?page=1&pageSize=20` | 分页读取活动 |
| `POST` | `/platform/billing/service-promotions` | 创建默认 2 折草稿 |
| `PATCH` | `/platform/billing/service-promotions/:id` | 保存草稿，使用 `expected_version` |
| `POST` | `/platform/billing/service-promotions/:id/publish` | 原子发布，使用幂等键和乐观锁 |
| `POST` | `/platform/billing/service-promotions/:id/stop` | 提前停止，使用幂等键和乐观锁 |

继续使用 `platform.service_product.manage` 权限，并要求平台模式会话。能够修改套餐价格的操作员已经具备同等级的价格管理能力，第一期不新增重复权限。

### 6.3 租户商品接口

保留 `GET /billing/service-products?page=1&pageSize=20`，为每个正式套餐返回：

- `list_amount_fen`：标价；
- `base_amount_fen`：已发布商品的日常实付价；
- `amount_fen`：当前最终应付价，兼容现有小程序；
- `effective_amount_fen`：与 `amount_fen` 相同，用于新客户端明确表达；
- `base_price_rate_basis_points`：日常价格折扣；
- `price_rate_basis_points`：当前有效折扣；
- `promotion`：仅活动有效时返回活动内容、版本和时间；
- 顶层 `server_time`：小程序校准倒计时。

待开始和已结束的活动不返回给租户客户端。活动停止或结束后接口自动恢复已发布商品日常价。

### 6.4 创建订单

当前流程先读取商品再插入订单。活动上线后，最终价格解析与待支付订单创建必须进入同一数据库事务/RPC：

1. 按商品编码读取并锁定已发布商品版本；
2. 使用数据库时间读取当前有效活动版本；
3. 计算活动价并验证金额边界；
4. 构造包含商品和活动版本的快照；
5. 写入待支付订单和最终 `amount_fen`；
6. 返回订单后再按现有流程申请微信预支付。

若预支付申请失败，继续沿用现有订单恢复机制，不重新定价或创建第二张订单。

## 7. Admin 交互

在现有“技术服务套餐”页面增加同级页签：

- 套餐；
- 限时活动。

活动页沿用平台列表页结构，不使用卡片嵌套。列表列为：活动、折扣、活动时间、阶段、版本、更新时间、操作。

编辑使用现有 Dialog 或 Sheet 模式，字段按“运营内容、价格与时间”分组。创建表单默认填入 2 折及推荐文案，但开始、结束时间保持为空，不能直接发布。

发布确认展示：

- 活动版本和时间；
- 1 年、2 年、3 年套餐的标价、日常价和活动价；
- “只影响发布后创建的新订单，已有订单继续使用订单快照”；
- “发布后到开始时间自动生效，到结束时间自动恢复日常价”。

活动进行中重新发布新版本时，确认层明确提示新内容和价格将立即影响后续新订单。停止操作使用危险确认，要求填写简短原因。

## 8. 小程序对接

Orange 仓库仅作只读参考，由小程序团队实施：

- 继续以 `amount_fen` 展示和确认最终应付金额；
- 活动存在时展示角标、标题、说明、标价删除线、活动价和结束时间；
- 使用 `server_time` 计算剩余时间，前台每秒更新显示但不自行决定订单价格；
- 页面回到前台、倒计时结束、创建订单发生价格冲突时重新读取商品；
- 下单请求仍只提交 `product_code`、条款版本和幂等键，不提交活动金额；
- 订单创建成功后，以订单 `amount_fen` 作为支付确认金额；
- 不记录支付签名字段、用户 token 或完整支付响应。

后端变更保持旧客户端兼容：活动期间旧客户端读取的 `amount_fen` 也是最终活动价，只是不会展示新增运营文案和倒计时。正式发布活动前仍应完成新版小程序真机验收。

## 9. 错误和并发

新增稳定错误码：

- `SERVICE_PROMOTION_NOT_FOUND`：活动不存在；
- `SERVICE_PROMOTION_VERSION_CONFLICT`：草稿或状态已被他人更新；
- `SERVICE_PROMOTION_TIME_INVALID`：时间缺失、顺序错误或已无法发布；
- `SERVICE_PROMOTION_OVERLAP`：与另一已发布活动时间重叠；
- `SERVICE_PROMOTION_PRICE_NOT_LOWER`：至少一档活动价没有低于日常价；
- `SERVICE_PROMOTION_PRODUCT_UNAVAILABLE`：三个正式套餐中有未发布或已归档商品；
- `SERVICE_PROMOTION_INVALID_STATE`：当前状态不允许发布或停止。

发布、重新发布、停止和创建订单都使用数据库事务、行锁、乐观锁及幂等键。服务层不得依赖进程内锁或缓存判断活动是否有效。

## 10. 验证

### 10.1 数据库与 API

- migration 合同、表约束、RLS/授权、索引和发布 RPC 测试；
- 默认折扣为 2000，但 migration 不产生有效活动；
- 开始时间包含、结束时间不包含的边界测试；
- 三档套餐 2 折金额和分值取整测试；
- 重叠发布、无效时间、非降价和正式商品缺失测试；
- 活动前、活动中、活动后和提前停止时的商品列表测试；
- 订单创建跨活动边界的事务测试；
- 同幂等键重复创建返回同一订单、活动版本和金额；
- 活动结束后历史订单、继续支付、退款和履约仍使用原快照。

### 10.2 Admin

- 默认文案和默认 2 折表单测试；
- 时间、折扣和内容长度校验；
- 三档价格预览；
- 发布与停止确认；
- 版本冲突、加载失败和权限不足状态；
- `pnpm --dir apps/admin check`、相关测试和页面 smoke。

### 10.3 发布验收

- dev 应用 migration 后用 `supabase migration list` 核对 Local/Remote；
- 超管创建短时间测试活动，验证待开始、开始、结束和停止；
- 微信小程序开发版真机核对商品展示、倒计时、创建订单和实际支付金额；
- 验证活动期间创建的待支付订单在活动结束后仍可按锁定金额继续支付；
- 生产发布前由运营复核实际开始/结束时间、三档金额和活动规则；
- 回传只包含活动 ID、版本、状态、时间和脱敏订单号，不回传 token、支付签名或用户信息。

## 11. 发布与回滚

上线顺序：

1. 发布兼容性数据库 migration；
2. 发布 API 和 Admin；
3. 小程序团队完成字段对接和真机验收；
4. 超管创建并核对活动草稿；
5. 超管明确发布活动。

回滚时先通过 Admin 停止活动，使新订单立即恢复商品日常价，再回滚应用代码。数据库表和历史活动/订单快照保留，通过后续 migration 调整，不执行远端手工 DDL/DML。旧客户端始终可以继续使用 `amount_fen`。
