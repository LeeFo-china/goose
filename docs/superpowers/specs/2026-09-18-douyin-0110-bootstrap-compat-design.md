# 抖音小程序 0.1.10 Bootstrap 兼容修复设计

## 背景与根因

线上版 0.1.10 会严格校验 `/douyin-mini/bootstrap` 的手机号功能字段，只接受：

```json
{
  "douyin_phone": false,
  "phone_capture_mode": "sms"
}
```

生产运行配置启用抖音手机号能力后，接口改为返回
`douyin_phone=true` 和 `phone_capture_mode=douyin_phone`。0.1.10 因此拒绝整个
bootstrap 响应，继而导致首页和项目实景停留在骨架屏，预算初算提示数据无效，免费量房
提示咨询服务无法加载。

正在审核的 0.1.39 已兼容旧、新两种字段组合，且必须继续收到当前运行配置，才能保留抖音
手机号能力。0.1.10 与 0.1.39 的会话请求体相同，不能通过业务请求字段区分版本。

抖音 `tt.request` 会自动附带固定格式的 `Referer`：
`https://tmaservice.developer.toutiao.com/?appid={appid}&version={appVersion}`。
客户端不能覆盖该请求头，因此后端可用它识别线上旧版本，而无需修改或撤回审核包。
依据：<https://developer.open-douyin.com/docs/resource/zh-CN/mini-app/develop/api/network/http/tt-request>。

## 目标

- 立即恢复应用 `ttd033a68e4e56ccd301` 的线上 0.1.10 内容加载。
- 不撤回、不修改正在审核的 0.1.39。
- 保持 0.1.39 的抖音手机号授权能力。
- 将兼容范围限制在一个 AppID 和一个版本，避免影响其他抖音小程序安装。
- 在 0.1.39 全量上线并稳定运行后删除临时兼容逻辑。

## 非目标

- 不修改抖音小程序代码或重新上传审核包。
- 不修改数据库结构或运行配置。
- 不改变鉴权、租户选择、短信验证或抖音手机号解密流程。
- 不根据 User-Agent、缓存会话时间或安装记录中的模板版本猜测客户端版本。

## 方案

### 请求版本识别

Controller 从 `request.headers.referer` 读取请求头并交给一个纯函数解析。只有同时满足以下条件
才选择 0.1.10 兼容合同：

1. URL 使用 `https`；
2. 主机名为 `tmaservice.developer.toutiao.com`；
3. `appid` 为 `ttd033a68e4e56ccd301`；
4. `version` 精确等于 `0.1.10`；
5. `appid` 与当前 JWT 中的 `douyin_app_id` 一致。

请求头缺失、不是字符串、URL 无法解析、域名不符、AppID 不符或版本不符时，一律选择当前
运行配置。解析失败不产生接口错误，避免普通客户端因非业务请求头异常而不可用。

### Controller 与 Service 边界

Controller 负责读取 HTTP 请求头并把结果转换为明确的合同选项：

```ts
{ featureContract: "legacy_0_1_10" | "runtime" }
```

Content service 继续负责组合 bootstrap 数据。选择 `legacy_0_1_10` 时，仅在响应副本中覆盖：

```json
{
  "douyin_phone": false,
  "phone_capture_mode": "sms"
}
```

`cases`、`sites`、`sms_lead` 及所有其他 bootstrap 数据继续使用生产运行配置。Service 不修改
数据库中的 `runtime_config`，也不改变后续短信或手机号接口的权限规则。

### 数据流

1. 0.1.10 发起 `GET /douyin-mini/bootstrap`，抖音运行时自动附带包含版本号的 Referer。
2. Controller 验证 Referer 的来源、AppID、版本及 JWT AppID。
3. Controller 将 `legacy_0_1_10` 传入 content service。
4. Service 加载现有租户、公司、项目和运行配置，只覆盖响应中的两个手机号功能字段。
5. 0.1.10 接受响应并正常渲染；短信方案继续可用。
6. 0.1.39 或其他版本得到 `runtime` 合同，继续使用抖音手机号授权。

## 安全与失败处理

- Referer 只用于响应兼容，不参与身份认证、租户选择或权限判断。
- 即使请求头被外部 HTTP 客户端伪造，结果也只是退回短信手机号模式，不会获得额外权限。
- JWT AppID 必须与 Referer AppID 一致，避免跨应用误用兼容合同。
- 不记录 token、手机号或完整请求头。必要的诊断日志只能包含解析后的 AppID、版本和合同名。
- 所有既有业务错误继续通过 `error-factory.ts` 产生；兼容解析本身采用安全回退，不新增错误响应。

## 验证

自动化验证覆盖：

- 官方格式 Referer、目标 AppID、0.1.10 选择旧合同；
- 0.1.39、其他版本、其他 AppID、JWT AppID 不匹配、错误域名、非 HTTPS、缺失或畸形 Referer
  均选择当前合同；
- 旧合同只覆盖两个手机号功能字段，不改变其他功能字段；
- 当前合同原样返回现代手机号配置；
- Controller 将解析结果和认证用户正确传给 service；
- API 类型检查、相关 Bun 测试和 API 构建通过。

生产发布后使用 iPhone 抖音真机验证线上 0.1.10：

- 首页结束骨架屏并展示内容；
- 项目实景正常加载；
- 预算初算配置正常加载；
- 免费量房页正常加载并展示短信手机号流程。

同时使用 0.1.39 审核版二维码验证：

- 免费量房仍可获取抖音绑定手机号；
- 客户项目登录仍可授权抖音手机号；
- 首页、项目实景和预算初算正常加载。

## 发布、回滚与删除条件

本次只发布 API，不发布 admin、不上传小程序。若线上验证失败，回滚 API 部署到上一生产 revision；
由于没有数据库变更，不需要数据回滚。

兼容逻辑在以下条件全部满足后删除：

1. 0.1.39 审核通过并完成全量上线；
2. 线上版本信息确认 0.1.39 已替代 0.1.10；
3. 首页、项目实景、预算初算、免费量房和客户项目登录均完成生产真机验证；
4. 全量上线后连续 7 天没有与 0.1.10 兼容相关的用户反馈或生产异常。

删除时一并移除版本识别、旧合同分支和对应测试，bootstrap 恢复始终返回运行配置。

## 备选方案及取舍

- **全局关闭抖音手机号能力：** 可以恢复 0.1.10，但会让审核版免费量房退回短信模式，增加审核风险。
- **等待 0.1.39 上线：** 不需后端修改，但现有线上服务在审核和发布期间持续不可用。
- **修改客户端主动上传版本：** 长期更清晰，但当前审核包没有该字段，必须撤回并重新上传，无法处理本次故障。

因此采用 Referer 精确匹配的后端兼容方案。
