# 供应商 SKU 系统管理编码设计

## 目标

租户私有 SKU 与平台共享 SKU 的内部管理编码均由系统生成，用户在新增和编辑时不再填写或修改编码。

## 规则

- 租户私有 SKU 使用 `TS-<完整 SKU UUID 去连字符后的大写十六进制>`。
- 平台共享 SKU 使用 `PS-<完整 SKU UUID 去连字符后的大写十六进制>`。
- 服务端始终根据路径中的 `skuId` 生成编码，忽略旧客户端提交的 `sku_code`。
- 创建和更新 schema 暂时接受旧客户端的 `sku_code`，由 Service 在可信边界覆盖或剥离，避免破坏已部署客户端重试。
- 既有 SKU 编码保持不变，不回填、不重写。
- 数据库新增 `command_supplier_sku_v3`，在原子命令内再次覆盖或剥离编码，防止绕过 Service 写入手工编码。
- v3 会规范化 v2 已记录的旧请求载荷，确保部署前成功请求在部署后仍可用同一幂等键重放。
- 可采购商品一键创建新增 v2 RPC，规范化完整 SKU 编码、调用 SKU v3，并兼容 v1 历史父命令请求重放；原 v1 保持不变供旧 API 启动和受控回退。
- SKU 编码继续由现有作用域唯一索引约束；migration 仅新增 SKU v3、复合命令 v2 及其执行权限，不改表、不回填数据。

## 管理界面

- 新增 SKU 显示只读提示“保存后系统自动生成”。
- 编辑 SKU 显示当前编码但不可修改。
- 租户侧 SKU 列表不展示内部编码。
- 平台商品管理侧 SKU 列表保留只读编码，供排障和数据核对。

## 边界

内部管理编码不承载厂商货号、条码或 ERP 编码。后续如需这些业务标识，应新增独立字段，不能复用 `sku_code`。

## 验证

- Schema 测试证明旧客户端编码仍可被接收，Service 测试证明编码会在可信边界被覆盖或剥离。
- Service 测试证明租户与平台创建命令分别使用 `TS-`、`PS-` 系统编码。
- Migration 合同测试证明数据库使用完整 UUID 编码，并兼容旧请求重放和滚动发布期间的 v2 调用；待所有 API 版本切换后再单独撤销 v2 权限。
- Admin 状态测试证明编码不参与表单有效性和提交载荷。
- 运行 API/Admin 类型检查、构建和供应商商品相关测试。

## 发布约束

- 这是写入语义切换，不允许新旧 API 同时承接 SKU 写请求。
- 应先短暂停止 SKU 新增/编辑流量，应用 migration 后立即切换新 API，再恢复写入。
- 应用回滚前同样先停止 SKU 写入和不确定请求重试；数据库 migration 保持向前兼容，不回退函数。
- 旧客户端仅修改 `sku_code` 的全新请求会被拒绝；保留该字段的 schema 兼容仅用于重放发布前已成功的幂等事件。
