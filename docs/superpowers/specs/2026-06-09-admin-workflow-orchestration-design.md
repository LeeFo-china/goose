# Admin 流程编排平台设计

## 背景

当前系统里已经存在多套硬编码流程：

- 客户和项目主状态机。
- 施工阶段和工序验收。
- 费用申请、审批链和打款。
- 任务中心待办。

这些流程能支撑标准业务，但不同装修公司的销售、施工、验收和审批习惯差异明显。如果继续为每个业务域单独加配置表，短期能解决局部问题，长期会形成多套难以组合的流程配置。

本设计目标是在 Admin 端建设一套租户可配置的流程编排能力。第一阶段采用“受限流程引擎 + 业务节点库”路线：底层统一流程定义和运行时，上层只开放装修业务可理解、可校验的节点类型和属性。

## 目标

- 租户 Admin 可以通过画布配置主流程和子流程。
- 节点可以拖拽编排，并按类型编辑属性。
- 支持业务流转、施工阶段、工序、审批、确认、通知、自动动作等节点。
- 流程发布后生成不可变版本，新实例绑定创建时版本。
- 第一阶段真实运行费用审批子流程。
- 主流程、施工阶段和工序流程先支持设计、预览和校验，不直接影响生产小程序流程。
- 为后续扩展到更自由的编排能力预留模型边界。

## 非目标

- 第一版不做完整 n8n 式低代码平台。
- 第一版不开放自由脚本、任意 HTTP 请求、SQL 或不受控表达式。
- 第一版不让流程配置变更立即影响所有进行中的实例。
- 第一版不直接替换施工和工序生产链路。
- 第一版不迁移历史费用、项目、客户实例到新运行时。

## 产品结构

Admin 新增“流程编排”模块，独立于单个业务页面。

### 流程模板库

平台提供预置模板，租户复制后编辑：

- 客户销售主流程。
- 施工主流程。
- 标准工序模板。
- 费用审批模板。

租户不需要从空白画布开始。模板库也为后续行业最佳实践沉淀留出入口。

### 流程设计器

设计器采用三栏布局：

- 左侧：流程导航和节点库。
- 中间：画布，支持拖拽节点、连线、子流程折叠或展开、缩放和自动排布。
- 右侧：属性面板，根据节点类型展示不同配置项。

顶部提供版本、保存草稿、模拟运行、校验、发布操作。底部或抽屉展示校验结果、模拟路径和影响范围。

### 发布与版本管理

流程有草稿版和已发布版。租户编辑草稿，发布前必须通过校验。发布后生成不可变版本快照，只影响新创建的流程实例。

已有实例继续绑定创建时版本。后续可以提供受控迁移能力，但不把“立即影响全部未完成实例”作为常规能力。

## 节点模型

画布节点使用统一 Node Shell：

- 节点 ID。
- 流程归属。
- 节点标题和描述。
- 节点类型。
- 画布位置。
- 入边和出边。
- 权限、可见性、超时、回退策略。
- 类型属性。

节点类型决定属性面板和执行器。第一阶段支持以下节点类型。

### 业务节点

用于客户销售和项目主流程，例如：

- 客户线索。
- 电话跟进。
- 到店。
- 量房。
- 设计。
- 报价。
- 定金。
- 签约。

可配置属性：

- 业务状态。
- 进入条件。
- 负责人规则。
- 跟进时限。
- 待办生成规则。
- 退出条件。

### 施工阶段节点

用于施工主阶段，例如拆改、水电、泥木、油漆、安装、竣工。

可配置属性：

- 阶段编码。
- 阶段名称。
- 前置阶段。
- 负责人规则。
- 是否允许并行。
- 是否触发工序子流程。

### 工序节点

工序节点是独立核心节点，不合并到施工阶段里。它描述具体作业项，例如水电定位、开槽、布管、打压测试、闭水试验。

可配置属性：

- 所属施工阶段。
- 作业说明。
- 施工日志要求。
- 图片要求。
- 验收触发条件。
- 整改规则。
- 客户可见性。

### 审批节点

用于费用审批、主管确认、财务审批等。

可配置属性：

- 审批人规则。
- 岗位、部门或员工选择。
- 金额阈值。
- 会签或或签。
- 驳回目标。
- 审批意见要求。

### 确认节点

用于客户确认、内部确认、整改确认。

可配置属性：

- 确认对象。
- 超时策略。
- 默认动作。
- 异议入口。
- 整改路径。

### 通知节点

用于小程序通知、短信、待办提醒。

可配置属性：

- 通知对象。
- 通知渠道。
- 通知模板。
- 模板变量。
- 失败重试策略。

### 自动动作节点

用于有限白名单动作，不开放任意代码。

第一版允许的动作：

- 创建待办。
- 更新业务状态。
- 启动子流程。
- 写入审计事件。

后续可以扩展更多动作，但必须逐项加入白名单和后端校验。

## 主流程与子流程

采用“主流程 + 子流程”结构。

主画布表达客户全生命周期：

- 线索。
- 电话跟进。
- 到店。
- 设计。
- 报价。
- 定金。
- 签约。
- 开工。
- 竣工。
- 结算。

复杂部分作为子流程展开：

- 施工子流程。
- 工序子流程。
- 费用审批子流程。
- 验收或客户确认子流程。

所有流程共用一个运行时和节点模型。子流程节点可以启动另一个 workflow instance，并把父子关系写入实例关系。

## 节点配置校验

节点配置使用 JSONB 存储，但不能自由写入。后端按节点类型提供 Zod schema 校验。

校验分两层：

- 公共节点校验：标题、节点类型、权限、超时、回退、位置等。
- 类型属性校验：审批人规则、工序要求、通知模板、动作白名单等。

发布前必须通过流程级校验：

- 有且只有一个开始节点。
- 至少一个结束节点。
- 不允许不可达节点。
- 不允许无出口的非结束节点。
- 条件分支不能全部为空。
- 节点属性必须满足类型 schema。
- 费用审批试点流程必须包含审批通过、驳回和结束路径。
- 财务、客户确认、验收节点必须启用审计。

## 运行时设计

运行时作为独立 service，不把流程执行逻辑散落到各业务 service 中。

核心方法：

- `startWorkflow(input)`
- `completeNode(input)`
- `failNode(input)`
- `retryNode(input)`
- `cancelWorkflow(input)`
- `simulateWorkflow(input)`

业务模块只通过运行时接口启动或推进流程。

执行过程：

1. 业务模块创建业务对象。
2. 调用 `startWorkflow()` 创建流程实例。
3. 运行时创建开始节点实例。
4. 节点执行器处理节点动作。
5. 节点完成后，运行时根据连线条件计算下一节点。
6. 创建后续节点实例和待办。
7. 所有状态变化写审计日志。

节点执行失败时，节点进入 `failed` 状态。Admin 可以手动重试、跳过或终止，但这些动作必须受权限控制并写审计日志。

## 费用审批试点

第一阶段真实运行只接费用审批子流程。

接入方式：

- 创建费用申请后启动费用审批 workflow instance。
- 主管审批、财务审批、打款登记映射为审批节点或自动动作节点。
- 金额阈值通过结构化条件控制是否跳过节点。
- 原有费用申请状态字段继续保留，但状态来源逐步改为 workflow 驱动。
- 原有费用接口外观尽量不变，减少 Admin 和小程序改动。
- 待办可以先通过适配层同步到现有任务中心，后续再统一消费 `workflow_tasks`。

费用审批试点必须保留原审计能力：

- 审批人。
- 审批动作。
- 审批意见。
- 审批时间。
- 驳回路径。
- 打款记录。

## Admin 设计器交互

租户 Admin 的典型操作流：

1. 从模板库复制一个流程。
2. 在主画布配置客户生命周期节点。
3. 给关键节点挂子流程。
4. 点击节点，在右侧属性面板配置负责人、条件、表单要求、待办、通知、回退路径。
5. 使用模拟运行选择样例对象。
6. 查看系统会进入哪些节点、跳过哪些节点、创建哪些待办、谁是负责人。
7. 校验通过后发布。

条件编辑使用结构化规则构建器，不让用户写表达式。示例：

- 费用金额大于 5000。
- 客户来源等于抖音。
- 当前阶段等于水电。
- 项目类型等于整装。

## 小程序集成原则

小程序不理解画布，也不直接消费流程定义。

小程序只消费后端归一化后的结果：

- 当前任务。
- 下一步动作。
- 必填材料。
- 可见节点状态。
- 待确认事项。

这样流程配置复杂度留在后端和 Admin，小程序端保持稳定。

## 版本策略

流程实例默认锁定创建时版本：

- 流程配置变更只影响新实例。
- 已进入流程的实例继续按旧版本运行。
- 发布版本不可变。

后期可以增加受控迁移：

- Admin 选择部分实例迁移。
- 系统先做迁移预检。
- 已完成节点不回滚。
- 财务审批、客户确认、验收节点默认不可自动改写。
- 迁移写审计日志。

不把“配置一改立即影响所有未完成实例”作为常规能力。

## MVP 分期

### Phase 1：流程基础设施和设计器骨架

交付：

- 统一流程定义、版本、节点、连线、发布快照表。
- Admin 流程列表、模板复制、设计器画布、节点属性面板。
- 主流程、施工阶段、工序、费用审批都能设计和预览。
- 支持保存草稿、校验、发布。
- 不驱动真实业务。

目标：验证租户能否理解和配置这套模型。

### Phase 2：费用审批真实运行

交付：

- 费用审批流程接入运行时。
- 创建费用申请启动 workflow instance。
- 主管审批、财务审批、打款登记由节点驱动。
- 待办、审批记录、状态回写、审计日志打通。
- 保留现有费用接口外观。

目标：用低风险业务验证引擎可靠性。

### Phase 3：主流程和销售业务流转

交付：

- 客户线索、电话跟进、到店、设计、报价、定金、签约节点接入。
- 业务节点驱动客户或项目状态、跟进待办和统计口径。
- 支持租户按公司销售方法配置流程。

目标：把流程编排从财务扩展到经营前端。

### Phase 4：施工阶段、工序和验收

交付：

- 施工阶段节点、工序节点真实驱动小程序任务。
- 工序日志、图片要求、验收、整改、客户确认接入。
- 项目进入下一阶段由流程规则控制。
- 支持子流程模板复用，例如标准水电工序模板。

目标：接入装修交付核心，但放在引擎成熟之后。

## 迁移策略

第一版不直接替换现有状态机：

- 现有硬编码状态继续保留。
- 新 workflow 先作为控制层和适配层接入费用审批。
- 费用审批稳定后，再逐步让客户状态、项目状态、施工阶段状态由 workflow 驱动。
- 每个业务域迁移时保留兼容字段，例如 `status`、`current_step`。
- 老数据继续按旧逻辑展示。
- 新实例使用新流程版本。
- 每个业务域迁移都必须有审计和回滚方案。

## 风险和约束

### 自由度过高

第一版必须限制节点类型和属性，不开放脚本、任意 API、SQL 或复杂表达式。

### 租户误配置

发布前校验和模拟运行是必做能力。未通过校验不能发布。

### 历史实例混乱

流程版本必须不可变，实例必须绑定版本。

### 小程序复杂度

小程序不读取画布，只读取后端归一化的当前任务和下一步动作。

### 审计合规

审批、财务、客户确认、验收节点必须记录完整执行日志。

### 查询性能

流程实例、节点实例、待办和审计日志都会成为高频列表。所有列表接口必须分页；涉及租户、业务对象、状态、待办人的查询必须建立索引，并通过 migration 管理。

## 决策记录

- 选择路线 B：受限流程引擎 + 业务节点库。
- 采用主流程 + 子流程结构。
- 第一阶段 MVP 采用主流程可视化 + 费用审批子流程真实运行。
- 工序节点作为独立核心节点，不合并到施工阶段。
- 流程实例默认绑定创建时版本，后续只做受控迁移。
- 第一版不开放 C 级自由编排能力，但数据模型为未来扩展预留空间。
