# 租户客户线索统一管理设计

日期：2026-09-06。状态：依据用户已同意的评估方案整理，供下一阶段实施。

## 目标与范围

微信小程序员工端增加“客户线索”，支持查看、筛选、分配或改派、跟进、转客户、标记无效。Admin 与小程序操作同一份租户数据。首期接入现有抖音小程序线索，建立来源无关的管理契约，为小红书、视频号预留接入边界。

首期不实施小红书或视频号采集、导入、消息订阅、自动派单、批量操作、公海认领、直接拨号。现有 H5 营销线索与平台派给租户的线索不自动纳入新列表，它们有不同的归属和转化流程，后续接入需逐项核对。

本仓库负责 API、Admin、共享 domain、migration 和交接文档。orange 仓库只能只读参考，小程序页面由小程序团队实现。

## 已核实的基础

- 数据保存在 `public.marketing_leads`；已有 `source`、`assigned_employee_id`、`customer_id`、`lead_status`、`version` 等字段。
- `apps/api/src/controllers/tenant-douyin-leads/index.ts` 已提供列表、详情、候选员工、负责人筛选项、预约、跟进、分配、转客户和无效操作。
- `apps/api/src/services/tenant-douyin-leads.ts` 已执行租户、操作权限、负责人数据范围和客户创建权限检查。
- `apps/api/src/schema/tenant-douyin-leads.ts` 已要求命令携带 `expected_lead_version` 和 `idempotency_key`，但跟进强制关联预约。
- `douyin_lead_follow_ups` 的预约外键目前非空；数据库命令、来源快照、操作流水和保护触发器存在抖音耦合。
- `apps/api/src/services/tenant-douyin-leads-public.ts` 使用严格响应契约；客户和负责人摘要没有 ID，手机号只返回脱敏值。
- `apps/api/src/plugins/auth/legacy/douyin-routes.ts` 仅将 `/douyin-mini/*` 识别为抖音访客会话接口；租户管理接口沿用正常员工鉴权。微信真实员工会话可用性仍需联调。
- `20260830110000_align_douyin_measurement_command_owners.sql` 专门修复了命令函数 owner 与表 owner 不一致的问题；新命令必须保留这一边界。

## 接口与数据设计

新增 `/tenant/customer-leads` 系列接口。旧 `/tenant/douyin-miniapp/leads` 保留路径、字段、错误码和抖音来源限制，两者复用通用业务核心；不复制业务服务或历史线索。

新接口返回 `source` 和 `source_label`。首期支持的来源为 `douyin_miniapp`，展示“抖音小程序”。现有 `attribution.source_type` 继续表示短视频、直播、搜索等渠道内归因，不与平台渠道混用。未知来源不默认按抖音解析，也不自动暴露其他营销数据。

通用详情包含线索基础信息、脱敏手机号、负责人 ID、客户关联 ID、版本和可用操作。客户关联 ID/跳转能力必须经过现有客户访问策略校验；仅有线索查看权限不获得客户详情权限。量房、预算、AI 信息是可选扩展，缺失不阻止通用操作。

列表状态仍为 `new/contacted/converted/invalid`；“未分配”使用独立负责人过滤，不增加业务状态。列表、跟进、预约、员工候选及筛选选项均分页，默认 1/20，最大每页 100。排序使用 `created_at DESC, id DESC`。

## 权限和兼容

新增 `customer_lead.read/assign/follow_up/convert`；无效操作首期沿用 convert 权限，保持现有业务分组。标准租户 `system_admin` 依项目现有模式获得新权限；普通角色由租户管理员配置，旧 `douyin_lead.*` 不自动转换成跨来源权限。员工权限覆盖和显式禁用继续遵循现有权限计算。

旧入口继续要求旧权限。新入口要求新权限，没有从新权限失败回退旧权限的隐式逻辑。普通员工与部门负责人仅查看授权数据范围，未分配线索只有 `all` 范围可见；首期不开放部门公海或员工抢单。

分配目标必须为同租户有效员工，部门范围必须同时约束原线索和目标员工。变更发生时数据库复核负责人/部门前置条件，防止请求期间的调岗或改派绕过授权。改派后失去读取权限的操作者应得到成功回执并关闭详情、刷新列表。

## 操作一致性

- 普通跟进可以不关联预约；修改量房状态时必须关联属于该租户和该线索的有效预约，并执行现有状态机与确认时间约束。
- 转客户按 `(tenant_id, phone)` 查重。创建新客户时保留 `customer.create` 权限与当前创建范围规则；默认负责人为线索负责人，未分配时为操作员工。
- 关联已有客户保留其负责人和主来源，同时追加线索来源记录。新客户来源由服务器来源映射产生，不能由客户端任意传入。
- 无效线索不能转客户，已转客户不能标记无效；其他状态限制以当前命令为基线，不新增恢复操作。
- 同一次业务意图的网络重试复用幂等键；内容或版本变化后形成新意图。版本冲突返回 409，要求刷新，不能静默覆盖。
- 新旧入口共享同一线索版本与幂等事实。保留已有请求摘要和历史结果兼容，升级后旧请求仍能重放。
- 线索转化、客户关联、来源记录、预约关联及幂等结果在同一事务中提交。

## 数据库演进

复用 `marketing_leads` 和现有操作事实。首期保留历史表名，避免重命名引发对现有提交链路、RPC、触发器的广泛修改；代码通过通用 repository 封装历史命名。

将通用命令逻辑从现有抖音函数提取为公共核心，旧函数作为限定来源的兼容包装。预约与抖音来源快照属于来源扩展。跟进预约列允许空值，但非空时必须校验预约、线索、租户一致。新增无预约来源记录的去重边界，保留原预约来源记录及唯一约束。

所有字段、索引、函数、权限种子、约束和触发器变更通过新 migration。保留租户复合外键、只追加流水、受控函数写入、版本管理和 `SECURITY DEFINER`/owner 限制。禁止为兼容而关闭保护触发器。

## 发布和验收

按 migration → API → Admin → 共享包交接 → 微信小程序发布顺序实施。先验证静态检查，再进行数据库和双端 smoke。关键证据包括权限隔离、未分配范围、同手机号转化、无预约跟进、重复点击、并发改派、旧请求重放、预约来源保留和错误恢复。

先停用新入口即可回退前端；数据库采用前向修复，保留新增跟进和来源事实。产生空预约跟进后不得直接恢复非空约束。涉及 SQL 核心回退时必须同时核对新旧 API 兼容与函数 owner，不删除业务数据。
