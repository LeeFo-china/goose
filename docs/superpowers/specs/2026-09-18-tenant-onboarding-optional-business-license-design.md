# 装企入驻营业执照选填设计

## 目标

与小程序提交契约保持一致：装企入驻申请可以不上传营业执照，平台超管仍可审核通过并创建租户。`business_license_file_id` 缺省、为 `null` 或为空字符串时均表示未上传；存在有效文件 ID 时继续执行现有的私有文件、访客归属、场景和状态校验。

## 业务边界

- 营业执照不是提交申请或批准创建租户的前置条件。
- 未上传营业执照的申请继续进入现有 `submitted`、`reviewing`、`approved` 流程，不新增状态或布尔标志。
- 超管仍可在个案审核中把“营业执照”列为补充资料；申请人补充后继续走现有重新提交逻辑。
- 已上传营业执照的安全校验保持不变，不能引用其他访客、错误场景、公开、已删除或非活动文件。
- 本次不修改 `/Users/leefo/Public/work/orange`，小程序端已完成的选填交互仅作为只读契约依据。

## 方案

### 请求和领域模型

API 使用独立的可选营业执照字段 schema，把去除首尾空白后的空字符串归一为 `null`，合法非空值继续校验 UUID。

创建申请时，字段缺省、`null` 和空字符串最终都写入数据库 `NULL`。补充资料时保留 PATCH 语义：字段缺省表示保持原值，显式 `null` 或空字符串表示移除已有营业执照，合法 UUID 表示设置或替换营业执照。

共享申请记录、平台审核详情、数据库生成类型和运行时解析器统一使用 `string | null`，避免数据库已允许空值但 API 或后台仍按必填解析。

### 服务和持久化

提交服务仅在规范化后的文件 ID 非空时调用 `assertPrivateBusinessLicense`。创建 payload 明确把缺省值转换为 `null`。

补充资料服务仅对非空的新文件 ID 执行文件校验；显式清空会生成 `business_license_file_id: null` 的补丁。原子补充 RPC 只在补丁包含非空文件 ID 时锁定并复核文件，字段为 `null` 时直接清空数据库列。

新增前向 migration，执行以下变更：

1. 删除 `tenant_onboarding_applications.business_license_file_id` 的 `NOT NULL` 约束。
2. 保留指向 `platform_file_objects(id)` 的外键和 `ON DELETE RESTRICT`。
3. 重新定义申请提交 RPC，使 UUID 转换和文件复核仅在非空文件 ID 时执行。
4. 重新定义补充资料 RPC，使显式 `null` 可以清空字段，同时保留非空文件的写边界复核。

已有历史 migration 不修改。新 migration 设置有限的 `lock_timeout` 和 `statement_timeout`，并包含说明性列注释。

### 审批和租户创建

现有批准服务和 `approve_tenant_onboarding_application` RPC 不依赖营业执照文件，不增加新的资质拦截。平台超管可以对无营业执照的 `submitted` 或 `reviewing` 申请执行现有批准动作，原子创建租户、管理员、服务商资料和审核记录。

平台审核状态变更 RPC 继续在申请快照中返回 `business_license_file_id`，允许值为 `null`。补充资料字段枚举继续保留 `business_license_file_id`，使超管仍能按具体申请要求补充营业执照。

### 超管后台

平台审核详情类型把 `business_license_file_id` 改为可空。详情页在无文件时显示“未上传”，并隐藏或禁用营业执照预览操作，不请求签名 URL。

营业执照预览接口继续只允许具备审核权限的用户访问。无文件申请被直接请求预览时，返回经过错误工厂包装的 `TENANT_ONBOARDING_DOCUMENT_NOT_UPLOADED` 业务错误，不把“未上传”误报为申请不存在，也不生成无效签名 URL。

## 数据流

1. 小程序提交申请，可省略 `business_license_file_id`。
2. 请求 schema 将缺省、`null` 或空字符串规范化为无文件状态。
3. 服务完成短信、定位上下文和来源归因校验；仅在文件存在时校验营业执照。
4. 原子提交 RPC 在写边界再次校验非空文件，并将无文件状态保存为 `NULL`。
5. 查询解析器和超管后台接收可空字段；无文件时展示“未上传”。
6. 超管可以直接批准申请，批准 RPC 不以营业执照是否存在作为条件。
7. 若超管选择要求补充营业执照，则沿用现有 `supplement_required` 流程；申请人提交文件后恢复为 `submitted`。

## 错误处理

- 非 UUID 的非空文件 ID：请求校验失败。
- 文件不存在、归属其他访客、场景错误、已删除、非活动、非私有或存在公开 URL：保持现有 `TENANT_ONBOARDING_DOCUMENT_FORBIDDEN`。
- 无营业执照直接调用预览接口：返回 `TENANT_ONBOARDING_DOCUMENT_NOT_UPLOADED` 和“营业执照未上传”。
- 幂等键重复提交：无文件和有文件请求都返回原申请，不重复消费短信或创建记录。
- 数据库迁移失败：事务整体回滚，不留下部分函数或约束状态。

## 兼容性

- 已有非空营业执照记录不改值，外键和删除限制保持不变。
- 旧客户端继续上传文件时，校验、提交和审核行为保持不变。
- 新客户端省略字段时可以正常提交和批准。
- 申请列表字段不包含营业执照，不改变分页和查询成本。
- 不新增依赖、缓存、队列或额外数据库查询。

## 验证

- Schema：覆盖字段缺省、`null`、空字符串、纯空白、合法 UUID 和非法非空值。
- Service：覆盖无文件跳过文件查询并以 `NULL` 创建；合法文件继续校验；非法或越权文件继续拒绝；补充资料的缺省、清空和替换语义。
- Parser：覆盖申请详情、平台审核详情和审核 mutation 快照中的 `null`。
- Repository/RPC 契约：覆盖提交 RPC 的条件文件校验、补充 RPC 的显式清空、服务角色权限和幂等路径。
- Approval：覆盖无营业执照申请可以批准并创建租户，批准结果和审核记录完整。
- Admin：类型检查和构建通过，无文件详情不触发预览请求并显示“未上传”。
- Database：使用 `supabase migration list` 确认本地与远端状态；应用后核对列可空、外键仍存在且删除规则仍为 `RESTRICT`。

## 发布与回滚

先部署 migration，再部署依赖可空返回类型的 API 和 Admin，以避免应用代码接收到数据库尚未支持的写入。发布后分别 smoke 无文件提交、有文件提交、无文件批准和营业执照预览。

代码回滚不会改写已有数据。若需要恢复数据库 `NOT NULL`，必须先确认不存在 `business_license_file_id IS NULL` 的申请，并为存量空值补齐真实文件；禁止使用占位 UUID。完成数据处置后再通过新的前向 migration 恢复约束。
