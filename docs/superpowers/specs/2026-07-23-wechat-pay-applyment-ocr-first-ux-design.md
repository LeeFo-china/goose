# 微信支付进件 OCR-first 交互重构设计

> 日期：2026-07-23
> 状态：方向已确认，待规格评审
> 范围：租户 Admin 微信支付开通申请
> 设计系统：Gooes Admin + shadcn/ui

## 1. 背景

当前租户微信支付开通申请采用四步表单：

1. 主体与证照
2. 法人和超级管理员
3. 经营及结算
4. 附件与复核

OCR 依赖证照附件，但附件位于最后一步。用户需要先手工填写主体、法人和结算信息，
再上传证照并执行识别，随后返回前面的步骤核对回填结果。该顺序把 OCR 作为传统表单
的附加功能，没有发挥证照自动采集信息、减少重复输入的作用。

当前实现已经具备私有附件上传、OCR capability 查询、单份证照识别、识别字段映射和
草稿保存能力。本次重构优先调整信息架构和交互状态，不重新设计微信支付进件领域模型。

## 2. 目标

1. 让证照成为申请信息的主要入口，用户先上传资料，再核对识别结果。
2. 自动回填可可靠识别的信息，只要求用户处理缺失、冲突和业务补充字段。
3. 把附件、识别结果和对应字段放在同一工作上下文中，避免跨步骤往返。
4. 支持草稿自动保存和中断恢复，重新进入时定位到第一个未解决事项。
5. 明确 OCR 不可用、识别失败、资料不完整和权限不足等状态。
6. 保证敏感资料私有存储、短时预览、可追溯且不会被静默覆盖。

## 3. 非目标

- 不让 OCR 自动提交微信支付进件申请。
- 不修改微信支付要求的字段含义、必填规则和审核规则。
- 不在首版引入新的 OCR 服务商或新的前端依赖。
- 不在首版重做平台超管审核页面。
- 不在本次直接修改小程序仓库；后端契约应保持渠道无关，供后续小程序复用。
- 不为交互重构预先新增数据库表；确需持久化新状态时必须另行通过 migration 实施。

## 4. 用户与成功标准

主要用户是租户公司的管理员或财务负责人。他们低频办理进件，对微信支付技术字段不熟悉，
但能够提供营业执照、身份证、结算账户证明和经营场景材料。

成功标准：

- 首次进入申请时，首要任务是上传资料，而不是填写二十余个文本字段。
- 上传并识别支持的证照后，识别字段自动进入核对状态。
- 用户可以明确看到哪些字段来自 OCR、哪些需要手工补充。
- 正常样本下，用户只需修正异常字段和填写 OCR 无法获得的业务信息。
- 任意时刻离开页面后，已上传资料、已确认字段和手工输入不会丢失。
- 提交前所有阻塞项集中、可定位、可操作。

## 5. 设计方向

该页面属于受监管的后台任务流，采用克制、可信、任务导向的产品界面：

- `DESIGN_VARIANCE: 3`
- `MOTION_INTENSITY: 2`
- `VISUAL_DENSITY: 6`

页面沿用 Gooes Admin 的黑色主操作、黄色焦点状态、暖白工作台背景和 8px 以内圆角。
不使用营销式大标题、装饰渐变、卡片堆叠或非必要动画。

## 6. 信息架构

申请流程重构为四个有顺序含义的阶段：

1. `上传资料`
2. `核对识别`
3. `补充信息`
4. `确认提交`

顺序流程不再使用可任意切换的 Tabs 表达。页面顶部使用步骤状态条和 Progress，
已完成步骤允许返回查看，未满足前置条件的后续步骤不可直接跳过。

页面由一个主工作区构成，不使用卡片套卡片：

- 顶部：申请状态、四阶段进度、自动保存状态。
- 中部：当前阶段工作区。
- 底部：固定操作栏，包含返回、下一步或提交审核。
- 页面内错误：靠近对应资料或字段展示。
- 全局阻塞项：集中显示在底部操作栏上方。

## 7. 阶段一：上传资料

### 7.1 资料清单

页面根据主体类型、联系人类型和后端 readiness 规则生成资料清单，不在前端重复维护
微信支付必填规则。现有资料类别包括：

- 营业执照照片
- 法人身份证人像面
- 法人身份证国徽面
- 经办人身份证人像面
- 经办人身份证国徽面
- 结算账户证明
- 经营场景材料

主体类型优先从租户档案预填。租户档案缺失或无法确定时，只在资料清单上方要求用户先
选择主体类型；该选择属于生成资料清单的必要前置条件，不恢复为完整主体信息表单。

每项资料使用独立的上传项，包含：

- 资料名称和必填标记
- 上传要求
- 固定比例缩略图
- 文件名称和大小
- 当前处理状态
- 查看、替换、删除和重试操作

上传项状态统一为：

`待上传 / 上传中 / 识别中 / 待核对 / 已确认 / 识别失败`

### 7.2 OCR 触发

用户首次上传支持 OCR 的敏感资料前，集中确认一次证照识别授权。授权后：

1. 文件直传成功；
2. 后端返回 `file_object_id`；
3. 前端自动创建一次 OCR recognition；
4. 当前上传项进入“识别中”；
5. 识别完成后进入“待核对”或“识别失败”。

不再要求用户逐张点击“识别并回填”。相同文件版本和幂等键只允许创建一次有效识别
请求，页面重渲染或刷新不能重复计费。识别失败时由用户显式点击“重新识别”，并由
后端按明确的重试语义记录新尝试。

OCR capability 不支持当前证照时，上传仍然可用，并明确显示：

> 证照识别暂不可用，请在下一步手动填写。

### 7.3 预览

上传后直接显示内嵌缩略图，不只显示文件名。点击缩略图使用 shadcn Dialog 放大查看，
支持旋转、缩放和正反面切换。预览使用私有对象的短时签名地址，不暴露永久公开 URL。

## 8. 阶段二：核对识别

### 8.1 布局

桌面端采用左右分栏：

- 左侧为当前证照预览和资料切换列表。
- 右侧为该证照对应的识别字段。

窄屏改为单列，先显示资料切换栏，证照预览和字段核对按顺序排列。证照预览保持稳定
宽高比，加载过程使用 Skeleton，避免布局跳动。

### 8.2 字段状态

字段展示来源和核对状态：

- `已识别`：OCR 返回且尚未人工修改。
- `需补充`：OCR 未返回必填值。
- `需核对`：格式异常、正反面冲突或后端标记需要确认。
- `已修改`：用户覆盖了 OCR 值。
- `已确认`：用户确认该资料组可继续。

若 OCR 服务没有提供可信的置信度，不在前端制造“高可信度”或百分比。

页面优先展开“需补充”和“需核对”字段，识别正常的字段组默认收起。所有字段均允许
人工修正，但修正后保留“已修改”来源标记。

### 8.3 替换和覆盖规则

重新上传资料会创建新的文件版本和识别结果。合并规则如下：

1. 空字段可以直接使用新识别值。
2. 仍保持旧 OCR 值的字段可以更新为新识别值。
3. 用户手工修改过的字段不得静默覆盖。
4. 存在人工修改冲突时，显示旧值、新识别值和保留选择。
5. 用户确认后再写入草稿。

身份证正反面属于同一资料组。OCR capability 可用时，人像面和国徽面均完成识别后才
允许确认该组，避免姓名、号码和有效期分别保存后产生不一致。OCR capability 不可用
或用户选择手工填写时，两面资料上传完成且必填字段人工核对完成即可确认。

## 9. 阶段三：补充信息

本阶段只保留证照无法可靠获得或属于业务选择的信息，例如：

- 商户简称
- 联系人类型
- 超级管理员手机号和邮箱
- 客服电话
- 经营行业与结算规则
- 开户银行和支行信息
- 经营场景说明
- 联系地址
- 备注

公司名称、统一社会信用代码、法人姓名、身份证号码、证件地址、证件有效期、结算账户
名称和卡号等字段优先来自租户档案或 OCR，不要求用户重复录入。

字段值来源优先级：

1. 用户已确认的人工值
2. 当前文件版本的 OCR 值
3. 租户档案预填值
4. 空值

租户档案和 OCR 值不一致时不自动决定，以“需核对”状态展示差异。

## 10. 阶段四：确认提交

最终页按业务分组展示只读摘要：

- 主体和营业执照
- 法人和超级管理员
- 经营及结算
- 申请附件

每组提供“返回修改”，直接定位到对应资料或字段，不要求用户从第一步重新查找。

提交按钮上方集中展示后端 `submission_readiness.blockers`。每个阻塞项必须包含可理解
的中文说明和定位动作，例如：

- 缺少法人身份证国徽面
- 身份证有效期尚未确认
- 结算账户名称与营业执照名称不一致
- 经营场景说明未填写

OCR 完成不代表资料真实有效，也不代表用户授权提交。只有具备提交权限的租户管理员
明确点击“提交审核”后，才进入平台审核流程。

## 11. 自动保存和恢复

- 上传完成、资料组确认、字段修改和步骤切换均触发防抖草稿保存。
- 页面只在顶部显示“保存中 / 已自动保存 / 保存失败”，不连续弹出成功 Toast。
- 保存失败时保留本地编辑状态，并提供重试，不允许无提示丢失输入。
- 再次进入草稿时，默认定位到第一个识别失败、待核对或未满足必填规则的位置。
- 提交中禁用重复提交，并使用稳定的幂等键。

| 表单分组与错误 | `FieldSet`、`FieldGroup`、`Field` |
| 流程完成度 | `Progress`、本地步骤状态组件 |

| 阻塞与降级说明 | `Alert` |
| 已确认信息折叠 | `Collapsible` |
| 原图放大查看 | `Dialog` |
| 替换资料冲突确认 | `AlertDialog` |
| 加载占位 | `Skeleton` |

所有文本输入、选择、复选和操作按钮继续复用现有 shadcn 组件，不使用浏览器原始表单
控件。顺序流程不使用 Tabs 伪装步骤导航。

## 13. 前后端数据流

首版复用现有能力：

1. Admin 查询当前进件草稿和 `submission_readiness`。
2. Admin 查询当前租户的 OCR capabilities。
3. 文件通过现有私有直传链路上传。
4. Admin 使用 `file_object_id` 创建 `wechat_pay_applyment` 场景 recognition。
5. API 返回规范化识别字段、识别状态、文档类型和 recognition ID。
6. 用户确认或修正后保存现有进件草稿。
7. 最终提交继续使用现有微信支付进件接口。

前端需要为每份资料建立稳定的展示状态，但不能把微信支付必填规则、OCR 文档支持范围
或字段校验复制为新的本地业务事实。支持范围来自 capabilities，提交阻塞来自 readiness。

首版优先利用现有 OCR recognition 和进件草稿记录。只有在实现计划核查后确认现有数据
无法持久化“文件版本、人工确认、字段来源”时，才新增 migration；禁止直接修改远端表。

## 14. 安全和审计

- 证照原图存储在私有对象空间。
- 预览 URL 短时有效，不写入日志或长期缓存。
- 身份证号、手机号和银行卡号在摘要页默认脱敏。
- OCR 请求记录操作者、租户、文件对象、文档类型、场景和 recognition ID。
- 重新识别、人工覆盖和提交申请均保留审计事件。
- 前端错误信息不展示 SecretId、SecretKey、原始密钥、内部对象凭证或完整敏感号码。
- 删除或替换资料时，不立即物理删除仍被审计记录引用的对象。

## 15. 错误与恢复

| 场景 | 用户反馈 | 恢复动作 |
| --- | --- | --- |
| 上传失败 | 当前资料项内显示失败原因 | 重新上传 |
| OCR 不支持 | 显示能力不可用说明 | 手动填写 |
| OCR 超时或失败 | 保留已上传缩略图 | 重新识别或手动填写 |
| OCR 字段缺失 | 标记具体缺失字段 | 手动补充 |
| 新旧识别冲突 | 展示差异，不覆盖人工值 | 逐项选择 |
| 草稿保存失败 | 顶部显示保存失败 | 重试保存 |
| readiness 阻塞 | 最终页集中列出并可定位 | 返回对应资料或字段 |
| 权限不足 | 页面可只读，提交按钮不出现 | 联系具备权限的管理员 |

## 16. 验收标准

1. 新建申请首屏为“上传资料”，不再先展示主体文本表单。
2. 支持 OCR 的资料在授权后上传即自动识别，无需逐张点击回填。
3. 每份资料都有缩略图、状态、查看、替换和失败重试入口。
4. 识别结果与证照预览在同一核对上下文中展示。
5. OCR 正常字段、缺失字段、冲突字段和人工修改字段视觉可区分。
6. 替换资料不会静默覆盖人工修改值。
7. OCR 不可用或失败时，申请仍可通过手动填写继续。
8. 草稿离开后重新进入，已上传资料和已保存字段保持一致。
9. 最终提交页集中展示后端 readiness 阻塞项并能定位修改。
10. OCR 不会自动提交审核，提交仍由具备权限的用户明确确认。
11. 桌面和窄屏下均无字段、按钮、状态标签或预览内容重叠。
12. Admin 类型检查、相关组件测试、API 测试和浏览器 smoke 通过。

## 17. 实施分段

### 第一段：OCR-first 主流程

- 重排四阶段信息架构。
- 把资料上传移动到首阶段。
- 上传成功后自动触发已授权 OCR。
- 增加内嵌缩略图和处理状态。
- 将现有 OCR 回填改为页面内核对。

### 第二段：恢复与冲突保护

- 增加字段来源和人工修改状态。
- 实现重新识别差异确认。
- 完善自动保存、失败恢复和草稿定位。

### 第三段：提交收敛和跨端契约

- 收敛 readiness 阻塞项的中文说明和定位信息。
- 完成响应式、无障碍和完整浏览器 smoke。
- 输出渠道无关的 OCR 资料契约，供小程序团队只读对接。

第一段与第二段属于本次重构的必要范围。第三段中的小程序代码改动不在 gooes 仓库执行，
只提供后端契约和对接文档。
