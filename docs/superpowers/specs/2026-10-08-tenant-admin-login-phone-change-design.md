# 超管变更租户管理员登录手机号：第一期设计

日期：2026-10-08。已按用户明确要求修订：平台超管直接变更，无需旧号码或新号码验证码。实现与验证记录见 [直接换号计划](../plans/2026-10-08-tenant-admin-phone-direct-change.md)。

## 目标与范围

平台超管可以在租户详情中，为同一位租户管理员纠正或更换登录手机号，解决建户填错、号码停用和本人换号的问题。保留员工 ID、姓名、岗位、角色、业务记录和历史操作归属。

操作命名为“变更登录手机号”。更换管理员本人、离职交接、微信账号恢复分别具有不同的身份和权限含义，不纳入本期。本期不修改 orange 仓库，不修改企业核验、试用期限或企业联系电话。

## 现状依据

- `apps/api/src/schema/platform-tenants.ts`：创建参数包含 `admin.phone`，更新参数仅包含租户基础信息。
- `apps/admin/components/platform-tenants/platform-tenant-dialog.tsx`：编辑模式不包含管理员输入项。
- `apps/admin/app/(console)/platform/tenants/[id]/page.tsx`：管理员卡片当前展示初始化时创建或识别的员工。
- `apps/api/src/repositories/platform-tenants/legacy/members.ts`：当前有效管理员角色为租户内启用的 `system_admin`。
- `apps/api/src/services/admin-auth.ts`：后台按员工手机号匹配，多个员工命中时拒绝登录；已有账号通过员工 `user_id` 关联。
- `apps/api/src/services/phone-identity-login/service.ts`：小程序手机号登录按手机号发现客户、员工等候选身份，同号客户身份并不等于员工号码冲突。
- `apps/api/src/services/platform-authorization.ts`：已有后台令牌版本校验针对平台人员；不能假定租户后台业务请求已经受同一校验保护。
- `apps/api/src/services/authorization/legacy/context-cache.ts`：权限上下文含进程内缓存，单纯修改号码或清理一台实例缓存不能证明所有旧会话失效。

## 方案选择

平台超管核实后直接变更：填写新号码及原因，确认“管理员本人未变更”后提交。此操作不发送、不校验短信验证码，也不依赖短信服务开关。普通用户登录继续遵循原有验证码规则。

## 页面与操作流程

1. 租户详情的管理员区域列出当前有效管理员。多位管理员时分页，默认 20、最多 100；操作明确绑定租户 ID 和员工 ID，不能默认修改初始化管理员或列表第一项。
2. 仅平台超管看到“变更登录手机号”。普通平台运营人员及租户管理员不能调用该平台变更能力。
3. 弹窗显示租户、管理员姓名、原手机号及绑定情况；输入新手机号、变更原因，确认管理员本人未变更。
4. 新号码格式合法、不同于旧号且未占用其他员工身份后才可变更。新号码若仅有客户身份，不因此拒绝。
5. 提交时重新核对超管及管理员资格、员工版本和号码占用。校验全部通过才变更。
6. 成功提示：“登录手机号已变更，请管理员使用新号码重新登录后台。”刷新当前管理员信息并展示审计结果。明确提交失败时保留表单；结果未知时提供原请求幂等重试。

第一期入口放在详情页。租户列表可通过已有详情入口进入，不新增列表逐行查询和批量换号。

## 身份与登录规则

- 这是同一员工的号码变更，员工 ID、用户关联、角色和业务成员关系保持连续，不创建另一份员工档案。
- 变更成功后，旧手机号不能再匹配该员工；旧号码如有独立客户身份，其客户登录不受影响。
- 新号码已属于其他员工时返回冲突，不清空、合并或迁移对方账号。号码重复检查需要数据库约束或等价并发保护，不能只做前端查询。
- 本人原有微信/OAuth 绑定保留，不执行全局解绑；因此本操作不宣称能踢出原微信使用人。更换微信持有人或怀疑账号被他人控制，应走独立恢复/交接操作。
- 已签发的该员工后台会话在变更提交后发起的新请求中必须被拒绝，新号重新验证登录后正常访问。提交前已进入业务执行的请求不承诺撤回。
- 撤销范围限于该员工的后台登录，不能退出其客户、其他业务身份或其他用户。
- 后台专用认证账号与共享认证账号需要分别核对手机号用途。实现不得通过清空 `user_id`、覆盖共享认证账号手机号或复用“清除其他员工绑定”来绕过关联问题。业务手机号是当前登录匹配依据；认证层可登录号码若仍允许旧号恢复该员工访问，必须一并修复后方可发布。

## 数据流与实现边界

遵循现有 controller → service → repository/RPC 分层，不在 controller 内直接操作 Supabase。

读取阶段返回当前有效管理员及版本、操作能力和不可操作原因。确认接口请求仅包含 `new_phone`、`expected_version`、`reason`、`same_person_confirmed` 和 `idempotency_key`；租户与员工 ID 在路径中，操作者来自服务端认证上下文。客户端提供验证码、挑战或操作者字段均拒绝。

服务重新验证超管身份，直接换号 RPC 再次检查有效超管及凭证版本，锁定目标员工并验证角色与号码冲突。员工手机号、号码保护记录、后台凭证版本递增和成功审计原子提交。权限或审计失败时不得留下已变更的手机号。审计标记 `authorization_method=platform_superadmin`。旧发送验证码接口返回 410 提示刷新，不发送短信。

沿用 `employees.version`、`admin_auth_version` 和平台命令幂等/审计模式。补齐租户后台请求的版本校验，使用数据库权威安全快照，不能将进程内缓存失效当作跨实例安全保证。对同一请求复用安全快照，避免重复查询；凭用户 ID 定位员工的查询应有索引且只读取必要字段。

所有涉及本期号码写入的路径都必须保持版本和会话撤销规则一致；评估普通员工编辑与超管变更的并发，不能因其中一条路径没有递增版本而绕过冲突检测。

新增函数、索引、权限或触发器均通过 migration 管理。历史挑战和审计记录保留。敏感 RPC 仅允许 service_role 执行，显式撤销 PUBLIC、anon 和 authenticated；函数内部再次校验操作者及目标租户范围。实现优先复用现有号码锁与命令基础，不增加依赖、队列或缓存服务。

验证码及完整令牌不得写入审计和日志。成功审计保存操作者、租户、员工、时间、原因、请求标识及变更前后号码；展示和普通日志使用脱敏号码，原始值受审计权限保护。

## 错误与恢复

| 情况 | 行为 |
| --- | --- |
| 无超管权限 | 403，前后端均限制 |
| 租户已归档、员工已离职/停用或管理员角色已撤销 | 拒绝提交，刷新展示原因；不自动恢复状态 |
| 租户暂停或试用到期 | 超管仍可办理号码纠正；不恢复租户服务访问 |
| 新旧号码相同 | 提示无需变更，不发短信 |
| 新号码已占用其他员工 | 409，不改动双方资料 |
| 旧页面调用发送验证码接口 | 410，提示刷新后直接变更 |
| 员工资料/角色/绑定在操作期间发生变化 | 409，要求刷新并重新确认 |
| 请求超时后使用相同幂等键重试 | 相同业务内容返回原结果；不同内容拒绝，不重复更新或写入审计 |
| 原子提交失败 | 回滚号码、号码保护记录、版本及审计；明确失败，不返回成功 |

后端错误统一经 `error-factory.ts` 包装。UI 显示可操作的中文提示，不暴露认证账号 ID 或数据库原始异常。

## 验收标准

1. 未绑定登录账号的管理员可以纠正初始号码，并使用新号码完成首次后台和小程序手机号登录。
2. 已绑定管理员换号后，档案、角色、历史业务及本人微信身份不变；新号后台登录和小程序身份发现正确。
3. 旧手机号不能登录该员工；换号前签发的后台令牌访问实际业务接口被拒绝，不只检查 `/admin/auth/me`。
4. 其他客户身份、其他租户及平台超管会话不受影响。
5. 多管理员准确选择、角色撤销、号码占用、直接换号无短信、重复提交、并发换号及普通员工编辑并发均有回归覆盖。
6. 数据库 smoke 证明更新、版本递增和审计原子性，失败场景完全回滚。
7. 新增安全快照读取验证查询边界与索引；跨实例不能因权限缓存继续接受旧后台令牌。
8. 先完成类型检查，再执行必要的接口和浏览器验证；发布时核对 migration，应用后验证 Local/Remote 对齐。
