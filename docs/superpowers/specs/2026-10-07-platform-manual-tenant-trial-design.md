# 超管手动建户试用期限设计

**日期：** 2026-10-07

**状态：** 待评审

**范围：** Gooes API、Admin、Domain 与 Supabase migration；不修改 orange 仓库

## 1. 目标与已确认规则

- 超管手动新建租户时可以设置试用天数。表单默认开启 30 天标准试用，也允许选择“暂不开通”。
- 手动创建的租户即使尚未完成企业核验，也可以开始试用。平台主动发放仍需要 `platform.service_trial.manage`、操作人和原因；租户自主申请仍要求已核验企业身份。
- 试用结束后固定进入 7 天只读宽限期；宽限期结束后停止试用访问。有效正式服务或已付款待开通服务仍按现有优先级放行。
- 租户列表展示实际服务访问状态、试用截止时间和宽限期截止时间；超管可以从列表延长试用。不提供缩短期限操作。立即终止沿用现有撤销试用能力。
- 暂不开通的超管新租户不能因为缺少旧订阅记录而得到无限期读写权限。

## 2. 现状与问题

`PlatformTenantService.create` 只调用 `create_tenant_with_default_template` 初始化租户和组织，不创建试用。试用发放 RPC `platform_service_trial_grant` 要求租户关联已审核入驻申请及一致的统一社会信用代码；手动建户没有这项资料，直接调用会报 `SERVICE_TRIAL_ENTERPRISE_IDENTITY_REQUIRED`。

当前服务访问按租户状态、正式合同、已付款待开通、有效试用、旧订阅依次判定。旧订阅状态只要不是 `locked`，包括没有订阅记录的 `null`，就返回无结束时间的 `legacy` 读写模式。因此仅新增试用截止时间字段不能实现到期封禁。试用访问还受 `PLATFORM_SERVICE_TRIAL_ACCESS_ENABLED` 开关控制，默认值为关闭。

超管建户和合作伙伴入驻都使用 `create_tenant_with_default_template`。改变该 RPC 的默认访问行为时必须显式保留合作伙伴现有路径，不能依赖调用人是否为空来猜测来源。

## 3. 方案选择

1. **只在 `tenants` 增加到期时间：不采用。** 会产生第二套与现有试用状态、范围、宽限期及审计不一致的授权规则。
2. **建户后单独调用现有发放接口：不采用。** 未核验身份会被拒绝；建户和发放分成两次提交也会留下建户成功、试用失败的中间状态。
3. **复用现有试用记录和受控命令，扩展平台手动建户来源：采用。** 创建和发放处于同一数据库事务，列表从同一试用与访问事实读取状态。

## 4. 数据和权限边界

新增显式的 `tenants.creation_source` 和 `tenants.service_access_policy`。来源区分历史未知、平台手动、合作伙伴和入驻审批；访问策略只有 `legacy_compatible` 与 `entitlement_required` 两种。历史租户经 migration 标记为旧版兼容访问；新列默认 `entitlement_required`，避免未来新增入口意外获得无限期权限。超管建户写入 `platform_manual` 和 `entitlement_required`；合作伙伴建户明确写入 `partner` 和当前兼容策略，入驻审批建户也显式保留其当前策略。创建来源不可通过普通租户编辑接口修改。不靠 `tenant_billing_subscriptions` 缺行推断。数据库 schema、约束、索引、回填均走 `supabase/migrations/`，不手动修改远端数据库。

试用记录增加身份依据：`verified_enterprise` 或 `provisional_tenant`。原有记录回填为前者，并保留现有企业摘要；后者仅允许 `platform_grant` 来源，企业摘要为空，通过租户 ID 做并发锁及同租户唯一约束。已核验记录的企业去重索引保留为仅针对 `verified_enterprise` 的部分索引；临时试用另建按租户与有效状态的部分唯一索引。租户自主申请仍要求已核验企业身份。平台人员对未核验手动租户单独发放试用时，走相同的受控例外。延长、撤销、状态规范化和归因命令都必须支持两种身份依据；临时身份不伪装为企业统一社会信用代码摘要。试用类型、范围、规则快照、幂等键、版本、审计事件和权限仍复用既有试用机制。

企业后续完成核验时，临时试用保留原始身份依据和审计历史；核验流程通过租户的已核验企业身份检查跨租户重复试用，不把旧记录强行改写成企业身份记录。核验本身不因已承诺试用而失败，也不静默撤销在用试用；发现重复时写入可查询的冲突事实，禁止该企业再次发放，后续由运营按已有撤销或到期规则处理。企业级重复校验必须同时覆盖已核验试用和已完成核验租户下的临时试用，不能仅过滤企业摘要非空的试用记录。任何涉及身份关联和去重索引的调整必须在 migration 中完成。

## 5. 创建和访问流程

超管创建接口接收“是否立即开通试用”和试用天数。默认 30 天；天数遵守当前试用策略上限，具备 `platform.service_trial.override` 权限时才允许规则内的例外。手动建户的宽限期固定为 7 天，表单直接说明只读截止日期。试用开启时，建户 RPC 在同一事务内完成租户、组织、管理员和标准试用发放；任何一步失败都回滚。试用关闭时只创建租户，服务访问为“未开通”。建户响应返回最终租户和试用事实，Admin 不推算服务器时间。

统一访问判定维持“租户停用 > 正式合同 > 已付款待开通 > 有效试用 > 显式旧版兼容资格 > 未开通／到期”的优先级。试用截止时进入 `grace`，只允许读与恢复类请求；7 天后进入 `service_blocked`。已撤销试用立即失效。平台管理和服务购买、申请等恢复接口遵循现有路由访问矩阵。

上述受控访问在试用访问开关启用后才能对用户生效。因此上线顺序必须先验证数据库事实和访问判定，再启用新的建户试用入口；开关关闭时禁止创建会被错误放行或错误阻断的试用租户。

## 6. 租户列表

分页列表按当前页租户 ID 批量取得实际服务状态和当前／最近试用事实，避免逐行 RPC 或 N+1。展示“未开通、试用中、只读宽限期、已到期、正式服务、旧版兼容、已停用”，并显示试用及宽限期截止时间。列表里的“延长试用”只对现有命令允许的 `active`、`grace_period` 状态开放，使用既有 `expected_version`、幂等键、权限、原因和审计；过期或无试用时不显示可执行的延期按钮。列表保留进入试用管理详情的路径以查看完整历史和撤销操作。

## 7. 验证与上线

验证手动新建默认试用、指定天数、暂不开通、建户事务回滚、未核验租户发放、试用截止转只读、宽限期截止阻断、延期后重新计算截止时间、撤销立即失效、已付费优先、旧租户兼容、合作伙伴建户不回归，以及分页列表无 N+1。重点验证数据库时间边界和试用开关状态。数据库迁移应用前确认待执行文件，应用后以 `supabase migration list` 核对 Local/Remote；回滚需提供前向补偿 migration，保留试用及审计历史，不删除已发放记录。

不新增缩短期限、独立免费期表、0 元订单或新缓存与队列。
