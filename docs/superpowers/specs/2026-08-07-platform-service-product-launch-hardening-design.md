# 平台技术服务套餐上线加固设计

## 目标

在不改变支付、订单和商品版本模型的前提下，补齐平台技术服务套餐的运营防误操作，并为 1 年、2 年、3 年套餐提供可直接审核发布的正式服务条款草稿。

## 范围

本阶段只包含：

- Admin 套餐详情中的发布确认和归档确认；
- 发布确认中展示草稿相对已发布版本的关键变化；
- 归档确认中明确小程序购买影响；
- 通过 migration 更新三档正式套餐的草稿服务条款；
- 开发数据库 migration 和 Admin/API 验证。

本阶段不包含：

- 生产数据库 migration 或生产服务发布；
- 微信支付配置调整；
- 小程序接口和页面调整；
- 新增套餐状态、停用/恢复接口或新依赖；
- 自动发布条款草稿。

## 交互设计

### 发布套餐

点击“发布套餐”后先打开确认对话框，不立即请求后端。对话框展示：

- 当前草稿版本和即将生成的发布版本；
- 标价、实付价、折扣和条款版本；
- 草稿相对当前发布版本发生变化的字段；
- “只影响新订单，已有订单继续使用下单快照”的业务提示。

只有点击“确认发布套餐”才调用现有 `POST /platform/billing/service-products/:id/publish`。提交期间按钮显示加载状态且不可重复点击，失败后保留对话框并显示后端错误，成功后关闭确认层并刷新列表。

### 归档套餐

点击“归档套餐”后打开危险操作确认对话框。文案明确：

- 归档后小程序不再展示和销售该套餐；
- 历史订单和已发布版本保留；
- 当前 Admin 没有恢复归档套餐的交互。

只有点击“确认归档套餐”才调用现有归档接口。确认按钮使用 destructive 语义，取消按钮保持可见。

## 数据设计

新增一条 migration，只更新三档正式商品的草稿字段：

- `terms_content`：补齐交付成果、客户配合、响应时间、不包含事项、验收、整改、退款、服务期起算和续费规则；
- `terms_version`：仅在条款内容确实变化时递增；
- `version`：仅在条款内容确实变化时递增；
- `updated_at`：记录更新时间。

migration 不修改 `published_version_id`，不插入发布版本，不操作一分钱开发测试商品。运营人员必须在 Admin 核对草稿后主动发布，发布接口继续生成不可变版本并记录发布人。

## 错误和并发

- 继续使用 `expected_version` 乐观锁和 UUID 幂等键；
- 确认对话框打开后若后台版本已变化，由后端返回版本冲突，前端展示错误并要求刷新；
- 关闭确认对话框时清理局部错误，不影响详情弹窗；
- 发布或归档进行中禁止关闭确认层和重复提交。

## 验证

- Admin 源码测试先验证确认层、变更摘要、影响提示和 destructive 操作；
- Admin 类型检查和文件体积检查；
- API 套餐、订单快照和路由测试保持通过；
- migration dry-run 后应用到开发数据库；
- `supabase migration list` 确认 Local/Remote 对齐；
- 只读查询确认三档套餐草稿条款版本递增、已发布指针未被 migration 改动；
- 开发 Admin 人工验证确认层、取消、加载、成功和失败状态。

## 上线边界

本阶段完成只代表开发环境具备生产候选条件。生产 Admin 路由、生产三档商品状态、普通支付配置和正式开售仍按独立生产发布门禁验收。
