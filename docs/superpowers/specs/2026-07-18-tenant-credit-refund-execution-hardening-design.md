# 租户积分充值退款执行加固设计

## 背景

租户积分充值退款已具备申请、审核、微信退款执行和回调反向积分流水。
在真实退款联调前，需要对齐微信支付 APIv3 普通商户退款规范：退款原因最多
80 个 UTF-8 字节，执行退款前应主动确认原订单支付成功，退款请求结果不确定时
必须沿用原商户退款单号查询状态，不能直接判定失败后换号重试。

## 范围

本次只修改 gooes 后端并在本机验证，不 push，不部署，也不修改
orange。自动化验证默认只使用 mock；在用户明确授权后，额外通过本机
API `:3000` 和 Admin `:3010` 对一笔 ¥1.01 的已审核申请执行一次
真实微信退款 smoke。

## 设计

1. 业务退款原因仍允许保存 500 个字符，用于审核和审计；发送微信前按 UTF-8
   字节边界截断到 80 字节，避免截断多字节字符。
2. 微信支付网关新增按 `out_refund_no` 查询退款能力，固定使用普通商户 APIv3
   `GET /v3/refund/domestic/refunds/{out_refund_no}`。
3. 平台执行退款前，先按 `out_trade_no` 查询微信订单，要求：
   `trade_state=SUCCESS`、`transaction_id` 与本地一致、`amount.total` 与本地
   已支付金额一致。任一不一致均在本地状态变更前拒绝执行。
4. 申请退款调用失败后，立即用相同 `out_refund_no` 查询退款：
   - 查询到退款单：保存微信退款单号和状态，保持 `refunding`，等待回调确认终态；
   - 明确返回 `RESOURCE_NOT_EXISTS`：按原有逻辑标记 `failed`；
   - 查询结果仍不确定：保持 `refunding` 并返回稳定错误码，避免不安全重试。
5. 微信 `SUCCESS` 回调仍是扣减积分、写反向流水和更新 `refunded` 的唯一入口。

## 验证

使用 Bun 单测覆盖 UTF-8 截断、退款查询、支付状态/交易号/金额校验、请求失败后的
查退款分支，再运行 API typecheck 与 build。授权后的本机真实退款结果为：
微信 `REFUND.SUCCESS` 回调签名有效且已处理，申请和订单均进入 `refunded`，
反向流水唯一扣回 1 积分，可用余额从 1008 变为 1007。
