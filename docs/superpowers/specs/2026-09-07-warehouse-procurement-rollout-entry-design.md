# 仓库采购平台开关入口补充设计

状态：用户于 2026-09-08 确认设计；本地实现及审查通过。后续已获授权合并 main、完成开发迁移/部署及分支清理；租户开关仍关闭，未发布生产。

实现证据：`../../operations/evidence/2026-09-08-warehouse-procurement-rollout-entry.md`。

开发发布证据：`../../operations/evidence/2026-09-08-warehouse-rollout-main-dev-release.md`。

## 目标与根因

Stage B 开发联调指定租户已具备默认仓库，但 `warehouse_procurement_enabled=false`。
该列和依赖约束已经存在；平台设置的严格 HTTP schema、service、repository RPC 参数及
Admin 供应商模块卡片均未接入它。现有租户接口不能修改此开关，租户管理员也不能代替平台身份。

补齐正式入口，使有既有 `platform.supplier.manage` 权限的平台人员能按租户开启或关闭仓库采购，
不手工 UPDATE、不给租户管理员增加平台权限、不自动开启任何租户。

## 方案选择

推荐扩展现有平台租户供应商设置卡片及 `PATCH /platform/tenant-supplier-settings/:tenantId`，
复用既有版本号、幂等命令、依赖检查和审计。相较单独新建设置页面/API，改动范围更小，运营只维护一处。
一次性的开发库初始化 migration 虽可开启指定租户，但不能形成后续运营入口，因此不采用。

## 行为与权限

- 在采购批次 Workflow 后增加“仓库采购”开关，默认关闭；无平台管理权限只读展示。
- 沿用逐级开启、逆序关闭规则。开启仓库采购要求模块、采购快照和批次 Workflow 已开启，
  并满足这些父开关原有的依赖链；仓库采购未关闭前不能关闭父开关。
- 关闭只停止新仓库采购入口及既有受此开关保护的业务动作，不删除库存/单据/审计，
  不增加对既有应付、付款结算的阻断；具体业务门禁沿用 Stage B 已验证契约。
- 不新建权限，不修改平台身份校验、租户数据范围、审批人或员工角色。
- 更新前后状态、操作者、目标租户、原因和版本进入现有命令事件/平台审计。

## API、数据库与旧版本兼容

- HTTP 新字段为 `warehouse_procurement_enabled`，新 Admin 显式提交布尔值。
- 旧客户端省略字段必须保留当前值，不能默认成 false 而意外关闭已经启用的仓库采购。
- 扩展现有 controller → service → repository → RPC 链路；各读取 DTO、必要字段 select、
  前后状态映射均包含真实开关值，缺失历史回执按旧版本兼容规则处理。
- 通过新增 `supabase/migrations/` 文件扩展原子命令；不得修改已有 13 份待升级 migration。
  沿用数据库先兼容、再发布 API/Admin 的顺序，保留仍在服务的旧签名调用及旧命令重放。
- 新旧调用都必须保持 actor/key、原始 payload 指纹、版本冲突及单次版本递增语义；
  旧调用不允许越过依赖约束。禁止为了兼容修改历史命令事件或业务开关存量。
- RPC 权限仍仅 service_role，固定安全 search_path；不向 anon/authenticated 开放执行。
- 新 migration 不包含自动启用租户的初始化数据。新增 migration 的远端应用须单独核对清单；
  用户此前批准的 13 条升级不应被描述为已经包含本补充项。

## 交互与失败恢复

复用现有 Switch、状态提示、原因输入和加载/错误区域，不新增页面或通用状态框架。
显示依赖未满足、无管理权限、保存中及版本冲突的明确原因。
同一未确认请求重试使用原版本、payload 和幂等键；读取最新配置不等于确认该命令失败，
不能把同一个 key 与刷新后的新 payload 混用。明确冲突后由操作者重新确认新意图。
成功回执已确认而后续读取失败时只重新读取，不重复写入。

## 验收

1. API schema/repository/service：新布尔字段往返、旧省略保留、平台权限与租户身份拒绝、
   依赖顺序、版本冲突、审计前后值、幂等重放与异载荷冲突。
2. 隔离数据库：真实新旧 RPC、旧历史命令重放、并发版本控制、执行 ACL、默认关闭、
   无存量开关或事实变化；新增 migration 失败可事务回滚。
3. Admin：读写权限、依赖禁用、启用/关闭、失败恢复及桌面/375px；先静态检查，再浏览器验证。
4. 在完成规格/质量审查后提交候选；开发应用前后执行 migration list/dry-run，记录源码版本。
5. 获授权的平台操作人通过正式接口开启指定开发租户后，再由合法独立审批身份完成新单据验收。
   不操作该租户已有应付，不使用未获授权的其他员工登录。

## 恢复与范围外事项

关闭开关通过正式命令，保留数据；数据库修正采用受审前向 migration，不覆盖已发生的业务事实。
本设计不授权生产发布、生产开关、员工加权、代登录或其他租户测试；不修改 Orange。
开发环境独立付款审批员工已在后续授权记录中落实；采购工作流身份及完整验收仍需分别核对。
入口实现不代表真实联调已经通过。实施计划见 `../plans/2026-09-08-warehouse-procurement-rollout-entry.md`。
