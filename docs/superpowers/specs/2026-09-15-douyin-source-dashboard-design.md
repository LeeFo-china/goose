# 抖音小程序站内流量来源看板设计

## 目标与范围

在河南晴天等租户后台的抖音小程序栏目展示本租户的小程序入口、站内浏览、量房意向和成功预约，按来源类型、抖音账号、视频、直播间及手工链接标记拆分。这里统计的是**进入小程序之后**的事件，不包含抖音视频播放、曝光及抖音开放平台数据中心的官方渠道总量；这些数据须单独申请数据分析权限并接入。看板不用于员工分佣结算。

同一批次补齐线索详情“本次留资来源”的创建时间，使用与来源快照关联的最新量房预约 `created_at`；无预约的历史线索使用线索 `created_at` 并标明时间含义。现有 API 已返回这两个时间，无需数据库新列。

## 采集与统计口径

当前 `app_launch` 在 `tt.getAnalysisInfo` 异步返回前记录，且外部再次进入不会记录新启动事件，因此历史 `direct` 不可直接用于来源排行。新模板在每次确定为外部进入时等候现有有界官方归因读取，再记录一次入口事件；内部页面切换不会增加入口次数。官方结果缺失时归入“未识别”，有 `campaign_code` 或 `content_id` 而无官方结果时归入“链接参数（手工标记）”。官方结果始终优先。

新客户端事件带固定口径版本。服务器产生的预约成功事件只在同租户、同主体、同内容来源的新版入口之后 24 小时内计入看板；先用视频／直播内容匹配，再允许切换到账号汇总，保证总预约数不随分组方式变化。旧事件不回填，旧 `direct` 不合并进新口径；页面显示首次有新口径事件的时间和旧数据不参与来源统计的说明。事件仍使用现有 `marketing_events`、预约 `source_snapshot` 和租户隔离模式。

选择近 7、30 或 90 天，按北京时间自然日统计。入口次数是入口事件数；访问人数是入口事件中去重的主体散列数；浏览、量房按钮点击是各自事件次数；成功预约按不同预约 ID 去重。来源行显示这些独立阶段的次数和人数；“每百次进入的预约数”是效率指标，不称为同一次访问的精确转化率。没有足够入口样本时显示“样本不足”，不制造百分比。服务端限制日期窗口不超过 90 天，来源排行必须分页，默认 20 条、最多 100 条。

## 数据与权限

API 通过 controller 校验日期和分页参数，再调用 service 鉴权、repository 只读聚合 RPC。聚合按 `tenant_id`、`source='douyin_miniapp'`、口径版本和有界日期过滤，仅返回计数、日期和受限的官方来源标识；不返回手机号、主体散列、客户家庭照片或原始事件载荷。现有抖音事件索引用于限定扫描，migration 中创建或调整聚合函数；如执行计划显示大表范围扫描，再在 migration 中加有针对性的索引。

租户后台沿用现有抖音小程序菜单及 `douyin_miniapp.read` 权限，不允许跨租户或平台模式默认旁路。页面使用现有 shadcn/ui 组件：时间筛选、总览指标、每日趋势、来源类型汇总和分页来源表。空数据、加载和失败状态都明确说明原因。官方来源账号和视频／直播标识只在有官方返回值时显示。

## 验证与发布

先验证新客户端入口事件等候、外部再次进入、失败兜底和旧数据隔离，再验证 API 严格校验、租户权限、分页和 SQL 聚合结果。迁移先应用并用 `supabase migration list` 确认，再发布 API/Admin，最后上传新抖音体验版；旧模板数据不会进入新口径看板。真实短视频、直播、主页与直接入口的真机验收仍需要绑定账号和 2.99.0 以上基础库，不能由模拟数据代替。
