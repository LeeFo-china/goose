# 微信支付开通申请单页重构设计

> 日期：2026-07-24
> 状态：已确认，待实现
> 范围：租户 Admin 微信支付开通申请
> 设计系统：Gooes Admin + shadcn/ui
> 取代范围：`2026-07-23-wechat-pay-applyment-ocr-first-ux-design.md` 中的四阶段向导信息架构

## 1. 背景

现有页面已经具备证照上传、私有预览、自动 OCR、人工修正、草稿自动保存、附件保存重试、
提交阻断和审核提交能力，但这些能力被拆分到“上传资料、核对识别、补充信息、确认提交”
四个阶段中。

用户上传证照后，需要切换到另一个阶段才能查看识别字段；补充资料和最终复核又重复展示
相同信息。页面右侧的“处理记录”占用固定空间，却不能帮助用户完成当前申请。这种结构
增加了往返操作和认知负担，也削弱了“上传即识别、识别即核对”的价值。

## 2. 目标

1. 在一个连续页面内完成资料上传、OCR 核对、业务补充和提交。
2. 每张证照与其识别字段保持在同一个视觉上下文中。
3. 身份证正反面作为一个资料组展示，便于核对完整身份信息。
4. 删除不能直接帮助完成申请的导航、进度和处理记录。
5. 保留现有数据契约、权限、草稿、OCR、附件版本和提交校验能力。
6. 桌面端清晰紧凑，移动端按自然阅读顺序自动堆叠，不出现横向溢出。

## 3. 非目标

- 不修改微信支付进件字段、必填规则、审核规则和后端接口。
- 不重新设计 OCR 服务、附件存储或敏感信息加密。
- 不新增前端依赖。
- 不修改平台超管审核页。
- 不修改小程序仓库。
- 不在本次新增数据库 migration。

## 4. 设计原则

该页面是低频、高信任的受监管资料采集页，采用克制、明确的后台表单语言：

- `DESIGN_VARIANCE: 3`
- `MOTION_INTENSITY: 2`
- `VISUAL_DENSITY: 5`

页面遵循 Gooes Admin 的既有颜色、字体和间距。圆角不超过 8px，不使用渐变、营销式大字、
装饰插图或卡片套卡片。颜色只表达状态、警告和主操作。

## 5. 单页信息架构

页面按业务资料的自然顺序连续展示：

1. 申请身份
2. 营业执照
3. 法人身份证
4. 经办人身份证，仅在超级管理员不是法人时显示
5. 联系信息
6. 结算账户
7. 经营资料
8. 提交确认

取消以下界面：

- 四阶段按钮和进度条
- 上一步、下一步和阶段计数
- 独立的 OCR 核对阶段
- 独立的完整复核阶段
- 右侧处理记录

页面顶部继续显示申请状态、保存状态和全局错误。表单主体使用单一主列容器，各业务区使用
标题、简短说明和 `Separator` 分隔，不把每个区都包装成独立浮动卡片。

## 6. 资料区设计

### 6.1 申请身份

页面最前方保留两个决定资料范围的 `Select`：

- 主体类型
- 超级管理员身份

选择改变后立即更新资料要求。现有草稿保存和联系人资料增删规则保持不变。

OCR 授权放在首次证照上传前的紧凑提示区中。OCR 不可用时显示 `Alert`，说明附件仍可保存，
字段可以手工填写。

### 6.2 营业执照

营业执照区由两部分组成：

- 上传、缩略图预览、替换、删除、保存重试和识别状态
- 紧接在下方的营业执照识别字段

识别字段包括主体名称、统一社会信用代码、注册地址、营业期限和法人姓名。上传完成后，
识别状态与字段原地更新。用户不需要进入其他页面或选择证照类别。

OCR 建议值与已保存值冲突时，继续使用现有逐字段选择和确认机制，不静默覆盖人工值。

### 6.3 法人身份证

身份证人像面和国徽面在桌面端同一行展示，宽度相等；窄屏按人像面、国徽面的顺序堆叠。

两张证照下方统一展示该身份证组的识别字段：

- 姓名
- 身份证号码
- 居住地址
- 有效期开始
- 有效期结束

两面识别、字段核对和手动填写仍使用现有资料状态。任何一面替换后，只更新对应附件版本，
并按现有冲突规则重新核对。

### 6.4 经办人身份证

仅当超级管理员身份为经办人时显示，结构与法人身份证一致。切回法人本人时沿用现有数据
处理规则，不在视图层自行删除后端仍需保留的数据。

### 6.5 结算账户证明与经营场景

结算账户证明放在结算账户字段之前，上传后在同一区域展示可识别的银行卡号和开户银行。
经营场景材料放在经营资料区末尾，保留最多五张、私有预览和附件保存状态。

## 7. 表单信息分组

原“补充信息”字段按业务含义拆分，不再作为一个独立阶段：

### 7.1 联系信息

- 商户简称
- 超级管理员手机号
- 超级管理员邮箱
- 客服电话

### 7.2 结算账户

- 结算账户类型
- 结算账户开户名
- 银行账号
- 开户银行全称
- 开户银行联行号
- 经营行业与结算规则

### 7.3 经营资料

- 经营场景说明
- 经营联系地址
- 经营场景材料
- 备注

字段继续使用现有 `Field`、`FieldGroup`、`Input`、`Select` 和 `Textarea` 组件。必填与选填
标识保持明确，不把技术 ID 暴露给租户。

## 8. 提交区

不再重复展示一整套只读资料摘要。用户已经在每个资料区原地完成核对，页面底部只保留：

- 后端 `submission_readiness.blockers` 缺失项列表
- 必传附件完成数量
- “确认资料真实有效”复选框
- 自动保存状态和最后保存时间
- “保存申请”按钮
- “提交平台审核”主按钮

缺失项可以定位并滚动到对应资料区或字段。提交前继续执行现有完整表单校验、草稿 flush 和
确认弹窗，不允许绕过后端 readiness。

## 9. 状态与异常

### 9.1 OCR 状态

每个资料组就地展示：

`未上传 / 已上传 / 识别中 / 待核对 / 已确认 / 手动填写 / 识别失败`

识别失败时提供“重试识别”和“手动填写”，不会阻止附件本身保存。

### 9.2 保存状态

页面顶部或底部稳定展示：

`保存中 / 已自动保存 / 保存失败`

保存失败保留当前编辑值并提供重试。附件保存失败继续显示在对应附件附近。

### 9.3 只读状态

申请提交后，页面保持同一信息架构，只禁用编辑、上传、替换和提交操作。用户仍可查看证照、
字段和当前审核状态，不切换到另一套详情页。

## 10. 组件边界

实施时优先复用现有业务逻辑，调整展示组合：

- 保留 `useWechatPayApplymentMaterials`
- 保留 `useWechatPayApplymentOcrReview`
- 保留 `useWechatPayApplymentAutosave`
- 保留附件 checkpoint、重试、预览和 OCR 冲突合并逻辑
- 新增单页资料区编排组件
- 将 OCR 核对能力改为按资料类别直接渲染，不再依赖类别 `Select`
- 将补充字段组件拆成联系、结算和经营三个视觉分组
- 将现有 review 缩减为底部提交 readiness 和确认区
- 从 `FinanceWechatPayApplymentPanel` 删除事件列表布局
- 逐步移除只服务于四阶段导航的组件和测试

不得复制现有上传或 OCR 状态逻辑形成第二套实现。

## 11. shadcn 组件映射

| 表单和字段分组 | `Field`、`FieldGroup` |
| 主体和身份选择 | `Select` |

## 12. 验收标准

1. 页面不存在四阶段按钮、进度条、上一步、下一步和阶段计数。
2. 页面不存在“处理记录”区域。
3. 营业执照上传区后直接显示营业执照字段。
4. 法人身份证正反面在桌面同一行，字段紧接在两张证照下方。
5. 经办人身份证只在对应身份选择下显示。
6. 结算账户证明与结算字段处于同一业务区。
7. OCR 上传、识别、确认、失败重试和手动填写行为保持可用。
8. 自动保存、附件 checkpoint、提交前 flush 和 readiness 阻断保持可用。
9. 草稿、已提交和无编辑权限三种状态均可正常展示。
10. 360px、768px、1280px 视口下无横向溢出、内容遮挡和按钮文字截断。
11. 相关单元测试、Admin 静态检查和浏览器 smoke 通过。
