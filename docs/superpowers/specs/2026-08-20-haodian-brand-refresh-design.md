# 好店智装云品牌迁移与 Admin 去渐变设计

**日期：** 2026-08-20
**状态：** 已确认，待实施计划
**范围：** Gooes 仓库的用户可见平台品牌；Admin 租户后台与平台超管后台去渐变

## 1. 背景与现状

平台当前对外品牌为“鹅班长”，品牌名称、Logo 和黄黑视觉分散在 Admin、独立官网、
API 运行时兜底、测试和文档中。基于 `origin/main` 的只读盘点结果：

- 精确文本“鹅班长”分布在 29 个文件、60 处；
- Admin 和 Web 各自维护静态 `logo.png`，Admin 另有 `app/icon.png`；
- API 在 `branding-default-logo.ts` 内嵌旧品牌的 256 × 256 Base64 兜底 Logo；
- API 的平台兜底显示名当前为“字节跳动”，与实际平台品牌也不一致；
- 平台品牌还可以通过现有品牌管理功能保存并发布到数据库，租户在权益有效时可以覆盖
  平台品牌；
- Admin 默认使用黄黑暖色工作台，登录页和工作台外壳存在装饰性渐变；
- H5 和抖音小程序也有用于图片可读性的渐变遮罩，但已明确不纳入去渐变范围。

新品牌资产是用户提供的“好店智装云 / HAODIAN DATA”方形 PNG，尺寸 1254 × 1254，
约 0.90 MB，无透明通道。该文件符合现有品牌 Logo 上传策略的格式、尺寸、宽高比和
2 MB 大小限制，但完整文字锁定稿不适合直接缩小为 28～32px 导航图标或浏览器图标。

## 2. 已确认决策

1. 平台用户可见品牌由“鹅班长”统一迁移为“好店智装云”。
2. 品牌名称、静态 Logo、应用图标、SEO、分享图、结构化数据和 API 兜底品牌在同一
   个 PR 中完成。
3. Admin 默认品牌视觉由黄黑调整为深蓝主色、橙色点缀和中性表面。
4. Admin 租户后台与平台超管后台取消所有实际渲染的渐变；登录页和共用工作台外壳
   使用纯色。
5. H5 和抖音小程序的渐变不改，包括图片可读性遮罩。
6. 租户已发布的私有品牌名称和 Logo 不被覆盖，平台品牌仍只作为默认和回退来源。
7. `gooes`、`@gooes/*`、`GOOES_*`、域名、容器名和数据库标识等技术名称不改。
8. 仓库代码和资产放在一个 PR 中，以多个小提交组织；不拆成多个 PR。
9. 不引入新依赖，不绕过 Git hooks，不使用 `--no-verify`。

## 3. 目标

- Admin、官网、分享内容和运行时回退不再向用户展示旧平台品牌。
- 新 Logo 在大图、导航、favicon 和应用图标中都保持可辨识，不把完整文字稿机械压缩
  到小尺寸。
- Admin 租户后台和平台超管后台形成一致、克制、无渐变的中后台视觉。
- 平台品牌切换不破坏租户私有品牌、品牌权益和现有发布流程。
- 品牌迁移具备可验证的代码、视觉、运行时和运营检查清单。

## 4. 非目标

- 不重命名仓库、包、环境变量、Cookie、容器、数据库对象或部署服务。
- 不修改 H5、抖音小程序的页面视觉、渐变、布局或租户内容展示逻辑。
- 不重构与品牌迁移无关的 Admin 页面、业务流程或 API 架构。
- 不改变品牌权益、租户覆盖优先级、权限或 RLS。
- 不手工修改远端数据库，不为现有平台品牌发布新增 migration。
- 不修改只读的 `orange` 仓库。
- 不伪造或重绘新的品牌造型；小尺寸图标必须来自用户确认的原始品牌图形。

## 5. 方案选择

### 方案 A：完整品牌迁移与 Admin 纯色化

统一处理用户可见名称、分尺寸资产、SEO、运行时兜底和测试，同时将 Admin 默认品牌色
调整为蓝橙，并只在 Admin 删除渐变。代码合并后使用现有平台品牌管理流程发布运行时
品牌。

优点是品牌链路完整、视觉一致、回归范围明确；缺点是 PR 涉及多个应用，需要按应用
分组验证。

### 方案 B：机械替换文字和三张图片

改动最快，但会遗漏 API 内置兜底、数据库已发布品牌、Open Graph、结构化数据和小尺寸
图标适配；黄黑 Admin 也会与蓝橙 Logo 冲突。

### 方案 C：拆分品牌、视觉和运行时 PR

单个 PR 更小，但中间版本会出现新旧品牌混用，也不符合本次一次完成仓库改造的要求。

**决定：采用方案 A，并以一个 PR、多个可独立审查的提交完成。**

## 6. 品牌边界与命名

### 6.1 用户可见平台品牌

以下语义统一使用“好店智装云”：

- Admin 页面标题、登录页、工作台、公开合伙人页和图片替代文本；
- Web 页头页脚、营销文案、Metadata、Open Graph、Twitter 和 JSON-LD；
- 平台兜底显示名、平台兜底 Logo 和相关测试断言；
- 仍然有效的品牌资产说明和操作文档；
- 对外编辑部、官网、城市合伙人等带品牌前缀的称谓。

抖音开放平台当前实际应用或模板若仍名为“鹅班长装企管家”，目标名称为
“好店智装云装企管家”。仓库中的契约样例可以改为目标名称，但第三方平台真实改名
必须作为部署后的独立运营动作执行和验收。

### 6.2 技术标识

以下名称保持不变：

- Git 仓库和目录 `gooes`；
- 包作用域 `@gooes/*`；
- 环境变量 `GOOES_*`；
- `goodcms.cn` 及现有子域名；
- Docker 服务名、Cookie 名、数据库对象名和历史 migration 名。

这些标识不直接面向最终用户，机械重命名会扩大部署和兼容风险，且不能提升品牌体验。

### 6.3 历史文档

当前仍指导实现或运营的品牌文档更新为新品牌。带日期的历史证据、既有架构决策和已完成
计划不为满足全文零匹配而改写事实；如该文档仍被引用，则在相关位置标注“原鹅班长品牌”
或补充迁移说明。验收标准是用户可见运行界面和当前有效规范不再使用旧品牌，不要求历史
证据全文零出现。

## 7. 品牌资产设计

### 7.1 资产角色

从用户提供的同一品牌稿准备两种视觉角色：

1. **完整品牌锁定稿**：`HD + 鹅 + 好店智装云 + HAODIAN DATA`，用于登录页等有足够
   空间的品牌展示和平台品牌资料。
2. **品牌图标**：只保留 `HD + 鹅` 图形，用于 28～48px 导航、Admin App Icon、Web
   favicon 和 API 256 × 256 兜底快照。

图标不得把完整中英文文字压缩到小尺寸。原图无透明通道，因此白底版本必须放在明确的
白色或中性图标容器中；若后续提供官方透明 SVG/PNG，应优先替换为官方源文件。

### 7.2 仓库落点

- `apps/admin/public/logo.png`：Admin 品牌展示资产；
- `apps/admin/app/icon.png`：Admin 小尺寸应用图标；
- `apps/web/public/logo.png`：官网导航品牌图标；
- `apps/web/app/icon.png`：新增官网 favicon/App Router 图标；
- `apps/api/src/services/branding-default-logo.ts`：更新受控 256 × 256 兜底快照、来源说明、
  尺寸和 SHA-256。

不从 `orange` 复制或修改资产。新兜底快照的来源必须指向 Gooes 仓库内受控资产或本次
用户提供的确认源，并在注释中记录哈希，保证回退资产可追溯。

### 7.3 页面使用规则

- 28～48px 位置只使用品牌图标，并由邻近可见文字表达“好店智装云”；
- 大尺寸品牌区可使用完整品牌锁定稿，但避免图片内品牌名与页面文字重复两次；
- 图片 `alt` 描述品牌，不用空替代文本隐藏有意义的品牌标识；
- Open Graph 使用 1200 × 630 动态分享图，采用实体深蓝、白色和少量橙色，不使用
  渐变文字或装饰性渐变。

## 8. Admin 纯色视觉设计

### 8.1 适用范围

Admin 租户员工和平台员工共用登录页与工作台外壳，因此统一处理：

- `.console-grid` 登录背景；
- `.goose-workbench-bg` Console 工作台背景；
- 登录表单主按钮；
- 默认 Admin 品牌 Token 和品牌 Logo 容器。

H5 `styles.css` 和抖音小程序 `hero-banner` 的渐变保持原状。Web 当前没有实际渲染的
渐变，不为本需求新增渐变。

### 8.2 色彩角色

- **品牌主色：** 从 Logo 深蓝提取并固化为语义 `primary`/品牌角色；
- **品牌点缀：** Logo 鹅嘴橙色，仅用于焦点、少量强调和品牌细节；
- **表面：** 中性白和低色度浅灰蓝，承载页面、侧栏和卡片；
- **文字：** 深色中性文本，确保正文至少满足 WCAG AA；
- **状态：** 成功、警告、错误继续使用独立语义色，不用品牌蓝橙替代业务状态。

为控制改动范围，现有 `--goose-*` 内部 CSS 变量名可以暂时保留并更新默认值；它们属于
技术标识，不向用户展示。不得在组件中新增散落的品牌十六进制颜色，优先使用语义 Token。

### 8.3 去渐变规则

- `.console-grid` 改为单一中性背景色；
- `.goose-workbench-bg` 改为单一工作台背景色；
- 登录按钮改为纯深蓝背景，Hover/Active 使用同色阶实体色；
- 不以阴影、发光圆斑或多层半透明背景模拟渐变；
- 页面层级使用实体表面、边框、间距和小范围结构性阴影表达；
- 现有测试中的“不得包含 `bg-gradient`”约束保留，并增加覆盖 Admin 全局背景与登录按钮
  的回归契约。

Admin 的租户模式和平台超管模式不得各自维护一套背景或按钮样式，差异只通过权限、导航
和业务内容表达。

## 9. 运行时平台品牌与租户隔离

品牌有效值保持现有优先级：

```text
权益有效且租户品牌已发布
        -> 租户私有 display_name / logo
否则
        -> 已发布的平台品牌
否则
        -> 代码内置“好店智装云”名称 / 受控兜底 Logo
```

实施要求：

- 将 `PLATFORM_FALLBACK_DISPLAY_NAME` 改为“好店智装云”；
- 替换 `CONTROLLED_FALLBACK_LOGO_URL` 和对应完整性说明；
- 不批量更新租户 `brand_profiles`，不改变租户权益判断；
- 不通过 SQL 或 Supabase 控制台直接更新平台品牌；
- 代码部署后，由具备 `platform.branding.manage` 的平台人员在现有 Admin 页面上传新 Logo、
  保存草稿并执行发布；
- 发布后通过 `GET /branding/effective` 分别验证匿名/平台回退、无品牌权益租户和有私有品牌
  租户。

本次不改变数据库结构、索引、RLS、函数或初始化数据，因此不新增 migration。若实施期间
发现必须修改数据库默认数据，必须停止并另行设计 migration，不得扩大本 PR 隐式修库。

## 10. SEO、分享与内容一致性

Web 需要同步更新：

- 根布局和页面 Metadata；
- `applicationName`、Open Graph、Twitter 和图片 `alt`；
- 动态 `opengraph-image.tsx` 中的品牌名称和颜色；
- JSON-LD 的 Organization `publisher`/`provider`；
- 页头、页脚、移动导航和营销页面文案；
- 对应内容渲染、预览、分享和设计系统契约测试。

品牌迁移不更改公开 URL、Canonical、ICP 备案、业务 CTA、表单字段和埋点标识。搜索引擎
可能短期保留旧缓存，发布后应主动检查首页源代码、分享卡片和主流搜索抓取结果。

## 11. 测试与验收

### 11.1 静态检查

- 对 Admin/Web/API 当前用户可见源码扫描旧品牌名称；
- 明确排除历史证据、历史计划和解释旧品牌迁移的文档；
- Admin 实际样式中不得存在 `linear-gradient`、`radial-gradient`、`conic-gradient`、
  `bg-gradient-*`；负向测试断言中的字符串不计为实际样式；
- H5 和抖音小程序渐变文件必须保持无改动；
- 所有 TS/TSX 文件不超过 500 行，Git hooks 全部正常执行。

### 11.2 自动化验证

- 运行稳定工作区测试 `bun run test`；
- 运行 `bun run admin:check`、`bun run web:check`、`bun run api:check`；
- 运行文件大小检查；
- 更新并运行 Admin 品牌/布局契约、Admin E2E 品牌断言、Web SEO/分享契约、API 有效品牌
  单元测试；
- 不因本次改动跳过 pre-commit 或 CI 检查。

### 11.3 视觉 Smoke

至少检查以下桌面和移动尺寸：

- Admin 登录页；
- 租户 Admin 展开/收起侧栏；
- 平台超管展开/收起侧栏；
- 官网首页页头、页脚和分享图；
- 16/32/48px 浏览器与导航图标清晰度；
- 浅色和深色官网中的白底 Logo 边界；
- 焦点、Hover、Disabled、成功、警告和错误状态的对比度。

验收时确认 Admin 页面无渐变，但 H5 和抖音小程序原有渐变仍存在且文件未被改动。

### 11.4 运行时验收

部署并发布平台品牌后验证：

1. 未配置平台资料时，代码兜底名称和 Logo 为“好店智装云”；
2. 已发布平台资料时，匿名或无租户覆盖场景返回新平台品牌；
3. 没有私有品牌权益的租户使用新平台品牌；
4. 已发布私有品牌且权益有效的租户继续显示自己的名称和 Logo；
5. 权益失效后回退到新平台品牌，不回退到旧品牌；
6. Admin 租户和平台超管登录、导航和退出流程不受影响。

## 12. 提交、发布与回滚

### 12.1 单 PR 组织

一个 PR 内按可审查边界组织小提交：

1. 设计和品牌资产；
2. Admin 名称、纯色 Token、图标和测试；
3. Web 名称、SEO、分享图、图标和测试；
4. API 兜底品牌、契约测试和当前有效文档；
5. 最终验证修正。

每个提交只暂存本步骤文件，不纳入其他工作区或用户未跟踪文件。

### 12.2 发布顺序

1. 合并 PR 并完成 API、Admin、Web 正常部署；
2. 平台超管通过品牌管理上传并发布新品牌；
3. 验证有效品牌接口和租户覆盖边界；
4. 提交抖音开放平台应用/模板改名并等待平台审核；
5. 检查官网 SEO、分享图和浏览器图标缓存。

### 12.3 回滚

- 代码或视觉异常：回滚该 PR，恢复旧静态资产和代码兜底；
- 平台品牌发布异常：通过现有平台品牌管理重新发布上一版本，不手工改库；
- 租户私有品牌异常：停止平台发布验收并核查有效品牌优先级，不批量覆盖租户数据；
- 第三方应用改名异常：在抖音开放平台撤回或重新提交名称，不以代码夹带平台状态假设。

回滚不涉及数据库 schema，因为本次不包含 migration。
