## 核查结果与优先级

### P1：缩略图 src 随预览刷新变化

- `ProjectLogCommunication/useProjectLogCommunication.ts`：IntersectionObserver 更新visible；visible变化导致取消/重建预览订阅。receive 在折叠状态直接以 `preview.recent_comments` 替换列表，图片使用 `attachment.url` 为src。
- `previewBatch.ts`：最后一个订阅取消时删除batch；重新进入视口创建batch，其nextAt=0。因而“15秒轮询”不等于“滚动重新进入仍至少15秒”，单个日志或最后一个可见日志反复出入时会重新立即查询。
- 后端serializer每次序列化调用 `signAttachments`，COS短链以当次时间签发。对截图同一附件连续两次真实生产预览，file_id不变、url变化。证据见 `../operations/evidence/2026-10-11-project-log-comment-v2-ui/readcheck.json`，未输出短链或凭证。
- 图片key当前已是file_id，单纯改key或加memo无法阻止src变化导致重新加载。没有真机加载事件追踪，尚不能排除父组件重挂载等额外因素。

修复要求：

1. 以当前会话/租户/身份/项目/日志/file_id为范围，在组件或页面内存保留显示用url与expires_at。同一附件仍有效且距离过期有足够余量时继续用当前src，不能每次预览响应都替换。归属校验成功的新响应可更新其他字段。
2. 临近过期、首次加载或一次图片加载失败时，使用已经鉴权的新响应/专用链接接口更新；失败重签每文件最多一次进行中请求，禁止onError循环。保留真实expires_at，不伪造延期、不删除签名参数、不改公共URL。
3. 无实际字段变化时不重建整份显示列表。图片使用稳定file_id为key并保留固定尺寸。新图准备好前保留旧图或尺寸占位，不先把src置空。
4. 页面内调度器在短暂不可见时停止请求，但保留下一次可请求时间；重新进入遵守15秒间隔。退出页面/切换会话时完整释放，不能跨身份共享图片缓存。恢复前台/主动刷新策略需明确，不能每行重新订阅都刷新整个项目。
5. 403/401/410立即清除当前内容和URL，签名短链显示缓存不替代服务端权限检查。
6. 真机临时记录file_id、src是否变化、onLoad/onError次数及mount/unmount次数，不记录完整签名URL；上下滑动20次、跨一次轮询和5分钟过期刷新后确认，不以开发者工具静态截图判定修复。

## 布局与键盘方案

设计判断：这是员工和客户的移动项目沟通，保留当前绿色主题和系统字体，做局部结构调整。变化/动效/密度取3/2/5；design-taste的营销页排版、首屏和动画规范不用于此业务页面。gooes蓝色Admin规范不覆盖orange绿色项目页。

现状：每条日志都可独立展开原生Textarea，autoHeight且min-height=120设计px；工具栏在下方，图片0/9、字数、默认蓝色发送分散排列；仅adjustPosition与cursorSpacing=24，没有键盘高度、固定页脚或单一活跃编辑器协调。图片移除按钮在缩略图下方占位，选9图后增加布局不稳定。截图中的项目头、甘特图和底部导航已明显挤压评论空间。

建议保持评论始终行内，输入改为页面唯一的底部编辑区：

- 日志下仅保留紧凑“写评论…”入口；点击回复/写评论唤起同一个输入区，并显示当前日志及“回复姓名”。这不恢复先点“项目沟通”才能看评论的流程。
- 输入区挂在页面根部，不挂在每条时间线、transform祖先或滚动裁切容器内。复用现有Taroify组件；若使用Popup，应核对实际挂载位置，不能假定其自动portal到页面根。
- 上行：回复对象摘要与取消回复；中间：有标签的2-4行输入框；图片选择后显示小缩略图网格和角上移除按钮；下行固定为“添加图片 n/9”、次要字数、绿色发送按钮。空草稿禁用发送，上传中保留布局并显示进度/失败状态。
- 一个页面最多一个活跃编辑器；切换日志或回复对象不能把附件/正文误发到别条日志，未发送草稿按日志与身份保存于内存，用户明确放弃才丢弃。身份/项目退出按既有规则清空。
- 使用当前绿色语义token，发送不再使用未定制的默认蓝色。评论作者/时间12-13px，正文14-15px，触摸目标至少44px；这些是设备CSS px目标，工程designWidth=750，需要按现有px转换规则换算，不能直接当750设计px照抄。
- 作者和时间保持可换行/省略的边界，回复摘要一行截断，评论项间距收紧。AI生成分享与评论编辑分开，不贴在发送栏下；编辑打开时不参与浮动工具栏。

键盘处理选定一种策略，不能同时自动上推页面和完整手动上移：

1. 推荐固定编辑区使用原生Textarea `fixed=true`、`adjustPosition=false`，由 `onKeyboardHeightChange` 处理原始px键盘高度，统一移动整个编辑区。不能只上移textarea，留下图片/发送被遮挡。
2. 键盘关闭时bottom=0且保留底部安全区；键盘打开时贴键盘上沿，不重复加安全区；需要以当前微信窗口实际resize/键盘事件核对偏移，避免双倍抬升。不要硬编码键盘高度或忽略全部height=0事件。
3. 键盘打开/编辑时协调客户tab栏与员工固定底部动作，隐藏或让其位于编辑区下方，关闭恢复；正文保留占位/滚动空间，不能改变业务权限。
4. 不用无限autoHeight；输入区保持2-4行可滚动，图片网格在可用高度内滚动，发送行始终可点。500字、9图、小屏、中文候选栏同时出现仍可操作。
5. onFocus/onBlur、选图/预览返回、键盘收起分别管理；blur不能销毁草稿，打开相册导致页面hide不能误当身份退出。关闭输入器恢复原日志阅读位置。
6. 如暂保留行内输入，必须让整个composer滚动进入可用区域并选择adjustPosition=true一条路径；不能同时再bottom=键盘高度。仅扩大cursorSpacing不能完成整个工具栏避让。

## 官方与安装版本核对

当前依赖为Taro 4.1.11、Taroify ^0.9.2，没有taro-ui依赖。读取已安装 `@tarojs/components/types/Textarea.d.ts` 确认fixed/adjustPosition/cursorSpacing/onKeyboardHeightChange；读取Taroify textarea/native-textarea、popup和uploader类型。

- [Taro UI AtTextarea源码](https://github.com/NervJS/taro-ui/blob/dev/src/components/textarea/index.tsx)及[类型](https://github.com/NervJS/taro-ui/blob/dev/types/textarea.d.ts)：包装原生Textarea并转交fixed/cursorSpacing等，不包含完整“输入＋图片＋发送”键盘避让容器。不能以换AtTextarea替代页面协调，也不引入第二套UI库。
