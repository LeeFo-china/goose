# Admin UI Style Guide

本文档用于统一 `apps/admin` 后台管理系统的页面结构、主题颜色、组件使用和交互细节。后续新增或重构 Admin 页面时，应优先遵循本文档。

> 2026-05-15 起，新的总入口文档为 `docs/admin-design-system-guidelines.md`。本文保留历史规范内容；新增页面和后续整改优先参考总入口文档。

## 整体定位

`apps/admin` 是面向内部员工和管理员的业务后台，整体风格应保持：

- 企业后台 / 运维管理 / CRM 风格。
- 清爽、克制、工具型，优先保证信息密度和可扫描性。
- 白底、浅灰边框、轻阴影、卡片分区、表格为主。
- 不做营销式 hero，不做大面积渐变背景，不做强装饰视觉。

## 页面结构

后台页面统一采用以下结构：

1. 顶部标题区
   - 左侧：`h1` + 一句简短说明。
   - 右侧：当前页面主操作，例如“新增员工”“新建活动”。

2. 摘要区
   - 用指标卡展示当前页面核心状态。
   - 指标卡数量建议 3-4 个。

3. 筛选区
   - 筛选表单放在一个 `Card` 内。
   - 输入框、下拉框、搜索按钮保持同一行高度。

4. 主体区
   - 列表页使用表格。
   - 配置页使用 Tabs + 配置项列表。
   - 运维页使用实时状态面板 + 脚本卡片 + 执行记录。

5. 分页区
   - 放在表格卡片下方。
   - 左侧显示：`每页 X 条，共 Y 条`。
   - 右侧显示：`上一页 / 下一页`。

页面主间距统一使用 `gap-5`，卡片内边距优先使用 `p-4` 或 `p-5`。

## 主题颜色

颜色应优先使用现有 Tailwind token 和 CSS variables，不随意新增硬编码颜色。

- 主操作：`primary`
- 普通背景：`background`
- 卡片背景：`card`
- 主文本：`foreground`
- 次级文本：`muted-foreground`
- 边框：`border`
- 成功状态：`success`
- 警告状态：`warning`
- 危险状态：`destructive` / `danger`
- 中性状态：`outline` / `secondary`

按钮颜色规则：

- 主操作按钮使用 `default`。
- 次操作按钮使用 `outline`。
- 轻操作、切换类操作使用 `ghost`。
- 危险操作使用 `destructive`。

状态 Badge 规则：

- 成功、在线、启用：`success`
- 运行中、警告、待处理：`warning`
- 失败、离线、禁用、删除：`danger`
- 普通信息：`outline` 或 `secondary`

## 组件使用

优先使用已有组件：

- `Button`
- `Badge`
- `Card`
- `Table`
- `Input`
- `Textarea`
- `Select`
- `Dialog`
- `DataTable`
- `StatusAlert`
- `Skeleton`

图标统一使用 `lucide-react`。

不要在新页面里手写一套独立的按钮、表格、弹窗或状态样式。确实需要新组件时，应复用现有 token 和布局约定。

## 列表页规范

列表页应保持统一结构：

- 页面标题区。
- 指标卡。
- 筛选卡。
- 表格卡。
- 分页区。

表格规范：

- 优先使用 `DataTable`。
- 短字段使用 `whitespace-nowrap`。
- 长字段使用 `truncate`。
- 状态字段使用 `Badge`。
- 操作列放在右侧。
- 避免列内容因为容器过窄频繁换行。
- 表格容器可设置稳定的 `minWidth`，让横向滚动优于挤压换行。

分页规范：

- 每页条数由页面固定，通常为 10 或 20。
- 页码状态写入 URL query。
- 翻页按钮使用 `outline`。
- 异步切换时使用 `Loader2`。

## 表单规范

新建和编辑优先使用 `Dialog`。

表单规则：

- 字段标签使用 `FieldLabel` 或 `Label`。
- 输入控件保持统一高度。
- 必填校验使用 `zod + react-hook-form`。
- 保存按钮放在右下角。
- 异步提交时按钮内显示 `Loader2`。
- 错误提示使用 `StatusAlert`。
- 成功后刷新当前页面或局部数据。

表单布局：

- 简单表单使用单列。
- 字段较多时使用响应式双列。
- 不要让输入框、按钮或错误提示相互挤压。

## 卡片规范

卡片只用于明确的信息容器：

- 指标卡。
- 表格容器。
- 配置分组。
- 运维脚本项。
- 详情面板。

避免卡片套卡片。不要把整页所有 section 都做成浮动大卡片。

卡片圆角和边框沿用现有 `Card` 组件，不额外做夸张阴影或大圆角。

## 运维页面规范

运维页面应偏工具化和信息密集：

- 顶部显示实时状态或关键指标。
- 自动刷新应静默执行，不让主按钮反复闪 loading。
- 手动刷新时才显示按钮 loading。
- 只读实时接口不应写入操作记录。
- 手动执行脚本才写入最近执行记录。
- 运行结果输出使用等宽字体和 `Textarea` 或预格式文本。

资源状态展示建议：

- CPU 使用环形进度。
- 内存和磁盘使用横向进度条。
- PM2 进程使用状态 Badge + 数值指标。

## 系统配置页面规范

配置项较多时必须分组展示：

- 使用 Tabs 切换配置组。
- Tab 状态写入 URL，例如 `/settings?group=ai`。
- Tab 上显示配置项数量。
- 有未配置项时显示提示数量。

配置项规则：

- 非敏感配置可显示当前生效值。
- 敏感配置只显示掩码。
- 敏感配置输入框使用 `password`。
- 数据库配置优先，环境变量作为回退。
- 配置项的“重置 / 保存”按钮在桌面端垂直居中。

## 响应式规则

- 桌面端优先信息密度。
- 移动端允许纵向堆叠。
- 按钮组在移动端自然换行。
- 表格优先横向滚动，不强行压缩字段。
- 不使用随 viewport 缩放的字体大小。

## 文案规则

- 页面说明应短，解释当前页面职责即可。
- 按钮文案使用明确动作，例如“新增”“保存”“删除”“刷新”。
- 不在页面里写使用说明式长文案。
- 错误提示要可操作，避免只显示“失败”。

## 后续新增页面检查清单

新增或重构 Admin 页面时，至少检查：

- 是否复用了现有 `Card / Button / Badge / DataTable / Dialog`。
- 是否使用现有颜色 token，而不是硬编码颜色。
- 页面是否有统一的标题区和说明。
- 列表页是否有筛选、表格、分页。
- 表格短字段是否避免无意义换行。
- 异步操作是否有 loading 和错误态。
- 敏感信息是否只显示掩码。
- 自动刷新是否静默，不干扰按钮状态。
- 移动端是否不会出现明显重叠或溢出。
